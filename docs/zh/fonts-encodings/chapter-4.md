# 第四章 · 规范化、双向算法与东亚字符体系
### Chapter 4: Normalization, bidirectionality, and East Asian characters
**著者：雅尼斯·哈拉兰布斯 博士（Yannis Haralambous, Ph.D.）**  
*选自《字体与编码》（Fonts & Encodings）原著第 127–158 页*

*译者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

---

在理解了 Unicode 字符的基本定义、底层编码形式与宏观平面布局之后，我们必须正视文本排印中最棘手的三大计算挑战：**字符序列的等价正规化**、**多文种混排的双向流动算法**、以及**东亚表意汉字与音节文字的复杂拓扑结构**。

这三个领域分别对应着现代数字文本处理的核心灵魂：若没有规范化，搜索引擎将无法在海量异构文本中建立确定性的索引；若没有双向算法，阿拉伯文与希伯来文将永远无法与西方字母在同一段落内和谐共存；若没有对东亚文字体系的深刻数理建模，包含数万汉字的庞大信息世界将陷入字符爆炸的泥潭。

## 分解与规范化（Decompositions and Normalizations）

Unicode 继承了大量历史编码遗留下来的“预合成字符”（Precomposed Characters，例如带有重音符的拉丁字母 ‘é’、‘ü’），同时也提供了“基础字符 + 组合变音符”（Base Character + Combining Marks）的动态组合机制。

这就引发了一个严重的数学问题：对于人类视觉和语义完全相同的同一个文字单位，在计算机内部可能存在多种完全不同的二进制码位序列！例如，带有上加抑音符的字母 ‘è’ 可以表示为：
* 单一预合成字符：`U+00E8`（LATIN SMALL LETTER E WITH GRAVE）；
* 基础字符加组合标记：`U+0065`（LATIN SMALL LETTER E）+ `U+0300`（COMBINING GRAVE ACCENT）。

如果系统不对这些序列进行标准化规整，字符串相等性比较、哈希表查找以及数据库主键匹配将彻底失效。为此，Unicode 联合创始人马克·戴维斯（Mark Davis）与马丁·迪尔斯特（Martin Dürst）共同制定了 **Unicode 标准附件第 15 号（UAX #15: Unicode Normalization Forms）**。

### 组合字符与规范结合类（Combining Characters & Combining Classes）

当一个基础字符同时附带多个不同方位的变音符号时（例如越南语或古希腊语中的多重重音字母），变音符号在数据流中的先后顺序是否可以任意颠倒？

语言学与排版学表明：变音符号可以划分为彼此正交的方位类别。如果在不同方位（例如一个在字符下方，另一个在字符上方），则它们的施加顺序并不影响最终的印刷视觉形态；但如果两个变音符号处于同一个物理方位（例如两个都在字符上方依次叠放），则它们自下而上的堆叠顺序就具有决定性的拓扑意义！

为了在数理上严格形式化这一规则，Unicode 为每一个组合字符分配了一个介于 $0 \sim 255$ 之间的整数属性——**规范结合类（Canonical Combining Class, ccc）**：
* **Class 0（Spacing / Base Characters）**：所有基础字符、不可见控制符以及普通空格；
* **Class 1（Overlay）**：覆盖在字符中央的叠置标记（例如删除线、斜杠横杠）；
* **Class 7（Nukta）**：印度次大陆文字中紧随辅音的下方读音微调点；
* **Class 8（Kana Voicing）**：日文假名的浊点（゛）与半浊点（゜）；
* **Class 9（Virama）**：印度系文字中用于消除辅音固有元音、强制构成结合字的结音符（Halant / Virama）；
* **Class 200–214（Fixed Position Marks）**：希伯来文圣经吟诵音符等固定位置特殊标记；
* **Class 216（Attached Below / ATBL）**：紧贴在字符下方的字形变体（如罗马尼亚文逗号）；
* **Class 218（Attached Below Right）**：紧贴字符右下方的标记；
* **Class 220（Below / B）**：位于字符正下方的变音符（如变音下加点 `U+0323`、软音符 Cedilla）；
* **Class 222（Below Right / BR）**：位于字符右下方的独立变音符；
* **Class 228（Above / A）**：位于字符正上方的变音符（如锐音符、抑音符、长音符 Macron `U+0304`、波浪符 Tilde）；
* **Class 230（Above Right / AR）**：位于字符右上方的变音符；
* **Class 232（Double Above / DA）**：横跨在两个连续字符上方的双重变音符；
* **Class 240（Iota Subscript）**：古希腊文特有的下加 Iota 标记。

### 规范重排序算法（Canonical Ordering Algorithm）

有了结合类，Unicode 确立了确定性的**规范重排序算法（Canonical Ordering Algorithm）**：
1. 从左至右扫描字符串；
2. 基础字符（`ccc = 0`）的位置保持绝对不动；
3. 任何附属于该基础字符之后的连续组合字符序列，按照其**规范结合类数值（ccc）的大小升序排列**；
4. 若两个相邻组合字符的 `ccc` 数值完全相同，则保持它们原有的相对先后顺序不变（保证同向堆叠层级不被篡改）。

例如，字符 ‘a’ 同时附带下方加点（`U+0323`，`ccc = 220`）与上方长音符（`U+0304`，`ccc = 228`）：
* 序列一：`U+0061` + `U+0323`（下点 220）+ `U+0304`（长音 228）；
* 序列二：`U+0061` + `U+0304`（长音 228）+ `U+0323`（下点 220）。  
经过规范重排序算法处理后，由于 $220 < 228$，序列二将被确定性地强制重排为序列一！

### 规范分解与兼容分解

Unicode 定义了两种不同层级的字符分解：
* **规范分解（Canonical Decomposition）**：  
  仅针对在语言学和排版功能上**完全等价、绝对无损**的字符对。例如将预合成的 ‘é’（`U+00E8`）分解为 ‘e’（`U+0065`）+ 抑音符（`U+0300`）；
* **兼容分解（Compatibility Decomposition）**：  
  针对在排版样式、历史字模或遗留工业标准中存在细微视觉格式差异、但在纯文本语义上等价的字符。例如：
  * 日本排版连字 ‘㎦’（`U+33A6`）兼容分解为 ‘k’ + ‘m’ + 上标 ‘3’（`U+00B3`），上标 ‘3’ 进一步分解为普通数字 ‘3’；
  * 罗马数字 ‘Ⅳ’（`U+2163`）兼容分解为字母 ‘I’ + ‘V’；
  * 欧文印刷连字 ‘ﬁ’（`U+FB01`）兼容分解为 ‘f’ + ‘i’；
  * 全角英文字母 ‘Ａ’（`U+FF21`）兼容分解为普通 ASCII ‘A’；
  * 圆圈包围字符 ‘①’（`U+2460`）兼容分解为数字 ‘1’。

### 四大规范化形式（The Four Normalization Forms）

将上述两种分解方式与规范重排序及规范合成相结合，便诞生了全球通用的四大规范化形式：

| 规范化形式 | 英文全称 | 核心机制 | 典型适用场景 |
| :--- | :--- | :--- | :--- |
| **NFD** | Normalization Form D | 规范分解（Canonical Decomposition）+ 结合类升序重排序 | 语言学音标分析、变音符提取、字符搜索引擎底层 |
| **NFC** | Normalization Form C | 先执行 NFD 规范分解，再通过算法将字符重新**规范合成（Canonical Composition）** | **W3C、HTML、XML 及现代 Web 的绝对默认标准** |
| **NFKD** | Normalization Form KD | 兼容分解（Compatibility Decomposition）+ 结合类升序重排序 | 语义文本抽取、模糊匹配、无格式纯文本转换 |
| **NFKC** | Normalization Form KC | 先执行 NFKD 兼容分解，再执行规范合成 | 全局搜索引擎建立倒排索引、标识符标准化 |

## 双向排版算法（The Bidirectional Algorithm / UAX #9）

在由西方字母构成的单向世界中，文本流淌的方向是单一而自然的：从左向右（LTR）。然而在近东文明中，阿拉伯文、希伯来文、叙利亚文与它拿字母均是从右向左（RTL）书写。

当一篇现代科学文献、法律条约或网络百科中同时出现英语、希伯来语、阿拉伯语与数学公式时，计算机排版系统面临着极其惊心动魄的挑战：
1. **段落阅读的大方向与行内嵌套小方向的冲突**；
2. **文本在从右至左流动时，嵌入其中的阿拉伯数字却是从左至右书写的！**
3. **括号、引号与数学不等号在视觉呈现时必须根据文本流向发生物理镜像翻转！**
4. **多行排版时断行（Line Breaking）位置的双向边界重组！**

这就是著名的 **Unicode 双向排版算法（Unicode Bidirectional Algorithm, 简称 Bidi 算法，收录于 UAX #9）**。

### 段落排印的宏观流动与微观断行

作者在此给出了一个极富启发的双向排版断行实验：假设我们在一段英文（从左向右）中嵌入了一句从右向左书写的阿拉伯语诗句。若以小写反向拼写来模拟从右向左的文本流动，这段嵌入文本呈现为：
> First second third fourth hthgie htneves htxis htfif  
> htneetriht htflewt htnevele htnet htnin fourteenth  
> fifteenth sixteenth seventeenth.

注意到第二行的排列：由于这是一段从右向左流动的段落，当第一行右端空间不足发生断行时，文本并不是从第二行左侧开始，而是**从第二行最右侧继续向左书写**！当嵌入的从右向左段落结束后，英文文本（`fourteenth ...`）又恢复从左侧排起。若没有严格的数学算法指导，排版软件在计算折行坐标时将产生毁灭性的视觉错乱。

此外，数字的处理更是雪上加霜：在阿拉伯文与希伯来文中，**数字无论何时都必须从左向右书写**。例如作者的生日写作：
`Friday, February 16, 1962`
在阿拉伯语中，单词部分从右至左，但数字 `1962` 与 `16` 却必须保持从左至右。这意味着每一个数字串都被视为一个微观的从左至右“孤岛”。

### 双向字符类型（Bidirectional Character Types）

为了精确控制每一个字符的双向行为，Unicode 为全部 111 万个码位分配了唯一的双向类型，共划分为三大类 19 种属性：

1. **强字符类型（Strong Types）**：  
   具有绝对固有的书写方向，主导周围文本的排版趋势：
   * **L（Left-to-Right）**：所有拉丁字母、西里尔字母、希腊字母、东亚汉字与假名；
   * **R（Right-to-Left）**：希伯来字母及相关闪米特辅音文字；
   * **AL（Arabic Letter / Right-to-Left Arabic）**：阿拉伯字母及其专有标点（在数字处理上具有比 R 更强的语境推导力）。
2. **弱字符类型（Weak Types）**：  
   其方向性在很大程度上取决于其所处的上下文环境：
   * **EN（European Number）**：欧洲拉丁数字（`0`–`9`）；
   * **ES（European Number Separator）**：欧洲数字正负号（`+`、`-`）；
   * **ET（European Number Terminator）**：货币与百分比符号（`$`、`%`、`€`）；
   * **AN（Arabic-Indic Number）**：阿拉伯-印度数字（`٠`–`٩`）；
   * **CS（Common Number Separator）**：数字通用分隔符（冒号、逗号、小数点、不换行空格，共 11 个字符）；
   * **NSM（Non-Spacing Mark）**：组合变音符与变体选择符（自动继承其基底字符的方向类型）；
   * **BN（Boundary Neutral）**：排版边界中性符（零宽连字/非连字控制符、语言标签）。
3. **中性字符类型（Neutral Types）**：  
   本身完全没有方向倾向，方向完全由周围强字符决定：
   * **B（Paragraph Separator）**：段落分隔符（回车 `\r`、换行 `\n`）；
   * **S（Segment Separator）**：制表符 Tab；
   * **WS（Whitespace）**：所有非零宽度的普通空格；
   * **ON（Other Neutral）**：通用标点符号、数学运算符、几何图形、绘图符号等（共 3,007 个字符）。
4. **显式控制符（Explicit Formatting Codes）**：  
   排版人员可强行插入代码流以覆盖默认算法的 5 大特殊控制字符：`LRE`（左至右嵌入）、`RLE`（右至左嵌入）、`LRO`（左至右强制覆盖）、`RLO`（右至左强制覆盖）与 `PDF`（弹出方向格式化状态）。

### 双向算法六大步骤（The Six Steps of UAX #9）

Bidi 算法由六大紧密相扣的计算阶段构成：
* **步骤一：确立段落基准级别（Base Level）**：  
  扫描段落中的第一个强类型字符；若为 L 则基准级别 $S_0 = 0$（默认 LTR）；若为 R 或 AL 则基准级别 $S_0 = 1$（默认 RTL）。
* **步骤二：解析显式嵌入级别（Explicit Levels & Stack）**：  
  维护一个方向嵌套堆栈（最高支持 61 层，后续版本扩展至 125 层）。每遇到 `LRE`/`RLE`/`LRO`/`RLO` 便将新的级别压栈，遇到 `PDF` 则退栈。偶数级别代表从左向右，奇数级别代表从右向左。
* **步骤三：解析弱类型（Resolving Weak Types, W1–W7）**：  
  * **W1**：所有 `NSM` 继承其前驱基底字符的类型；
  * **W2**：若 `EN` 的左侧最近强字符为 `AL`，则该 `EN` 变为 `AN`；
  * **W3**：所有 `AL` 转为 `R`；
  * **W4**：夹在两个 `EN` 之间的单个 `ES`（如 `1+1`）或夹在两数之间的 `CS`（如 `3.14`）变为 `EN`；
  * **W5**：紧邻 `EN` 前后的连续 `ET`（如 `$100`）变为 `EN`；
  * **W6**：所有未被吸收的孤立 `ET`、`ES`、`CS` 全部退化为 `ON`；
  * **W7**：若 `EN` 前面的最近强字符为 `L`，则该 `EN` 变为 `L`。
* **步骤四：解析中性类型（Resolving Neutral Types, N1–N2）**：  
  * **N1**：若一段连续中性字符（空格或标点）两侧的字符方向相同，则该中性段直接变为该方向；
  * **N2**：若两侧方向相反，则该中性段的类型退回到当前嵌入环境的基准方向。
* **步骤五：确定隐式级别（Resolving Implicit Levels, I1–I2）**：  
  依据字符最终确立的类型（L、R、AN、EN），对其所在的显式级别进行最终调整微调（例如在偶数级别中的 R 需加 1 变成奇数）。
* **步骤六：行内重排与镜像翻转（Reordering & Mirroring, L1–L4）**：  
  找出当前行内的最高级别 $L_{\max}$，从最高级别逐步递减到最低级别，对处于当前级别及以上的所有连续子串进行**逐级倒序反转（Reverse）**！并在反转完成后，对所有具备镜像属性的字符执行字形翻转。

#### 嵌套反转生动算例
考虑嵌套字符串：`[0He said that “˝[1[2yes]2 means yes]1ˇ”.]0`  
* 级别 2 的子串 `[2yes]2` 最先发生第一级反转；
* 随后在级别 1 范围内进行第二级反转，内部已反转的子串再次被整体反转；
* 最终输出完美的物理显示序列。

### 镜像属性（Mirroring & BidiMirroring.txt）

双向排版中最令人叹为观止的细节莫过于**字符镜像**。在西方语言中，左圆括号 ‘(’ 象征着一段语句的“开始”；然而在从右向左流动的阿拉伯语或希伯来语文本文档中，“语句的开始”在物理空间的右侧！因此，排版引擎在渲染右横向文本时，如果遇到 ‘(’，绝不能直接画出向右凸出的弧线，而必须动态将其翻转为向左凸出的 ‘)’！

Unicode 专门发布了标准化映射文件 `BidiMirroring.txt`，其中收录了多达 **320 对具有严格几何镜像关系的字符**：
* 各种括弧：`(` 与 `)`、`[` 与 `]`、`{` 与 `}`、`〈` 与 `〉`、`«` 与 `»`；
* 数学关系运算符：`<` 与 `>`、`≤` 与 `≥`；
* 几何箭头：$\leftarrow$ 与 $\rightarrow$。

## 东亚书写系统（East Asian Scripts）

东亚表意文字系统是人类文字进化史上最壮丽的丰碑，同时也是计算机文字编码最具挑战性的领域。

### 中日韩汉字表意文字（Ideographs of Chinese Origin / CJK）

汉字起源于古代中国黄河流域的甲骨文与金文，历经数千年演化，传播至朝鲜半岛、日本列岛与越南，形成了横跨多国的“汉字文化圈”。

然而，汉字与西方拼音文字存在根本差异：它不是由几十个字母拼成的线形串，而是具有庞大字数、二维方块结构以及一字多音多义的表意体系。仅《康熙字典》便收录了 47,035 个汉字，而当今跨国学术与古籍整理涉及的汉字总量更是突破了十万之巨！

面对如此浩瀚的字海，Unicode 联合中日韩三方专家成立了**表意文字工作组（Ideographic Rapporteur Group, IRG）**，推进了计算历史上最伟大的**中日韩汉字统合（Han Unification）**工程：
* 剔除字形上的微小异体写法，确立以《康熙字典》214 个部首及笔画拓扑结构为准则的统合规则；
* 构建统汉字数据库（Unihan Database），为每个汉字记录其在普通话、粤语、唐代中古音、日文音读与训读、韩语音读以及越南语中的全部读音与交叉索引属性。

#### 汉字结构描述字符（Ideographic Description Characters, IDC）

尽管 Unicode 收录的汉字已达七万余个，但世界上总会存在某些地方志、宋元刻本或古代碑帖中从未被标准编码的罕见汉字。为了解决这一“外字（Gaiji）”危机，Unicode 在 $0\text{x2FF0} \sim 0\text{x2FFB}$ 区段引入了 **12 个表意文字描述字符（IDC）**。

这些字符不是可打印汉字，而是**前缀二元或三元结构操作符**，采用波兰前缀表达式（Prefix Notation）描述汉字的二维几何装配结构：

| 码位 | 字符符号 | 结构名称 | 语法与含义 | 范例装配 |
| :---: | :---: | :--- | :--- | :--- |
| `U+2FF0` | ⿰ | 左右结构（Left-to-Right） | 二元操作符：左部件 + 右部件 | ⿰ 禾 口 $\to$ 和 |
| `U+2FF1` | ⿱ | 上下结构（Above-to-Below） | 二元操作符：上部件 + 下部件 | ⿱ 艹 化 $\to$ 花 |
| `U+2FF2` | ⿲ | 左中右结构（Left-to-Middle-and-Right） | 三元操作符：左 + 中 + 右 | ⿲ 氵 木 ⿹ $\to$ 澍 |
| `U+2FF3` | ⿳ | 上中下结构（Above-to-Middle-and-Below） | 三元操作符：上 + 中 + 下 | ⿳ 𠂉 一 心 $\to$ 意 |
| `U+2FF4` | ⿴ | 全包围结构（Full Surround） | 二元操作符：外框 + 内部件 | ⿴ 囗 大 $\to$ 因 |
| `U+2FF5` | ⿵ | 上三包围（Surround from Above） | 二元操作符：上外框 + 内部件 | ⿵ 门 日 $\to$ 间 |
| `U+2FF6` | ⿶ | 下三包围（Surround from Below） | 二元操作符：下外框 + 内部件 | ⿶ 凵 凶 $\to$ 鬯 |
| `U+2FF7` | ⿷ | 左三包围（Surround from Left） | 二元操作符：左外框 + 内部件 | ⿷ 匚 矢 $\to$ 医 |
| `U+2FF8` | ⿸ | 左上包围（Surround from Upper Left） | 二元操作符：左上外框 + 内部件 | ⿸ 广 林 $\to$ 麻 |
| `U+2FF9` | ⿹ | 右上包围（Surround from Upper Right） | 二元操作符：右上外框 + 内部件 | ⿹ 戈 弋 $\to$ 鸢 |
| `U+2FFA` | ⿺ | 左下包围（Surround from Lower Left） | 二元操作符：左下走之 + 内部件 | ⿺ 辶 巛 $\to$ 巡 |
| `U+2FFB` | ⿻ | 镶嵌穿插结构（Overlaid） | 二元操作符：两部件穿插叠合 | ⿻ 二 十 $\to$ 井 |

### 字符描述语言（Character Description Language, CDL）

在 1980 年代，精通中文的美国计算机学者汤姆·毕晓普（Tom Bishop）为了开发汉字教学软件中动态展示笔画顺序的功能，发明了一套描述汉字内部几何骨架的语言。伴随着 XML 技术的风靡，毕晓普与理查德·库克（Richard Cook）将其升华为正式提交给 Unicode 技术委员会的 **字符描述语言（Character Description Language, CDL）**。

CDL 采用简洁的 XML 语法，通过两种机制精确构建汉字：
1. **组件嵌套复用（Component-based）**：使用已有的汉字或部首及其相对坐标系拼合新字：
```xml
<cdl char="沰">
  <comp char="氵" points="0,0 40,128"/>
  <comp char="石" points="50,10 128,128"/>
</cdl>
```
2. **纯笔画装配（Stroke-based）**：通过笔画类型代码与起止控制点坐标直接绘制基础部件：
```xml
<cdl char="氵">
  <stroke type="d" points="30,10 40,25"/>
  <stroke type="d" points="25,45 35,60"/>
  <stroke type="t" points="10,110 50,80"/>
</cdl>
```

### 朝鲜语谚文（Hangul）与字母算术

在东亚所有书写体系中，朝鲜语的**谚文（Hangul）**展现出了全人类文字史上最卓越的理知设计与数理纯粹性。

1443 年，朝鲜王朝第四代君主**世宗大王（Sejong the Great）**有感于汉字深奥难通、普通百姓无法申诉冤屈，亲自率领集贤殿学者历时四年创造了《训民正音》（Hunminjeongeum）。这是一套由 17 个基础辅音与 11 个基础元音构成的拼音文字体系，其设计深刻凝聚了语音学与哲学智慧：

#### 辅音的生理发音器官几何象征
* **‘ㄱ’（k/g）**：象形舌根闭塞咽喉之状；
* **‘ㄴ’（n）**：象形舌尖抵住上颚齿龈之状；
* **‘ㅁ’（m）**：象形嘴唇闭合之状；
* **‘ㅅ’（s）**：象形门齿锋利之状；
* **‘ㅇ’（ng/零声母）**：象形喉咙圆通虚空之状。  
在此基础上，通过在基础笔画上**加画（Stroke Addition）**来表达送气清音：如在 ‘ㄱ’ 上加一横变为送气音 ‘ㅋ’；在 ‘ㄴ’ 上加横变为 ‘ㄷ’，再加一横变为送气 ‘ㅌ’；在 ‘ㅁ’ 上加竖变为 ‘ㅂ’，再加横变为送气 ‘ㅍ’！

#### 元音的天地人三元宇宙观
* **‘·’（天，圆）**：象征无边无际的穹苍；
* **‘ㅡ’（地，平）**：象征平坦辽阔的大地；
* **‘ㅣ’（人，立）**：象征顶天立地的人类。  
三者交合化育万物：‘·’ 居于 ‘ㅡ’ 之上为 ‘ㅗ’（阳），居于 ‘ㅡ’ 之下为 ‘ㅜ’（阴）；‘·’ 居于 ‘ㅣ’ 之右为 ‘ㅏ’（阳），居于 ‘ㅣ’ 之左为 ‘ㅓ’（阴）。

### 现代谚文音节块的数字算法艺术

尽管谚文在本质上是拼音字母（Jamo），但它在视觉排印上**绝不横向线性排列**，而是将初声辅音（Initial, $L$）、中声元音（Medial, $V$）与可选的终声韵尾辅音（Final, $T$）严格组装为一个类似汉字的方块音节块！

一般音节结构遵循正则文法：
$$S = L + V + T^*$$

为了避免将初声与终声混淆，Unicode 规定了 19 个初声（$L$）、21 个中声（$V$）与 28 种终声状态（$T$，包括 27 个韵尾及一个“无韵尾”的空状态）。现代谚文全部可能的合法音节组合总数精确为：
$$N = 19 \times 21 \times 28 = 11{,}172$$

Unicode 在基本多语言平面的 $0\text{xAC00} \sim 0\text{xD7A3}$ 区段，完整开辟了这 11,172 个预合成音节块。任何一个谚文音节的码位，均可通过极其优美的高中代数方程无缝双向计算：

$$\text{CodePoint} = \text{0xAC00} + (L_{\text{index}} \times 588) + (V_{\text{index}} \times 28) + T_{\text{index}}$$

其中：
* $588 = 21 \times 28$ 为每个初声辅音所统辖的连续音节跨度；
* $28$ 为每个中声元音所统辖的连续终声跨度。

#### 算例验证：“한글”（Hangul）
以单词 “한글” 为例：
1. **第一个音节 “한”（Han）**：
   * 初声 ‘ㅎ’：索引 $L_{\text{index}} = 18$；
   * 中声 ‘ㅏ’：索引 $V_{\text{index}} = 0$；
   * 终声 ‘ㄴ’：索引 $T_{\text{index}} = 4$；
   * 码位计算：$0\text{xAC00} + (18 \times 588) + (0 \times 28) + 4 = 0\text{xAC00} + 10584 + 4 = 0\text{xAC00} + 0\text{x295C} = 0\text{xD55C}$（即 `U+D55C`，한）。
2. **第二个音节 “글”（Geul）**：
   * 初声 ‘ㄱ’：索引 $L_{\text{index}} = 0$；
   * 中声 ‘ㅡ’：索引 $V_{\text{index}} = 18$；
   * 终声 ‘ㄹ’：索引 $T_{\text{index}} = 8$；
   * 码位计算：$0\text{xAC00} + (0 \times 588) + (18 \times 28) + 8 = 0\text{xAC00} + 504 + 8 = 0\text{xAC00} + 0\text{x0200} = 0\text{xAE00}$（即 `U+AE00`，글）。

通过这一纯粹的整数算术，操作系统和文本引擎在处理谚文时完全无需查表，便能在单个 Jamo 字母与完整音节方块之间实现飞一般的瞬时合成与分解，达到了理性与工程的最高和谐！
