# 第三章 · Unicode 字符核心属性体系
### Chapter 3: Properties of Unicode Characters
**著者：雅尼斯·哈拉兰布斯 博士（Yannis Haralambous, Ph.D.）**  
*选自《字体与编码》（Fonts & Encodings）原著第 95–126 页*

---

在第二章中，我们鸟瞰了 Unicode 宏大平面的拓扑版图与多字节编码形式的数理机制。然而，如果仅仅将文字符号视为一连串冰冷的十六进制整数码位（code points），计算机在面对实际排版、文本检索、断行折行与大小写转换时依然会寸步难行：
* 当屏幕遇到一个空格时，它究竟允许排版引擎在此处换行，还是必须作为一个绝对不可断开的不换行空格（no-break space）？
* 当用户按下全大写转换键时，德语字母 “ß” 应当转换为何种形式？土耳其语中带点的 “i” 与不带点的 “ı” 应当如何映射？
* 在阿拉伯文与印度次大陆文字中，某两个字符相邻时究竟应当熔接为复合连写，还是各自保持独立？

为了赋予抽象字符以完整的可计算语义，Unicode 联盟构建了一套人类计算历史上最为繁复、详尽且严密的**字符属性系统（Character Properties System）**。每一个入选 Unicode 的字符，都伴随着数十个标准化的元数据属性。正是这套属性网络，构成了现代操作系统、浏览器排版引擎与自然语言处理管线的基础神经中枢。

---

## 基础属性（Basic Properties）

### 1. 字符规范名称（Character Name）

每一个 Unicode 码位都被赋予一个唯一的、全大写的**规范名称（Character Name）**。该名称由且仅由拉丁大写字母 `A`–`Z`、阿拉伯数字 `0`–`9`、连字符 `-` 以及单个空格构成。

Unicode 字符命名遵循极其苛刻的严肃规范：
* **命名永久不可篡改性（Name Stability）**：一旦字符被正式赋予规范名称并随正式标准发布，**该名称将被永久冻结，纵使日后发现存在严重拼写错误或历史学术误解，亦绝不修改更正**！例如，在西里尔字母区，字符 $\text{U+0446}$ 的名称最初被拼写为了 `CYRILLIC SMALL LETTER TSE`，而 $\text{U+049B}$ 被命名为了 `CYRILLIC SMALL LETTER KA WITH DESCENDER`。即便存在瑕疵，规范名称也永不撤回，以免破坏全球现有软件代码库的兼容性；
* **Unicode 1.0 历史旧名称（`Unicode_1_Name`）**：针对 Unicode 1.0 时期遗留的早期命名，规范在附加属性中予以归档备查；
* **ISO 国际注释（`ISO_Comment`）**：记录 ISO/IEC 10646 对应的注释说明；
* **无名称字符的算法自动命名（Algorithmic Names）**：对于庞大的中日韩统一表意汉字（CJK Unified Ideographs）与韩文谚文音节（Hangul Syllables），Unicode 采用规则驱动的算法生成名称。例如，码位 $\text{U+4E00}$ 的官方名称为 `CJK UNIFIED IDEOGRAPH-4E00`；韩文音节根据初声、中声、终声的组合自动生成名称（如 `HANGUL SYLLABLE GAG`）。

### 2. 区块与书写系统（Block and Script）

在 Unicode 空间中，字符在地理与文化维度上受到双重维度的坐标管辖：
* **区块（Block）**：区块是字符在物理码位轴上的连续区间划分，具有确切的起始码位与终止码位（例如 `Basic Latin` 为 $\text{U+0000} \sim \text{U+007F}$，`Hiragana` 为 $\text{U+3040} \sim \text{U+309F}$）。每个字符必然且仅能从属于一个物理区块；
* **书写系统 / 文种（Script）**：书写系统是字符在语言学层面的归属分类（如 `Latin`、`Cyrillic`、`Arabic`、`Han` 等）。
  * 值得注意的是，**区块与书写系统并不存在简单的一对一绑定关系**！例如，数学符号可能分布在多个不同的区块中；
  * 特殊的书写系统标识：对于被多种语言系统所共享的标点符号与空格（如英文句号、问号、空格），其 Script 属性被标记为 **`Common`（通用）**；而对于各类可依附于不同文种基础字母之上的组合变音符号（Combining marks），其 Script 属性被标记为 **`Inherited`（继承自宿主字符）**。

### 3. 时代与版本（Age）

属性 `Age` 记录了该字符首次被正式分配引入 Unicode 标准的版本号（例如 `1.1`、`2.0`、`3.0`、`4.0`、`5.0` 等）。如果一个字符在当前版本中尚未被分配，其 Age 属性为 `Unassigned`。该属性对于向下兼容性检查与通信协议协商至关重要。

## 通用类别分类法（General Category）

在 Unicode 属性矩阵中，最为根本、应用最广泛的核心属性莫过于**通用类别（General Category, 简称 `gc`）**。该属性为每个字符分配一个由两个英文字母构成的标准分类代码：首字母代表宏观主类（大类），次字母代表精细子类。

全套通用分类共分为七大主类、三十个子类：

| 主类（首字母） | 子类代码 | 英文全称 | 核心中文释义与典型代表范例 |
| :--- | :---: | :--- | :--- |
| **字母（Letter, `L`）** | **`Lu`** | Letter, uppercase | 拉丁、希腊、西里尔等文种中的**大写字母**（如 ‘A’, ‘$\Omega$’, ‘Д’）。 |
| | **`Ll`** | Letter, lowercase | 各文种中的**小写字母**（如 ‘a’, ‘$\omega$’, ‘д’）。 |
| | **`Lt`** | Letter, titlecase | **词首大写字母**（如克罗地亚语双合字母 ‘ǅ’, ‘ǈ’, ‘ǋ’）。 |
| | **`Lm`** | Letter, modifier | **修饰字母**（通常上标排印的小型修饰符号，如字母 ‘ʰ’, ‘ʲ’, ‘ʷ’）。 |
| | **`Lo`** | Letter, other | **其他字母**：无大小写区分的文种文字，包括汉字（CJK）、日文假名、希伯来文、阿拉伯文、天城文等。 |
| **标记（Mark, `M`）** | **`Mn`** | Mark, nonspacing | **非空格组合标记**：不占据横向字身宽、直接依附于前驱字符之上/下的变音符（如锐音符 ́、抑音符 ̀）。 |
| | **`Mc`** | Mark, spacing combining | **空格组合标记**：附属于前驱字符，但在横向度量上占据独立间距（如印地语天城文中的元音附标 ॉ、ा）。 |
| | **`Me`** | Mark, enclosing | **封闭环绕标记**：在图形上将前驱字符完全包围圈起的印迹（如环绕圆圈 ⃝、正方形框 ⃞）。 |
| **数值（Number, `N`）** | **`Nd`** | Number, decimal digit | **十进制数字**：严格具有 $0 \sim 9$ 进制位权值的数字（包含 ASCII 数字 0–9、阿拉伯文数字 ٠–٩、全角数字 ０–９）。 |
| | **`Nl`** | Number, letter | **字母型数字**：由书写系统字母充当的数值（如古罗马数字 Ⅰ, Ⅱ, Ⅴ, Ⅹ, Ⅿ）。 |
| | **`No`** | Number, other | **其他数字**：分数符号（如 ½, ¾）、带圈数字（如 ①, ❷）、苏州码子等。 |
| **标点（Punctuation, `P`）** | **`Pc`** | Punctuation, connector | **连接标点**：在词内起连接作用的符号（如下划线 `_`）。 |
| | **`Pd`** | Punctuation, dash | **破折号与连字符**：各种宽度的破折号与连字号（如连字符 `-`、短破折号 En dash ‘–’、长破折号 Em dash ‘—’）。 |
| | **`Ps`** | Punctuation, open | **开启括号/前标点**：各类成对标点的起始开侧（如 ‘(’, ‘[’, ‘{’, ‘《’, ‘（’）。 |
| | **`Pe`** | Punctuation, close | **闭合括号/后标点**：各类成对标点的闭合关侧（如 ‘)’, ‘]’, ‘}’, ‘》’, ‘）’）。 |
| | **`Pi`** | Punctuation, initial quote | **起始引号**（如英文左双引号 ‘“’、法文前书名书状号 ‘«’）。 |
| | **`Pf`** | Punctuation, final quote | **结束引号**（如英文右双引号 ‘”’、法文后书名书状号 ‘»’）。 |
| | **`Po`** | Punctuation, other | **其他通用标点**：句号、逗号、分号、冒号、感叹号、问号、省略号等。 |
| **符号（Symbol, `S`）** | **`Sm`** | Symbol, math | **数学符号**：运算符与关系符（如 $+$, $-$, $=$, $<$, $\sum$, $\int$, $\infty$）。 |
| | **`Sc`** | Symbol, currency | **货币符号**：全球各国货币标记（如 `$`、`€`、`£`、`¥`、`₩`、`₹`）。 |
| | **`Sk`** | Symbol, modifier | **修饰符号**：独立的重音占位符（如非组合式的扬抑符 `^`、抑音符 `` ` ``）。 |
| | **`So`** | Symbol, other | **其他杂项符号**：音乐符号、象棋符号、扑克花色、占星符号、回收标志等。 |
| **分隔符（Separator, `Z`）** | **`Zs`** | Separator, space | **空格分隔符**：各类具有正宽度的空白间隔（包含标准 ASCII 空格、Em 空格、En 空格、细空格、表意全角空格）。 |
| | **`Zl`** | Separator, line | **行分隔符**（严格指代码位 $\text{U+2028}$ / LINE SEPARATOR）。 |
| | **`Zp`** | Separator, paragraph | **段落分隔符**（严格指代码位 $\text{U+2029}$ / PARAGRAPH SEPARATOR）。 |
| **其他控制类（Other, `C`）** | **`Cc`** | Other, control | **控制字符**：继承自 ASCII 与 ISO 2022 的 C0/C1 控制码（如换行 LF、回车 CR、制表符 TAB）。 |
| | **`Cf`** | Other, format | **格式不可见控制符**：不具视觉图元、专门用于驱动排版状态变换的特殊控制符（如双向标记 LRM/RLM、连接控制符 ZWJ/ZWNJ）。 |
| | **`Cs`** | Other, surrogate | **代理区码位**：永久保留给 UTF-16 代理对的物理码位（$\text{U+D800} \sim \text{U+DFFF}$）。 |
| | **`Co`** | Other, private use | **私用区字符**（PUA 码位）。 |
| | **`Cn`** | Other, not assigned | **未分配码位**与永久非字符。 |

## 专用排印与行为控制属性

在通用类别之外，Unicode 为现代排印引擎定义了一系列专门的布尔与枚举属性：

### 1. 永久非字符（Noncharacters）

在 Unicode 的 17 个平面中，特意锁定了 **66 个永久非字符码位（`Noncharacter_Code_Point`）**：
* 位于基本多语言平面的 contiguous 区段：$\text{U+FDD0} \sim \text{U+FDEF}$（共 32 个码位）；
* 位于所有 17 个平面的最后两个端点码位：每个平面的 $\text{U+xxFFFE}$ 与 $\text{U+xxFFFF}$（共 $17 \times 2 = 34$ 个码位，例如 $\text{U+FFFE}, \text{U+FFFF}, \text{U+10FFFE}, \text{U+10FFFF}$）。

规范严格声明：**这 66 个码位在整个人类计算历史上永远不会被赋予任何字符！** 它们被专门保留给应用程序内部作为哨兵值（sentinel values）、错误标记或内存内部私有通信，绝不得在公开的数据交换格式中流通。

### 2. 软点字母（Soft-Dotted Letters）

在西文排印中，小写拉丁字母 ‘i’ 与 ‘j’ 的主干顶端带有一个小圆点（dot / tittle）。当需要在它们上方附加抑音符（`U+0300` ̀）或扬抑符（`U+0302` ̂）时，排印规则要求**原有的小圆点必须彻底消失**，替换为重音符号（形成 ‘ì’、‘î’），否则就会出现圆点与重音符重叠打架的滑稽视觉灾难！

具有这种属性的字符被标记为 **`Soft_Dotted`**。排版渲染引擎在检测到软点字母接续组合变音符时，会自动加载无点字形（dotless i ‘ı’, dotless j ‘ȷ’）来承接上方的变音符号。

### 3. 连接控制符（Join Control）与复杂文种排印

对于阿拉伯文、波斯文以及印度次大陆天城文等高度依赖上下文草书连写的文种，Unicode 设立了两个最为著名的格式控制符（`Join_Control`）：
* **零宽连字（Zero Width Joiner, ZWJ, $\text{U+200D}$）**：  
  强制让两个原本在排版规则下不相连的相邻字符发生上下文连写（Ligature / Joining）。在梵文天城文中，ZWJ 可以强制将原本呈现为带下斜杠杀音符（Virama）的死辅音转换为半字符（Half-form）；在现代 Emoji 表情符号中，ZWJ 被极其广泛地用于驱动多人物组合（例如 “👨” + ZWJ + “👩” + ZWJ + “👧” $\to$ 家庭合影图元）；
* **零宽不连字（Zero Width Non-Joiner, ZWNJ, $\text{U+200C}$）**：  
  在逻辑字符之间强行斩断连写趋势，迫使相邻字符各自保持独立孤立的字形外观。在波斯语中，许多复合前缀与词根之间在语法上必须保持微小的视觉断绝，ZWNJ 构成了波斯语正确拼写不可或缺的基石。

## 大小写属性与复杂折叠映射（Case Mappings）

在拉丁、希腊、西里尔与亚美尼亚等具有双形态（bicameral）的文字体系中，大小写转换绝非简单的“将 ASCII 码减去 32”那般肤浅。在国际化语境下，大小写映射展现出了极其深邃的语言学复杂性：

### 1. 简单大小写映射（Simple Case Mapping）
一个字符无条件地映射到另一个单一字符（如 ‘a’ $\to$ ‘A’）。

### 2. 长度可变的特殊大小写映射（Special Casing）
在某些语言中，一个单个小写字符在转换为大写时，会暴增为两个甚至多个字符！
* **德语德文字母 “ß”（Eszett / 尖 s）**：  
  在传统德语大写规则中，不存在独立的大写 ß。当单词 “*Straße*”（街道）整体转换为大写时，其小写字母 “ß” 必须展开映射为双字母序列 **“SS”**（变为 “*STRASSE*”）！单字符映射在此彻底失效；
* **希腊字母终形小写 $\text{U+03C2}$（Final Sigma, $\varsigma$）**：  
  在希腊语中，大写字母 ‘$\Sigma$’ 对应两种不同的小写形式：若位于单词末尾，转换为终形 ‘$\varsigma$’；若位于词首或词中，则转换为正形 ‘$\sigma$’。转换算法必须在运行时扫描上下文环境；
* **土耳其语与阿塞拜疆语的“点之战争”（The Turkish I Problem）**：  
  在土耳其语中，存在两组完全独立的字母：
  * 带点小写字母 ‘i’ 对应**带点大写字母 ‘İ’（$\text{U+0130}$）**；
  * 不带点小写字母 ‘ı’（$\text{U+0131}$）对应**不带点大写字母 ‘I’**。  
  如果直接运行西方标准的 ASCII 大小写算法，将小写 ‘i’ 转为大写 ‘I’，在土耳其语中将彻底改变词义，甚至引发严重的司法与宗教文献篡改事故！因此，Unicode 大小写引擎必须显式接收当前系统的**区域语言环境标签（Locale）**以执行有条件的语境判定。

### 3. 大小写折叠（Case Folding）

在进行全文搜索、SQL 数据库查询或标识符比对时，我们希望 “Straße” 与 “strasse” 能够无障碍匹配。Unicode 设计了专门的**大小写折叠算法（Case Folding）**：它不属于视觉呈现规范，而是将所有大小写变体归一化映射为内部统一的中立键值流（如将 ‘ß’ 与 ‘SS’ 全部折叠为 ‘ss’），为跨国界文本搜索奠定了基石。

## 阿拉伯文连写成形属性（Arabic Joining Properties）

阿拉伯字母是典型的草书连续书写系统。在数据流中顺序输入的同一个逻辑字符，根据其前后是否接续其他字母，必须动态呈现为四种字形位置形态之一：
$$\text{孤立形（Isolated）} \quad \text{词首形（Initial）} \quad \text{词中形（Medial）} \quad \text{词尾形（Final）}$$

为了让渲染引擎能够自动完成这一复杂的文本整形（Text Shaping），Unicode 为每个阿拉伯与叙利亚字符定义了 `Joining_Type` 枚举属性：

| 连写属性类别 | 代号 | 核心连写行为与语法规则 |
| :--- | :---: | :--- |
| **右连写（Right_Joining）** | **`R`** | 仅向右侧（前驱字母）伸出连线，**绝不与左侧（后随字母）相连**。例如字母 ALEF（ا）、DAL（د）、REH（ر）、WAW（و）。后随字母被迫转为孤立形或词首形。 |
| **左连写（Left_Joining）** | **`L`** | 仅向左侧伸出连线（罕见，主要存在于特定古文字中）。 |
| **双向连写（Dual_Joining）** | **`D`** | 既可与右侧相连，亦可与左侧相连。这是绝大多数阿拉伯常规字母的标准属性（如 BEH（ب）、TEH（ت）、SEEN（س））。 |
| **无连写（Non_Joining）** | **`U`** | 完全不参与任何连写，保持孤立形态（如阿拉伯数字、标点符号）。 |
| **引发连写（Join_Causing）** | **`C`** | 本身不呈现为字母，但其存在会强行诱发两侧字符呈现连结状态（如 ZWJ）。 |
| **通透连写（Transparent）** | **`T`** | 在连写分析中“隐形透明”：连写算法直接穿透该字符，将其前后的两个字母视为物理相邻（如阿拉伯文发音辅音变音符 Tashkil）。 |

## 解读 Unicode 官方数据表（UnicodeData.txt）

所有上述庞大的基础属性，全部被凝结记录在 Unicode 字符数据库（UCD, Unicode Character Database）的核心旗舰文件——**`UnicodeData.txt`** 之中。

该文件是一份纯文本文件，每一行对应一个字符，字段之间严格以分号（`;`）作为分隔符，总计包含 **14 个标准化核心数据字段**：

$$\text{Field 0} ; \text{Field 1} ; \text{Field 2} ; \dots ; \text{Field 14}$$

以拉丁大写字母 ‘Å’（带上圆圈的 A，码位 $\text{U+00C5}$）在 `UnicodeData.txt` 中的真实原始记录行为例：
```text
00C5;LATIN CAPITAL LETTER A WITH RING ABOVE;Lu;0;L;0041 030A;;;;N;LATIN CAPITAL LETTER A RING;;;00E5;
```

让我们剖析其 14 个字段的深层含义：
1. **`00C5`（Field 0, Code Point）**：码位的十六进制数值；
2. **`LATIN CAPITAL LETTER A WITH RING ABOVE`（Field 1, Name）**：字符唯一规范名称；
3. **`Lu`（Field 2, General Category）**：通用类别代码（Letter, uppercase / 大写字母）；
4. **`0`（Field 3, Canonical Combining Class, ccc）**：规范组合变音类别（0 代表独立基础字符，非 0 代表具有特定依附层级的组合标记）；
5. **`L`（Field 4, Bidi Class）**：双向排版算法类别（`L` 代表强从左至右 Left-to-Right 字符）；
6. **`0041 030A`（Field 5, Decomposition Type & Mapping）**：规范等价分解映射式！表明该字符在规范等价层面上可以分解为基础字符 ‘A’（$\text{U+0041}$）与组合上圆圈（$\text{U+030A}$）；
7. **空（Field 6, Decimal Digit Value）**：若为十进制数字则记录其 $0 \sim 9$ 的整数值；此处非数字，留空；
8. **空（Field 7, Digit Value）**：数字值，留空；
9. **空（Field 8, Numeric Value）**：通用数值，留空；
10. **`N`（Field 9, Bidi Mirrored）**：在双向排版中是否需要图形镜像翻转（`N` 为否，如括号类符号该值为 `Y`）；
11. **`LATIN CAPITAL LETTER A RING`（Field 10, Unicode 1.0 Name）**：Unicode 1.0 时代的历史旧名称；
12. **空（Field 11, 10646 Comment Field）**：ISO 注释字段；
13. **空（Field 12, Uppercase Mapping）**：该字符对应的大写码位（自身已是大写，留空）；
14. **`00E5`（Field 13, Lowercase Mapping）**：该字符对应的小写码位（映射为小写 $\text{U+00E5}$ ‘å’）；
15. **空（Field 14, Titlecase Mapping）**：词首大写码位（此处与大写一致，留空）。

通过这套逻辑严密、数理完备的属性架构，Unicode 将每一个散落在人类文明历史长河中的文字符号，转化为了具备高度自省与自解析能力的现代数字实体。

然而，在实际计算处理中，当一个字符既可以写作单一预组装符号（如 “Å”），又可以写作分离的组合序列（如 “A” + “̊”）时，计算机在字符串比对中应当如何消除歧义？当英文与阿拉伯文在同一段落内交织混排时，光标与断行又应当遵循何种物理轨迹？
