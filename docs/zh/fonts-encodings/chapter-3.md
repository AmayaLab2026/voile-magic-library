# 第三章 · Unicode 字符的属性体系
### Chapter 3: Properties of Unicode characters

**著者：雅尼斯·哈拉兰博斯（Yannis Haralambous, Ph.D.）**  
*选自《Fonts & Encodings》第 95–126 页*  
*译者：ヴワル魔法図書館（Voile Magic Library）文献翻译工房*

---

我们在本章中所关注的，是 Unicode 为每一个字符所提供的全部属性信息（Information）。依照我们此前所确立的严格定义，**字符**（Character）是对某一特定字形类（Class of Glyphs）的抽象描述。而在该类所有的具体字形中，会选出一个代表性字形（Representative Glyph）展示在 Unicode 标准的代码图表之中——无论是在其厚重的纸质实体卷册 [335] 中，还是在互联网上发布的官方 PDF 文档 [334] 内。

Unicode 将一个字符的**身份**（Identity）定义为其抽象描述（Description）与代表性字形的结合。另一方面，一个字符的**语义**（Semantics）则是由其字符身份连同其**规范属性**（Normative Properties）所共同赋予的。

这便引出了我们本章的核心论题：**字符属性**（Character Properties）。这些属性是历经漫长岁月沉淀、为每一个字符系统收集建立的数据资产，其目的在于帮助我们更加精准高效地运用 Unicode。例如，字符最基础的规范属性之一便是其**通用分类**（General Category）。在诸多的可能分类中，包含着诸如“标点符号”（Punctuation）这一范畴。如此一来，软件开发者便能轻而易举地获知某个书写系统中的哪些字符属于标点符号——从而在进行文本排序（Sorting）时自动忽略这些符号——而完全无需预先掌握该书写系统本身的复杂语言学细节。

另一个属性（尽管在此范例中它属于非强制的描述性属性，因而存在更多的语境模糊性）则是**大写/小写对应关系**（Uppercase/Lowercase Correspondence）。Unicode 为此提供了完备的对应表，软件可以直接调用这些规则将字符串从一种大小写形式转换为另一种形式（前提是该书写系统确实存在大小写概念）。

当然，无论何种文本操作（无论是文本排序还是大小写转换），都绝不可能做到百分之百的纯机械自动化。正如所有自然语言处理（NLP）领域的客观规律一样，由于语言本身及其语法结构所固有的歧义性，处理过程中永远伴随着一定程度的不确定性。然而，字符属性依然使得文本处理的绝大部分工序得以实现高度自动化；开发者所需要做的，只是在界面与机制上赋予用户纠正那些因规则普适化套用而偶然产生的极少数偏差的权利。

那么，究竟存在哪些字符属性？我们又该在何处查阅并获取它们？本章接下来的全部篇幅便将完整解答这两个关键问题。

## 基础属性（Basic Properties）

### 字符名称（Name）

字符的官方名称（Name），正是我们此前所称的“字符描述”（Description）。在 Unicode 编码空间内，依照字符编码位置排列的官方英文名称列表公布于以下核心数据文件之中：

```text
http://www.unicode.org/Public/UNIDATA/UnicodeData.txt
```

该文件以极其紧凑的计算机友好格式容纳了浩瀚的字符数据：每一行代表一个字符，由分号（Semicolon `;`）分隔为整整十五个文本字段（Fields）。以下摘录该文件开篇的若干典型数据行：

```text
0020;SPACE;Zs;0;WS;;;;;N;;;;;
0021;EXCLAMATION MARK;Po;0;ON;;;;;N;;;;;
0022;QUOTATION MARK;Po;0;ON;;;;;N;;;;;
0023;NUMBER SIGN;Po;0;ET;;;;;N;;;;;
0024;DOLLAR SIGN;Sc;0;ET;;;;;N;;;;;
```

在这套数据结构中，前两个字段分别代表字符的编码位置（Position，亦称**码点** `Code Point`）与字符名称（Name）。在计算机索引中，这两个字段编号分别为第 0 号与第 1 号字段（遵循从 0 开始计数的惯例）。关于后续字段的详细语义，我们将在后文中逐一剖析。

字符名称的设立绝非仅供人类肉眼阅读查阅；现代编程语言（Programming Languages）同样能够直接理解并解析它们。例如在 Perl 语言中，若要引用切罗基文（Cherokee）字母 ‘Ꭰ’，程序员可以直接编写 `\N{CHEROKEE LETTER A}`，这与直接使用其十六进制码点表达 `\x{13A0}` 在语义上是完全等价的。

### 区块与书写系统（Block and Script）

这些属性规定了全体字符在编码空间中的宏观宏构分布，主要依据字符所归属的书写系统（Script）或它们在功能上的同质性来进行区块（Block）切分。由此，我们不仅拥有亚美尼亚文字符区块（Armenian），亦拥有象形图形符号区块（Dingbats）、专用控制代码区块（Specials）等等。

所有官方分配的连续区块范围完整列载于核心文件 `Blocks.txt` 之中。以下为该文件的局部摘录：

```text
0000..007F; Basic Latin
0080..00FF; Latin-1 Supplement
0100..017F; Latin Extended-A
0180..024F; Latin Extended-B
...
10450..1047F; Shavian
10480..104AF; Osmanya
```

在支持高级正则表达式（Regular Expressions）的编程环境中，区块属性赋予了开发者强大的文本匹配能力。例如，正则表达式 `/\p{InShavian}/` 能够精准匹配落在萧伯纳字母（Shavian）区块范围内的任意字符。

然而，我们必须在此厘清一个极为关键的概念分野：**区块属性**（Block Property）与**书写系统属性**（Script Property）有着本质的不同。一个字符所处物理区块的名称，并不必然代表它所归属的真实书写系统。例如，希腊字母 ‘͵’（希腊文下角点，U+0375 `GREEK LOWER NUMERAL SIGN`）物理上位于希腊字母与科普特文字块中，但它同时具有独特的标点或数字修饰属性；而拉丁目母在全角/半角形式块（Halfwidth and Fullwidth Forms）中亦有分布。若我们要根据字符实际所属的文字系统进行匹配，应当使用书写系统属性（如 Perl 5.8+ 中的 `\p{IsCherokee}` 或 `\p{Script=Greek}`），该属性记录于专门的 `Scripts.txt` 文件之中。

### 诞生版本与纪年（Age）

每一字符何时被正式接纳并编入 Unicode 国际标准，由**纪年属性**（Age Property）严格记录，具体记载于 `Age.txt` 数据库内。由于 Unicode 标准具有神圣不可侵犯的**前向兼容性承诺**（Forward Compatibility Guarantee）——即任何一旦被编码分配的字符永不删除、码点永不挪用——因此字符的生命周期只有“诞生”，而无“消亡”。

该属性记录了接纳该字符的首个标准版本号：`1.1`、`2.0`、`2.1`、`3.0`、`3.1`、`3.2`、`4.0`、`4.1`、`5.0` 等。当软件需要在异构系统之间交换文本、或需要向下兼容旧版 Unicode 处理引擎时，纪年属性便成为了判定目标系统是否具备该字符解析能力的基准判据。

### 通用分类（General Category）

在 `UnicodeData.txt` 的全部十五个字段中，第 2 号字段承载着至关重要的**通用分类**（General Category，简记为 `gc`）。这是一项极其重要的规范属性（Normative Property），它为每一个字符赋予了一个由两个英文字母构成的分类代码。

首字母代表该字符的**顶级分类**（Major Class）：
- `L`：字母（Letter）
- `M`：修饰标志 / 附加符号（Mark）
- `N`：数字（Number）
- `P`：标点符号（Punctuation）
- `S`：符号（Symbol）
- `Z`：分隔符（Separator）
- `C`：其他 / 控制（Other / Control）

次字母则指示该顶级范畴下的具体子分类。以下我们对各大子类别进行细致解析：

#### 字母（Letters）

- **`Lu`（大写字母，Uppercase Letter）**：如标准的拉丁大写字母 ‘A’、希腊大写字母 ‘$\Omega$’、西里尔大写字母 ‘$\Phi$’ 等。
- **`Ll`（小写字母，Lowercase Letter）**：如小写字母 ‘a’、‘$\omega$’、‘$\phi$’ 等。
- **`Lt`（词首大写 / 标题字母，Titlecase Letter）**：这是一个初见时常令非语言学专业学者感到困惑的独特类别。某些语言在书写复合二合字母（Digraphs）时，若该词处于句首或标题位置，传统习惯是仅将二合字母的前半部分大写，而保持后半部分为小写。
  最典型的例证见于克罗地亚语（使用拉丁字母）与塞尔维亚语（使用西里尔字母）的双向转写体系。例如，西里尔字母 ‘Џ’（发音类似 judge 中的 j）在克罗地亚拉丁字母中写作 ‘D’ 与 ‘ž’ 的组合。在 Unicode 中，为了确保与南斯拉夫国家标准编码的单字符一对一转换，该二合字母被赋予了独立的单字符码点：
  1. 全大写形式（`Lu`）：`U+01C4` ‘Ǆ’（`LATIN CAPITAL LETTER DZ WITH CARON`）
  2. 词首大写形式（`Lt`）：`U+01C5` ‘ǅ’（`LATIN CAPITAL LETTER D WITH SMALL LETTER Z WITH CARON`）
  3. 全小写形式（`Ll`）：`U+01C6` ‘ǆ’（`LATIN SMALL LETTER DZ WITH CARON`）
  类似的二合字符还包括 ‘Ǉ / ǈ / ǉ’（`LJ`）与 ‘Ǌ / ǋ / ǌ’（`NJ`）。此外，在多调希腊文（Polytonic Greek）中，带有下写字标（Iota Subscript）的大写字母若以旁写字标（Prosgegrammeni）排印在标题词首时（如 ‘$\Omega\iota$’ 融合成单字符），亦归入 `Lt` 分类。
- **`Lm`（修饰字母，Modifier Letter）**：独立占据水平进幅间距、但在语言学功能上用于修饰前驱或后继字母发音的字符，如上标音标字符、声调修饰字母（Tone Letters）等。
- **`Lo`（其他字母，Other Letter）**：涵盖所有在文字系统中不具备大小写二元区分（Casing distinction）特征的字母与表意文字。汉字（CJK Ideographs）、希伯来字母（如 Alef ‘א’）、阿拉伯字母、泰文字母等统统归入此类。

#### 附加符号（Diacritical Marks / Marks）

- **`Mn`（非进幅符号，Nonspacing Mark）**：在渲染时不产生独立的水平进幅宽度（Advance Width 均为 0），而是悬浮附着于基底字符（Base Character）之上、之下或内部的变音符号。例如拉丁文的锐音符（Acute Accent `U+0301`）、希伯来文的元音点（Niqqud）等。
- **`Mc`（进幅结合符号，Spacing Combining Mark）**：与基底字符结合成一个语音单元，但自身在排版上占据独立视觉宽度的附加标记。在印度系文字（Indic Scripts，如天城文、孟加拉文）的元音附标中极其普遍。
- **`Me`（包围结合符号，Enclosing Mark）**：在视觉上将基底字符完全圈入其内部的符号，如结合用圆圈（Combining Enclosing Circle `U+20DD`）或方框。

#### 数字（Numbers）

- **`Nd`（十进制数字，Decimal Digit Number）**：遵循标准十进制进位制、且完整具备 0 至 9 连续数字序列的书写字符。包括普通的 ASCII 数字 `0..9`，以及天城文数字 `०..९`、阿拉伯-印度数字等。
- **`Nl`（字母数字，Letter Number）**：由字母形态演变而来、或在功能上充当数字的特殊符号，如古罗马数字符号（Roman Numerals `Ⅰ, Ⅱ, Ⅲ...`）、爱琴海数字符号等。
- **`No`（其他数字，Other Number）**：不属于上述两类的各类散乱数字符号，如普通分数符（½、¼）、带圈数字（`①, ②`）、上标数字等。

#### 标点符号（Punctuation）

- **`Pc`（连接标点，Connector Punctuation）**：如用于连接两个词素的下划线 ‘_’（Underscore）。
- **`Pd`（破折号与连字符，Dash Punctuation）**：包括连接号（Hyphen ‘-’）、半字线（En Dash ‘–’）、全字线（Em Dash ‘—’）等。
- **`Ps`（成对标点开启端，Open / Start Punctuation）**：所有开括号，如左圆括号 ‘(’、左方括号 ‘[’、左花括号 ‘{’ 等。
- **`Pe`（成对标点闭合端，Close Punctuation）**：所有闭括号，如右圆括号 ‘)’、右方括号 ‘]’、右花括号 ‘}’ 等。
- **`Pi`（起始引号，Initial Quote Punctuation）**：如左双引号 ‘“’，在某些语言排版中亦指特定开引号。
- **`Pf`（终结引号，Final Quote Punctuation）**：如右双引号 ‘”’，或法文书名号的闭合端。
- **`Po`（其他标点，Other Punctuation）**：句号、逗号、感叹号、问号、分号、冒号等常规标点。

#### 符号（Symbols）

- **`Sm`（数学符号，Math Symbol）**：如加号 ‘+’、等号 ‘=’、小于号 ‘<’、积分号 ‘$\int$’ 等。
- **`Sc`（货币符号，Currency Symbol）**：如美元符 `$`、欧元符 `€`、英镑符 `£`、日元/人民币符 `¥` 等。
- **`Sk`（修饰符号，Modifier Symbol）**：独立占据空间、但表示某种修饰属性的符号，如单独成字的声音符（U+005E 脱字符 ‘^’、U+0060 重音符 ‘`’）。
- **`So`（其他符号，Other Symbol）**：各类杂项图案符号，如扑克牌花色、麻将牌面、国际象棋棋子、商标符 ‘™’、版权符 ‘©’ 等。

#### 分隔符（Separators）

- **`Zs`（空白分隔符，Space Separator）**：标准空格（ASCII Space）、不换行空格（NBSP）、细空格（Thin Space）、全角空格（Em Space）等。
- **`Zl`（行分隔符，Line Separator）**：专门用于无条件强制换行但不断段的代码 `U+2028`。
- **`Zp`（段落分隔符，Paragraph Separator）**：专门用于强制分段的代码 `U+2029`。

#### 其余特殊类别（The Remaining Categories）

- **`Cc`（控制字符，Control Character）**：继承自 ASCII 与 ISO 8859 系列的 C0 与 C1 控制字符集（`0x00..0x1F` 与 `0x7F..0x9F`），如换行（LF）、回车（CR）、制表符（TAB）。
- **`Cf`（格式控制字符，Format Character）**：对排版、双向文本流动或字形连笔产生隐式控制但本身完全透明无视觉印迹的代码。典型代表包括：零宽连字符（ZWJ, `U+200D`）、零宽不连字符（ZWNJ, `U+200C`）、从左至右标记（LRM, `U+200E`）、从右至左标记（RLM, `U+200F`）、字节顺序标记（BOM, `U+FEFF`），以及用于高阶数学公式排版的不可见操作符（Invisible Operators，如 `U+2061` 函数应用符、`U+2062` 不可见乘号、`U+2063` 不可见分隔符）。
- **`Cs`（代理对码点，Surrogate）**：保留用于 UTF-16 编码机制的特殊码位（`0xD800..0xDFFF`）。它们在真实世界中永远不代表独立字符。
- **`Co`（专用私用区字符，Private Use）**：供各组织、字体设计师或软件厂商私下约定分配的保留区域（BMP 中的 `0xE000..0xF8FF`，以及平面 15 与 16 全域）。
- **`Cn`（未分配码点，Unassigned）**：尚未被 Unicode 标准分配任何字符的纯粹空置码位。

## 其他通用属性（Other General Properties）

除了 `UnicodeData.txt` 主文件所包含的基础属性外，Unicode 联合会（Unicode Consortium）还在附加属性列表文件 `PropList.txt` 以及一系列专门派生文件（Derived Property Files）中维护了极其庞大的细分属性体系。

### 空白符（Spaces / White_Space）
属性 `White_Space` 涵盖了所有视觉呈现为空白或导致光标发生进幅位移的字符。除了分类为 `Zs` 的各类空格外，该集合还纳入了控制字符中的水平制表符（HT, `0x0009`）、换行符（LF, `0x000A`）、垂直制表符（VT, `0x000B`）、换页符（FF, `0x000C`）、回车符（CR, `0x000D`）以及行/段分隔符。

### 字母性（Alphabetic Characters）
属性 `Alphabetic` 包含所有属于 `L` 类别的字符，以及具有字母发音衍生功能的若干特殊附加符号（`Mn`）。这对于编程语言词法分析器（Lexer）判定标识符的合法拼写范围至关重要。

### 非字符（Noncharacters）
在 Unicode 浩瀚的 1,114,112 个码位中，有整整 66 个码位被永久性地宣告为**非字符**（Noncharacters）。它们绝不能用于在开放系统间交换文本数据，而仅供系统内部作为哨兵值（Sentinel Values）或魔数（Magic Numbers）使用。它们包括：
1. 每一个平面的最后两个码点：`0xFFFE` 与 `0xFFFF`，`0x1FFFE` 与 `0x1FFFF`，直至 `0x10FFFE` 与 `0x10FFFF`（共 34 个）；
2. 基本多语言平面（BMP）中的一段连续保留区：`0xFDD0..0xFDEF`（共 32 个）。

### 默认可忽略字符（Default_Ignorable_Code_Point）
这一属性标记了一批在旧版软件或未实现对应渲染特效的排版引擎中，应当被安全“静默吞没”而不引发方框乱码（Tofu）的特殊格式字符。例如软连字符（Soft Hyphen `0x00AD`）、零宽字符、以及未分配的格式控制码。

### 废弃字符（Deprecated Characters）
尽管 Unicode 恪守永不删除字符的铁律，但对于早期标准因认知局限或历史失误而错误收录的冗余字符，联合会会将其打上**已废弃**（Deprecated）标记，强烈建议现代系统停止使用，并以正规的字符组合序列予以取代。例如过时的交替格式字符群（`0x206A..0x206F`）。

### 逻辑顺序例外（Logical-Order Exceptions）
Unicode 文本的绝对核心准则是**逻辑存储顺序**（Logical Order）——即字符必须严格按照人们发音或阅读的时间先后顺序存储于内存中。然而，全球数千种书写系统中存在着极其罕见的例外：泰文（Thai）与老挝文（Lao）的某些元音符号在视觉排印时，必须绘制在声母辅音字母的左侧（物理前置）。
由于当地传统打字机与遗留编码早已习惯先键入左侧元音、再键入辅音，Unicode 为维持与泰国国家标准 TIS 620 的完全兼容，被迫对这五个泰文字母（`0x0E40..0x0E44`）与老挝文字母做出了妥协。它们被赋予了 `Logical_Order_Exception` 属性，排版渲染引擎在执行双向重排或注音解析时，必须对此类字符执行反向预处理。

### 软点字母（Soft-Dotted Letters）
在拉丁字母 ‘i’ 与 ‘j’ 的小写形态中，字头上天生具有一颗小圆点（Tittle / Dot）。当在这两个字母上方叠加其他变音符（如重音符、扬抑符或长音符）时，传统排版习惯通常要求隐去其原本的小圆点（即变为无点基底），以避免双重符号发生难看的纵向重叠与墨团挤压。然而，在立陶宛语（Lithuanian）等特定语言的正字法中，重音符必须叠加在原有圆点之上保留显现！
拥有 `Soft_Dotted` 属性的字符（包括加罗林长 s ‘ſ’ 在某些字体中的变体、以及西里尔小写字母 ‘і’）提示着智能排版与字体设计引擎：其点状结构具有特殊的形态消失或共存逻辑。

### 数学、引号与标点专有属性
- **`Math`**：收纳全体数学符号、数学字母数字变体（如黑板粗体 $\mathbb{R}$、花体 $\mathcal{F}$ 等）。
- **`Quotation_Mark`**：统一索引世界各种书写系统所使用的全部形制配对或单体引号。
- **`Dash`** 与 **`Hyphen`**：对各类连字符、减号、长破折号进行精确的功能拓扑划分。
- **`Terminal_Punctuation`**：标记句末终结标点（如句号、叹号、阿拉伯文分句符），用于段落拆分与分句算法。
- **`Diacritic`**：标记所有具有变音功能的附加或独立符号。
- **`Extender`**：标记那些在视觉上将前驱字符在水平方向予以几何“拉长”的特殊文字成分，如阿拉伯文的延伸字线（Kashida / Tatweel `U+0640`）、平假名与片假名的长音符（`U+30FC`）。
- **`Join_Control`**：仅由两个最具魔力的格式字符独占：零宽连字符（ZWJ `U+200D`）与零宽不连字符（ZWNJ `U+200C`）。

### Unicode 1.0 旧名称与 ISO 注释
在 `UnicodeData.txt` 的第 10 与 11 号字段中，保留了历史沿革数据：
- **第 10 字段**：Unicode 1.0 版最初赋予该字符的旧名称。这在早期标准因更名而产生历史文档断层时提供了可贵的追溯依据。
- **第 11 字段**：国际标准化组织 ISO/IEC 10646 标准对该字符所附带的正式官方注释文本。

## 大小写相关属性（Properties That Pertain to Case）

对于拥有大小写双轨制的字母文字（如拉丁文、希腊文、西里尔文、亚美尼亚文以及格鲁吉亚语的历史变体），大小写的精确转换与等价判定构成了计算语言学中最古老却又暗藏无数暗礁的课题。

### 简单大小写映射（Simple Case Mappings）
记录于 `UnicodeData.txt` 的最后三个字段：
- 第 12 字段：简单大写映射（Simple Uppercase Mapping）
- 第 13 字段：简单小写映射（Simple Lowercase Mapping）
- 第 14 字段：简单词首大写映射（Simple Titlecase Mapping）

所谓“简单”，意味着其映射关系被严格限制为**单一码点到单一码点**（1:1）的对称替换。例如小写字母 ‘a’（`U+0061`）的第 12 字段填入大写 ‘A’（`U+0041`）。

### 特殊大小写映射（Special Case Mappings）
然而，自然语言的真实演化绝非单码点映射所能完全涵盖。为此，Unicode 创立了专门的高阶数据库文件 `SpecialCasing.txt`。该文件解决了三大类极端复杂的语言学难题：

1. **一对多扩展映射（1:Many Mappings）**：
   德语小写锐 S 字母 ‘ß’（Eszett, `U+00DF`）在传统德语正字法中完全不存在原生大写形态（直到 2017 年官方才有限度采纳大写 ẞ `U+1E9E`）。在传统全大写排版中，‘ß’ 必须无条件展开为两个独立的英文字母大写：“SS”。此外，诸多带有复合变音符的多调希腊字母在转为全大写时，其下写字标必须被拆卸解构并展开为普通大写 Iota（如 ‘ᾂ’ 展开为三个大写字符）。
2. **上下文敏感映射（Context-Dependent Mappings）**：
   在希腊文正字法中，大写字母 Sigma ‘$\Sigma$’ 转为小写时具有高度的语境依存性：若该字母处于单词的中间位置，其小写形态为普通的 ‘$\sigma$’；然而，若该字母恰好处于**单词的终末末尾**，它必须自动蜕变为专有的词尾 Sigma ‘$\varsigma$’（`U+03C2`）。任何合格的现代文本引擎都必须依据词边界上下文状态机来实现这一精准转换。
3. **语言区域敏感映射（Locale-Dependent Mappings）**：
   最为经典的案例莫过于土耳其语（Turkish）与阿塞拜疆语（Azeri）的正字法悖论。在英语与通用拉丁语境中：
   - ‘i’ 的大写是 ‘I’；‘I’ 的小写是 ‘i’。
   然而在土耳其语中，存在着两对彼此完全独立的平行的元音字母：
   - **带点组**：小写 ‘i’（带点）对应大写 ‘İ’（带点大写，`U+0130`）；
   - **无点组**：小写 ‘ı’（无点小写，`U+0131`）对应大写 ‘I’（无点大写）。
   如果一个通用的英文大小写算法在土耳其语环境下粗暴地将小写 ‘i’ 转换为普通的无点大写 ‘I’，就会彻底改变单词的词义甚至造成严重误解！`SpecialCasing.txt` 通过引入 ISO 639 语言标签（如 `tr`、`az`）精确隔离了此类区域特化规则。

### 大小写折叠（Case Folding）
当计算机需要判断用户输入的搜索词或数据库查询是否与目标字符串匹配时，我们往往期望实现“忽略大小写”（Case-Insensitive Match）。

简单的做法是将两者统统转为大写或统统转为小写后再逐字节比对。然而，由于德语 ‘ß’ 与 “SS” 的单双字符不对称、以及希腊文词首词中 ‘$\sigma$’ 与词尾 ‘$\varsigma$’ 的异构问题，单向转换极易发生假阴性失配。

Unicode 为此专门设立了独立的规范文件 `CaseFolding.txt`，制定了一套中立的**大小写折叠**（Case Folding）算法。该算法为每个字符确立了折叠状态（Status）：
- `C`（Common）：常规单字符折叠映射；
- `F`（Full）：全字符集深度折叠（如将 ‘ß’ 强制折叠为 “ss”）；
- `S`（Simple）：限制在单字符范围内的保守折叠；
- `T`（Turkic）：土耳其语系专属特化折叠。

两串原本大小写各异、写法不同的文本，只需分别经过完整大小写折叠算法的标准化规范清洗，即可直接进行二进制等价性比对。

## 渲染与书写属性（Rendering Properties）

### 阿拉伯文与叙利亚文的连笔塑形

在世界文字体系中，以阿拉伯文（Arabic）与叙利亚文（Syriac）为代表的闪米特语系文字展现出一种高度复杂的艺术化特质：**全手写草书连笔体**（Cursive Script）。

在这类文字中，字母并不是像拉丁字母那样彼此孤立排列，而是如同流水行云般依靠笔画的基线相互连接。因此，一个字母的实际视觉呈现形状，完全取决于它在单词中所处的相对拓扑位置：
1. **孤立位（Isolated Form）**：当字母单独出现或前后均不发生连笔时；
2. **词首位（Initial Form）**：当字母位于连笔词组的开端、仅向左侧（书写流动方向）引出连接线时；
3. **词中位（Medial Form）**：当字母两端均与邻近字母紧密相连时；
4. **词尾位（Final Form）**：当字母位于词组末端、仅承接右侧连接线时。

更具挑战性的是，阿拉伯字母表并非所有字母都能够“四面逢源”。事实上，阿拉伯字母被严格划分为两大阵营：
- **双向连接字母**：具备完整的四种形态位格（词首、词中、词尾、孤立）；
- **单向（右侧）连接字母**：只能与右侧的先行字母相连（呈现词尾或孤立形态），却严禁向左侧引出连线（如字母 Alif ‘ا’、Dal ‘د’、Ra ‘ر’ 等）。一旦遇到此类字母，连笔链条即告中断，其后继字母被迫以词首或孤立形态重新起笔。

为了让排版引擎与 OpenType 字体能够精准计算字形替换，Unicode 在核心属性中确立了**连接类型**（Joining Type，记录于 `ArabicShaping.txt`）：

| 连接类型代码 | 英文全称 | 连笔行为特征与规则定义 |
| :--- | :--- | :--- |
| **`D`** | Dual-joining（双向连接） | 能够自由与左右两侧的字符相互连接，完整具备四种上下文形态。 |
| **`R`** | Right-joining（右向连接） | 仅能与右侧（先行）字符连接；绝不向左侧引出连笔线。仅有词尾与孤立两种形态。 |
| **`L`** | Left-joining（左向连接） | 仅能与左侧（后继）字符连接。极度罕见，主要存在于特定叙利亚文变体中。 |
| **`U`** | Non-joining（不连接） | 完全独立孤立，绝不与任何方向的相邻字符发生物理连笔。 |
| **`C`** | Join-causing（引发连接） | 强制诱发连笔效果，其代表正是零宽连字符（ZWJ `U+200D`）与延伸字线 Kashida。 |
| **`T`** | Transparent（透明无阻） | 对连笔逻辑完全透明的字符（如各类发音短元音变音符）。排版引擎在扫描连笔链条时视其如空气，直接跳过并贯通其前后的辅音连笔。 |

### 字素簇管理（Managing Grapheme Clusters）

在计算机底层，一个“字符”（Character）只是编码表上的一个数字码点；然而在普通读者的直观视觉与心理认知中，一个“字”（Grapheme）往往是由一个基底字母及其周遭附着的一系列变音记号共同构成的不可分割的有机整体。

例如，越南语中的字母 ‘$\tilde{\hat{\text{E}}}$’（带有扬抑符与硬颚波浪符的小写 e），在内存中可能由基底字符 ‘E’ 紧随两个独立的组合变音码点（`U+0302` 与 `U+0303`）拼合而成。当用户在文本编辑器中按下键盘退格键（Backspace）、或使用光标左右箭头穿行文本、亦或软件执行换行与单词加亮时，软件绝不能野蛮地将光标停驻在字母 ‘E’ 与其变音符之间，更不能只删掉半个变音符而留下一堆破碎的乱码。

为了彻底规范文本交互中的基本视觉单元，Unicode 专门发布了 **第 29 号技术报告**（Unicode Standard Annex #29, UAX #29），确立了**用户感知字符**——即**字素簇**（Grapheme Cluster）的形式化边界算法。

标准严格区分了：
1. **传统字素簇**（Legacy Grapheme Cluster）
2. **扩展字素簇**（Extended Grapheme Cluster）

该规范依靠一组精密的布尔逻辑与字符边界属性（如 `Grapheme_Cluster_Break` 包含的 `CR`、`LF`、`Control`、`Prepend`、`Extend`、`SpacingMark` 等），构筑起现代文本编辑光标与排版折行绝不可逾越的护城河。

## 数值属性（Numeric Properties）

在 `UnicodeData.txt` 的主数据列中，整整分配了三个并行的字段（第 6、7、8 号字段）用于记录字符的数学数值（Numeric Properties）：
- **第 6 字段（Decimal Digit Value）**：十进制数码数值。若字符属于标准进位制十进制数字（分类 `Nd`），则填入其 0 至 9 的整数值；否则留空。
- **第 7 字段（Digit Value）**：数码数值。包括某些虽然代表数码但具有特殊排印修饰的符号（如带圈数字 `③` 的该字段值为 3）。
- **第 8 字段（Numeric Value）**：通用广义数值。能够接纳一切表示数量概念的字符，包括常规分数（如 `½` 记作 `1/2`）、罗马数字（如 `Ⅻ` 记作 `12`）、甚至汉字大写数字（如 ‘億’ 记作 `100000000`）。

## 标识符与语法规范（Identifiers and Pattern Syntax）

任何一门现代计算机编程语言（无论是 Python、Java、C# 还是 Rust）在编译源代码时，词法分析器面对的第一个严峻挑战便是：**源代码中的变量名、函数名与类名允许包含哪些 Unicode 字符？**

若缺乏统一的标准约束，开发者可能会随意使用肉眼无法辨识的不可见格式字符作为变量名，甚至利用希腊字母 ‘$\omicron$’（Omicron）与拉丁字母 ‘o’ 的视觉同形（Homoglyph）制造极其危险的安全木马漏洞。

为此，Unicode 颁布了权威的 **第 31 号技术报告**（UAX #31: Identifier and Pattern Syntax）。该规范将字符空间划分为四大基础属性：
- **`ID_Start`**：允许作为合法程序标识符**首字符**的集合（涵盖所有大写字母、小写字母、词首大写字母、汉字等，但坚决排除数字与连接标点）；
- **`ID_Continue`**：允许作为标识符**后续字符**的集合（在 `ID_Start` 基础上，纳入十进制数字、下划线及非进幅修饰标记）；
- **`Pattern_Syntax`**：专门为编程语言语法关键字、运算符与分隔语法保留的不可变字符集；
- **`Pattern_White_Space`**：被明确界定为源代码合法语法留白的空白字符集。

- **第二列**：该字符的代表性字形（Representative Glyph）；
- **第三列**：字符的终身法定名称（Character Name）以及丰富详尽的修饰细节。

字符名称一律采用大写英文排印：例如 `LATIN CAPITAL LETTER A WITH MACRON`（带长音符的拉丁大写字母 A）。**这一名称一旦被正式定稿颁布，即享有永恒不朽的绝对不可变更性**（Immutable for all of eternity）。哪怕数十年后人们发现当初的命名中存在拼写错误或地理历史学误判，这些错误也将作为标准的组成部分被永久保留在编码表中，与人类文明的计算机系统共存始终。

然而，为了弥补名称不可修改所带来的局限，Unicode 联合会保留了对字符条目追加**注释**（Annotations）与**说明**的权力：
1. **导引圆点注释（`•`）**：以黑色实心圆点开头的条目，属于无强制约束力的**信息性说明**（Informative Note），旨在辅助排版工匠与软件人员正确应用该字符。在图版中我们可以看到极其丰富的文献考据：例如注明 ‘ģ’ 是拉脱维亚语字母、‘ć’ 是波兰语与克罗地亚语字母、带撇号的 ‘ď’ 是捷克语排版中“带抑扬符的 d”（d with háček）的首选视觉形态、以及警告排版人员绝不可将克罗地亚语的 ‘Đ’ 与美洲原住民文献中的 ‘Ð’ 相互混淆等等。
2. **等号别名（`=`）**：代表字符的非正式辅助别名（Alternative Name）。例如在后续页面中，法文连字 ‘œ’ 拥有如下珍贵别名：

```text
œ
LATIN SMALL LIGATURE OE
= ethel (from Old English eðel)
• French, IPA, Old Icelandic, Old English, ...
→ 00E6 æ  latin small letter ae
→ 0276 œ  latin letter small capital oe
```

由此我们惊奇地获知：‘œ’ 连字不仅效力于法兰西语言，而且在古英语（Old English）中曾拥有一个极为优雅的名字——“eðel”，并且在古冰岛语（Old Icelandic）中亦广为流传。

### 交叉引用与不等式警告（`→`）
凡是以箭头 `→` 开头的行，要么是严厉的**显式不等式**（Explicit Inequalities），要么指示着深厚的**语言学亲缘关系**（Linguistic Relationships）。

例如，在字符 `0x0110`（`LATIN CAPITAL LETTER D WITH STROKE`，带横杠的拉丁大写字母 D）下方，我们可以查阅到如下指引：
- `→ 00D0 Ð  latin capital letter edh`（显式不等式：严正警告开发者绝不可与冰岛语的 Eth 字母混淆！）
- `→ 0111 đ  latin small letter d with stroke`（交叉引用：直接链接至其对应的小写字母，即表格中的下一项）
- `→ 0189 Đ  latin capital letter african d`（显式不等式：警告不可与西非埃维语 Ewe 所使用的非洲大写 D 混淆！）

而在其小写条目 `0x0111` 下方，赫然列有：
- `→ 0452 ђ  cyrillic small letter dje`（语言学亲缘关系：告知该克罗地亚字母在塞尔维亚西里尔文中的完全等价对应物正是字母 ‘ђ’，为两套字母表之间的精密音译转换提供了官方锚点）。

### 规范等价分解（`≡`）与兼容等价分解（`≈`）

当数据行以恒等号 **`≡`** 开头时，宣告该字符可以被无损解构还原为其他基础字符的组合序列——这便是**规范分解**（Canonical Decomposition）。根据定义，规范分解具有绝对的数学唯一性，并且必然由一个基底字符与一个或两个结合变音符拼接而成。例如：

`Ā`（`0x0100`）的规范分解为基底字母 `A`（`0x0041`）紧随结合长音符（`0x0304`）：
```text
Ā ≡ 0041 A + 0304 [combining macron]
```

在排版渲染与信息检索中，预组合单字符 ‘Ā’ 与拆分组合序列 “A + ̄” 被视为同一存在的两种等价表象。

另一方面，当数据行以约等号 **`≈`** 开头时，则揭示了另一种深刻的排版妥协——**兼容分解**（Compatibility Decomposition）。
兼容分解代表着当软件环境或字体技术受限、无法原生驾驭该特定字符时所能采取的次优降级方案。

典型例证见于南非荷兰裔白人所使用的阿非利卡语（Afrikaans）中的特殊冠词复合字母 ‘ʼn’（`0x0149` `LATIN SMALL LETTER N PRECEDED BY APOSTROPHE`）。该字符在官方规范中的完整定义如下：

```text
0149
ʼn
LATIN SMALL LETTER N PRECEDED BY APOSTROPHE
= LATIN SMALL LETTER APOSTROPHE N
• Afrikaans
• this is not actually a single letter
≈ 02BC ʼ  006E n
```

其兼容分解明确指示：在视觉上，它可以降级模拟为一个修饰字母撇号（`U+02BC`）外加一个小写字母 ‘n’。
然而我们必须牢记：**兼容分解永远伴随着语义信息的不可逆流失**。如果一位严谨的文献作者在其文档中显式键入了阿非利卡语专用的 ‘ʼn’，他必然怀有极其深刻的学术理由。但是，若面对一套技术处于“石器时代”的古董排版软件，让它用撇号加小写 n 来完成基本的检索与显示，总好过抛出一堆不可辨识的乱码方块——这正是工程严谨性（Rigor）与现实可用性（Efficiency）之间永恒的平衡艺术。

### 兼容格式化标签全景剖析（Formatting Tags）

既然谈到了视觉模拟，为何不在兼容分解中进一步赋予排版渲染引擎具体的样式提示？Unicode 为此量身打造了整整 **16 种格式化标签**（Formatting Tags）。这些标签大量涌现在各类符号与排版变体的兼容分解描述之中：

1. **`<font>`（字体样式模拟）**：
   通过精选特定历史字体来完美模拟该字符的视觉神韵。此标签在 Unicode 中被高频调用了不下 1,038 次！
   例如数学中表示复数实部的专有符号 ‘$\Re$’（`0x211C` `BLACK-LETTER CAPITAL R`），其官方兼容分解正是：
   ```text
   ≈ <font> 0052 R  latin capital letter r
   ```
   换言之，若软件缺乏该专有数学符号的独立矢量轮廓，只需调用一套正统的德意志黑体（Fraktur）字体并排印其中的英文字母 ‘R’，便能达到几可乱真的完美重现！至于应当选取何种古典黑体，研读本书第十一章必能给读者带来无尽的灵感。
2. **`<noBreak>`（不换行控制）**：
   指示该字符为其后继内容的绝对不换行版本。例如不换行连字符 ‘‑’（`0x2011` `NON-BREAKING HYPHEN`），其兼容分解为：
   ```text
   ≈ <noBreak> 2010 -  hyphen
   ```
   它向排版引擎施加了铁的纪律：此处严禁折行断句。
3. **`<initial>`、`<medial>`、`<final>`、`<isolated>`（上下文书写形态）**：
   专门用于阿拉伯文与叙利亚文演示形区块（Presentation Forms），分别明确绑定字符在词首、词中、词尾与孤立位的特定几何拓扑。
4. **`<circle>`（圈号修饰）**：
   指示该字符为加圈符号，如带圈字母 ‘Ⓡ’、带圈数字 ‘⑩’ 等。
5. **`<super>` 与 `<sub>`（上标与下标）**：
   指示文字应当以数学上标（如 ‘¹’、‘ᵃ’）或下标（如 ‘₁’、‘ₙ’）的几何比例进行缩小并垂直平移排印。
6. **`<vertical>`（纵排专有形态）**：
   指示该字符专供竖排文本流使用。例如竖排左括号 ‘（’（`0xFE35` `PRESENTATION FORM FOR VERTICAL LEFT PARENTHESIS`），其兼容分解为：
   ```text
   ≈ <vertical> 0028 (
   ```
   以此在缺乏 OpenType 竖排特性的古老环境中锁死括号在直排下的旋转姿态。
7. **`<wide>` 与 `<narrow>`（全角与半角转换）**：
   对应东亚排版中全角 ASCII 字符（Fullwidth Forms，占据整整一个汉字方块宽度）以及半角片假名字符（Halfwidth Katakana，如 `｢ｺﾒ･｣`）。
8. **`<small>`（小型变体）**：
   专用于台湾 CNS 11643 兼容区块（`0xFE50..0xFE6B`）中所收录的小型标点符号。
9. **`<square>`（方块字组字）**：
   将若干西文字符或假名微缩拼接在一个标准汉字方块空间内，如公制单位组合字符 ‘㎦’（立方千米）：
   ```text
   ≈ <square> 006B k  006D m  00B3 3
   ```
10. **`<fraction>`（分数斜线组合）**：
    指示标准分数结构。例如分数四分之一 ‘¼’：
    ```text
    ≈ <fraction> 0031 1  2044 /  0034 4
    ```
    注意此处使用的是专有分数斜线（Fraction Slash `U+2044`），绝不可与普通的 ASCII 斜杠 ‘/’（`0x002F`）混为一谈。
11. **`<compat>`（通用未分类兼容）**：
    涵盖其余一切无法归入上述专门标签的杂项兼容形态，在 `UnicodeData.txt` 中用于明确划清兼容分解与规范分解的技术界河。
