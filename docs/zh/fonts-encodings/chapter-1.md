# 第一章 · 前 Unicode 时代的编码体系
### Chapter 1: Before Unicode
**著者：雅尼斯·哈拉兰布斯 博士（Yannis Haralambous, Ph.D.）**  
*选自《字体与编码》（Fonts & Encodings）原著第 27–52 页*

---

在计算机能够处理富文本排印与多语言文字之前，人类首先必须解决一个更加底层、更加原始的工程命题：**如何用离散的电脉冲与有限的二进制比特序列，来唯一指代文字书写系统中的每一个抽象符号？**

这一将文字符号映射为二进制数值的规则体系，便是**字符编码（character encoding）**。在 Unicode 统一天下之前，人类计算文明经历院长达数十年的碎片化“战国时代”。理解这一前 Unicode 时代的编码演进源流，不仅是一场扣人心弦的技术考古，更是深刻领会现代 Unicode 架构设计中诸多“妥协”、“兼容性区段”（compatibility blocks）与“规范等价”（canonical equivalence）历史成因的唯一钥匙。

---

## 物理媒介的史前时代：从穿孔纸带到 FIELDATA

计算机对字符的编码，直接脱胎于十九世纪电报通信与二十世纪初机械制表机的工业遗产。

在莫尔斯电码（Morse code）之后，法国工程师埃米尔·波多（Émile Baudot）于 1870 年代发明了 5 单位等长电报码（**波多码 / Baudot code**）。波多码仅用 5 个二进制比特便能表示 $2^5 = 32$ 种状态，通过引入“数字换档”（Figures Shift, FIGS）与“字母换档”（Letters Shift, LTRS）两条转义状态指令，使信道能够传输大写字母、数字与基本标点。波多码随后演变为国际通用的 ITA2 标准（International Telegraph Alphabet No. 2）。

进入电子计算机时代后，美国军方于 1950 年代末主导开发了 **FIELDATA 编码系统**。FIELDATA 旨在为美军战术数据系统（如陆军移动数字计算机 MOBIDIC）建立一套标准化的数据交换格式。该系统采用了 6 位（bit）或 7 位的字长结构：
* 6 位版本可编码 64 个字符，包含大写拉丁字母、数字以及军事战术缩写符号；
* 7 位版本引入了第 7 位作为**奇偶校验位（parity bit）**，用于在有损通信信道中侦测数据传输错误。

FIELDATA 首次在计算历史上确立了将字符编码划分为“控制指令码”（control characters）与“图形打印符号”（graphic characters）的先驱架构，这一两分法深刻影响了其后 ASCII 标准的制定。

## 7 位 ASCII 的确立与统治

1963 年，在美国标准化协会（ASA，即今日 ANSI 的前身）主持下，计算历史上最著名的编码规范正式诞生——**美国信息交换标准代码（American Standard Code for Information Interchange, 简称 ASCII）**。该标准在 1967 年与 1968 年经历了重大修订（ANSI X3.4-1968），最终锁定了现代计算机文明的基石。

ASCII 是一套纯粹的 **7 位编码（7-bit encoding）**，共定义了 $2^7 = 128$ 个码位（范围为十六进制 `0x00` 至 `0x7F`）：
1. **控制字符（Control Characters, `0x00`–`0x1F` 及 `0x7F`）**：  
   共 33 个码位，专门用于向终端硬件发出设备控制指令。这些指令深深根植于当年的电传打字机（Teletypewriter / TTY）机械构造：
   * `CR`（Carriage Return, 回车, `0x0D`）：通知打印头机械滑架归位至行首；
   * `LF`（Line Feed, 换行, `0x0A`）：驱动卷纸滚筒将纸张向上推进一行；
   * `BEL`（Bell, 响铃, `0x07`）：物理敲击终端上的铜铃，发出叮咚警报声；
   * `BS`（Backspace, 退格, `0x08`）：将打印头向左回退一格；
   * `ESC`（Escape, 转义, `0x1B`）：通知终端后续字节为特殊的控制序列；
   * `DEL`（Delete, 删除, `0x7F`）：由于在 7 单位穿孔纸带上打出所有的孔即代表二进制全 1（`1111111`），当打字员打错字符时，只需在原位置将剩余的孔全部补穿打透，即可将废弃字符覆写为不可打印的 `DEL` 码！
2. **图形打印字符（Graphic / Printable Characters, `0x20`–`0x7E`）**：  
   共 95 个码位，包含空格（`0x20`）、英文标点、十进制数字 `0`–`9`（`0x30`–`0x39`）、26 个大写拉丁字母 `A`–`Z`（`0x41`–`0x5A`）以及 26 个小写拉丁字母 `a`–`z`（`0x61`–`0x7A`）。

ASCII 在数学二进制层面上展现了令人惊叹的精妙设计：**大写字母与对应的小写字母之间，仅存在一个二进制比特的翻转差异（第 6 位 / bit 5）**！
* 大写 ‘A’ 为 `0100 0001`（`0x41`）；
* 小写 ‘a’ 为 `0110 0001`（`0x61`）。

这意味着在底层的汇编语言与硬件逻辑中，大小写转换只需执行一条极其高效的按位逻辑运算（与 `0x20` 进行异或或或运算）。

然而，ASCII 的致命局限在于其彻头彻尾的“盎格鲁-撒克逊中心主义”（Anglo-Saxon centrism）：它完全没有为法语、德语、西班牙语、北欧语系的重音符与变音符（如 é, à, ç, ä, ñ, ø）保留任何位置，更遑论希腊文、西里尔文或远东汉字。

## IBM 帝国的封闭孤岛：EBCDIC

当整个业界逐步向 ASCII 标准靠拢时，大型机霸主 IBM 却走上了一条完全封闭的特立独行之路——**扩展二进制编码的十进制交换码（Extended Binary Coded Decimal Interchange Code, 简称 EBCDIC）**。

EBCDIC 是一套原生的 **8 位编码（8-bit encoding）**，拥有 256 个编码空间。然而，任何一个初涉 EBCDIC 的程序员都会被其令人费解的字母排列所困惑：在 EBCDIC 中，拉丁字母居然是**非连续排列的（non-contiguous）**！
* 字母 ‘A’ 到 ‘I’ 占据 `0xC1`–`0xC9`；
* 字母 ‘J’ 到 ‘R’ 占据 `0xD1`–`0xD9`；
* 字母 ‘S’ 到 ‘Z’ 占据 `0xE2`–`0xE9`；
在字母 ‘I’ 与 ‘J’ 之间、以及 ‘R’ 与 ‘S’ 之间，存在着巨大的、未分配的码位裂隙！

这一奇怪架构的根源，在于 IBM 对赫尔曼·霍列瑞斯（Herman Hollerith）穿孔卡片制表机机制的直接机械投影。

![ISO 1681 标准穿孔卡片物理结构（Figure 1-1）](/images/fonts-encodings/fig1-1-punch-card-iso-1681.png)

*图 1-1：标准穿孔卡片物理结构（ISO 1681 标准）。卡片包含 80 列，每列 12 个打孔位，上部第 12、11、0 行为区域孔（zone punches），下部 1–9 行为数字孔（digit punches）。*

在 **Figure 1-1** 所示的标准 80 列穿孔卡片中，每一列包含 12 个打孔位置：
* 下方的 0 至 9 行为**数字孔（digit punches）**；
* 最上方的两行（通常称为 12 行与 11 行）连同 0 行被称为**区域孔（zone punches）**。

在早期的制表机上：
* 字母 ‘A’ 到 ‘I’ 由“第 12 区域孔 + 数字孔 1 至 9”组合打出；
* 字母 ‘J’ 到 ‘R’ 由“第 11 区域孔 + 数字孔 1 至 9”组合打出；
* 字母 ‘S’ 到 ‘Z’ 则由“第 0 区域孔 + 数字孔 2 至 9”组合打出。

IBM 在将穿孔卡片逻辑直接硬编码进 System/360 大型机架构时，直接将卡片上的高位区域孔映射为了 EBCDIC 高 4 位字节的半区（nibble），从而在现代计算史上永久烙下了这道机械打孔时代的古老裂痕。

## ISO 2022：字符集转义扩展的通用框架

面对全世界形形色色的文字编码需求，国际标准化组织（ISO）在 1970 年代初制定了宏大的架构性元标准——**ISO 2022**（对应 ECMA-35）。

ISO 2022 的核心哲学，是在保持底层 7 位与 8 位硬件传输通道稳定的前提下，通过**转义序列（Escape sequences）**与**模式切换（modal switching）**，在多个不同的国家字符集之间动态来回跳跃。

在 8 位编码环境中，ISO 2022 将 256 个码位划分为四大核心功能象限，如 **Figure 1-2** 所示：

![ISO 2022 对 8 位编码空间的四象限划分（Figure 1-2）](/images/fonts-encodings/fig1-2-iso-2022-subdivisions.png)

*图 1-2：ISO 2022 对 8 位编码表格的划分方式。C0（`0x00`–`0x1F`）与 C1（`0x80`–`0x9F`）为控制字符区；GL（`0x20`–`0x7F`）与 GR（`0xA0`–`0xFF`）为图形可打印字符区。*

* **C0 控制区（`0x00`–`0x1F`）**：存放基本的控制字符（沿用 ASCII）；
* **GL 图形左区（Graphic Left, `0x20`–`0x7F`）**：对应 7 位字符集（如 ASCII）；
* **C1 控制区（`0x80`–`0x9F`）**：扩展的控制字符集；
* **GR 图形右区（Graphic Right, `0xA0`–`0xFF`）**：扩展的高位图形字符集。

系统预设了 4 个可挂载的字符集寄存器：**G0、G1、G2 与 G3**。通过发送特定的转义序列（以 `ESC` 引导，如 `ESC $ B`），用户可以将不同的字符集（例如日文汉字集 JIS X 0208）调入 G0，并通过**换入（Shift-In, SI）**与**换出（Shift-Out, SO）**控制符，指示终端当前后续字节流应当解释为哪个国家的文字。

ISO 2022 极具开创性，日后的日文邮件传输标准 ISO-2022-JP 至今仍在使用该机制。然而，这种“带状态记忆的流模式”（stateful encoding）在软件工程中极易引发灾难：一旦传输流中丢失了一个 `ESC` 转义序列，其后所有的文本都将被彻底错误解码为乱码（Mojibake）。

## ISO 8859 家族：8 位单字节的世界割据

为了彻底摆脱 ISO 2022 状态切换的繁琐，ISO 随后联合国际电报电话咨询委员会（CCITT）推出了现代单字节编码的经典旗舰——**ISO/IEC 8859 系列标准**。

ISO 8859 的架构极为明确：**完全保留低 128 个码位（`0x00`–`0x7F`）与 ASCII 完全一致（最高位 bit 7 为 0）；而将高 128 个码位（`0x80`–`0xFF`，最高位 bit 7 为 1）分配给特定语言区域的重音字母与拼写符号**。

ISO 8859 家族总计派生出了 16 个分卷标准，分别统治了全球不同的地缘文化版图：

| 标准编号 | 通用代号 | 覆盖主要语言与地理区域 | 核心特征与历史评述 |
| :--- | :--- | :--- | :--- |
| **ISO 8859-1** | **Latin-1** | 西欧主要语言（法、德、西、葡、意、荷、北欧） | 1987 年发布，成为早期互联网 HTTP 协议与 HTML 的默认基准字符集。 |
| **ISO 8859-2** | **Latin-2** | 中欧与东欧使用拉丁字母的语言（波兰、捷克、斯洛伐克、匈牙利、罗马尼亚） | 完整收录了中欧文字特有的哈谢克反折音符（Háček / ˇ）、下加尾形符（Ogonek / ˛）与斜杠划线字母（如波兰文 Ł）。 |
| **ISO 8859-3** | **Latin-3** | 南欧、世界语（Esperanto）、马耳他语（Maltese） | 特别收录世界语带字顶符字母（Ĉ, Ĝ, Ĥ, Ĵ, Ŝ, Ŭ）与马耳他语字母（Ċ, Ġ, Ħ, Ż）。 |
| **ISO 8859-4** | **Latin-4** | 北欧与早期波罗的海语言（爱沙尼亚、拉脱维亚、立陶宛） | 后期逐步被 ISO 8859-10 与 8859-13 所取代。 |
| **ISO 8859-5** | **Cyrillic** | 西里尔字母语言（俄语、白俄罗斯语、保加利亚语、马其顿语、塞尔维亚语） | 覆盖斯拉夫东正教文化圈，但在苏联民间受到了 KOI8-R 标准的强力竞争。 |
| **ISO 8859-6** | **Arabic** | 阿拉伯文基本字母 | 仅包含逻辑字母字符，不包含复杂的上下文草书连写变体字形。 |
| **ISO 8859-7** | **Greek** | 现代单音希腊文（Monotonic Greek） | 对应希腊国家标准 ELOT 928。 |
| **ISO 8859-8** | **Hebrew** | 希伯来文与意第绪语 | 针对闪米特从右至左（RTL）书写文种，分为视觉顺序与逻辑顺序两种流派。 |
| **ISO 8859-9** | **Latin-5** | 土耳其语（Turkish） | 将 Latin-1 中极少使用的冰岛语字母（Ð, ð, Þ, þ）剔除，替换为土耳其语不带点字母 ı 与带下加符 Ğ/ğ, Ş/ş。 |
| **ISO 8859-10** | **Latin-6** | 北欧萨米语（Sámi）与因纽特语 | 专为北极圈少数族群文字设计。 |
| **ISO 8859-11** | **Thai** | 泰文（Thai） | 直接脱胎于泰国国家标准 TIS-620。 |
| **ISO 8859-13** | **Latin-7** | 现代波罗的海边缘语言 | 彻底修正了 Latin-4 遗留的字母缺失瑕疵。 |
| **ISO 8859-14** | **Latin-8** | 凯尔特语族（爱尔兰盖尔语、苏格兰盖尔语、威尔士语、布列塔尼语） | 收录带有传统上加点符（*ponc séimhithe*）的古盖尔字母。 |
| **ISO 8859-15** | **Latin-9** | 现代西欧修订版（Latin-1 升级体） | 1999 年推出，旨在引入**欧元符号 €（`0xA4`）**，并补全了在法文中不可或缺的连字 **Œ / œ** 与芬兰文带两点字母 **Š / š / Ž / ž**。 |
| **ISO 8859-16** | **Latin-10** | 东南欧罗曼语族（特别针对罗马尼亚语） | 修正了罗马尼亚语中长期被错误使用下加软音符（Cedilla, Ș/Ț）而非标准**下加逗号（Comma Below, Ș/Ț）**的历史技术积弊。 |

ISO 8859 家族的根本缺陷在于其各分卷之间的**完全互斥性**：如果在同一篇文本中同时包含法语单词（é）、波兰语姓名（Ł）与俄语书名，任何一个单字节 ISO 8859 编码都无法在一张表内同时呈现它们——此时文本将被迫沦为乱码的深渊。

## 远东 CJK 汉字文化圈的破局：双字节编码时代

对于中、日、韩（CJK）三国而言，汉字系统的表意文字数量数以万计，单字节的 256 个码位无异于杯水车薪。远东各国的计算先驱必须开拓出**多字节编码（Multi-byte Encodings）**的疆土。

### 1. 中国国家标准：GB 2312-1980 与区位码
1980 年，中国国家标准总局发布了划时代的 **GB 2312-1980**（《信息交换用汉字编码字符集·基本集》）。
* GB 2312 构建了一个 $94 \times 94$ 的二维矩阵，被称为**区位码（Row-Cell Coding）**：
  * **区号（Row, 1–94）**：1–9 区为图形符号、全角数字与拉丁字母、希腊字母、日文假名、拼音等；16–55 区收录 3,755 个按汉语拼音排序的一级常用汉字；56–87 区收录 3,008 个按部首排序的二级次常用汉字；
  * **位号（Cell, 1–94）**：每个区包含 94 个字位。
* 为了使汉字字节流能够在计算机中与单字节 ASCII 完全兼容共存，工程上发明了 **EUC-CN（Extended Unix Code）**，即今天人们常说的 GB 2312 落地格式：**将区号和位号分别加上偏移量 `0xA0`（即十进制 160）**！  
  如此一来，每个汉字的高字节与低字节均严格落在 `0xA1`–`0xFE` 之间，最高位（bit 7）恒为 1，从而与最高位为 0 的 7 位 ASCII 码（`0x00`–`0x7F`）井水不犯河水。计算机只需检测字节的最高位，便能瞬间判断当前是一个英文单字符，还是一个双字节汉字的起始前导码。

### 2. 日本与台湾地区的多元发展
* **Shift-JIS（SJIS）**：  
  在个人计算机领域，日本 ASCII 公司与微软为 MS-DOS 系统开发了 Shift-JIS 编码。它通过精巧的数学位移（Shift），将 JIS X 0208 的汉字与半角片假名紧凑塞入了单字节与双字节交织的空隙中；
* **Big5（大五码）**：  
  1984 年由台湾资策会与五大电脑厂商联合制定，收录 13,053 个繁体汉字，成为港台及海外繁体中文社群事实上的核心工业基准。

## 操作系统巨头的封建割据：微软代码页与苹果编码

在个人计算机操作系统的垄断战中，微软与苹果各自构建了封闭的字符编码王国：

### 微软代码页（Microsoft Codepages）
微软在 MS-DOS 时代创造了 **代码页（Codepage）** 这一术语，特指操作系统在特定硬件或区域设置下所加载的字符映射表：
* **DOS OEM 代码页**：如著名的 **CP437（IBM PC 原生代码页）**，其高 128 位充斥着大量用于绘制字符界面窗口边框的制表符（box-drawing characters）与希腊数学符号；以及面向西欧的 CP850；
* **Windows ANSI 代码页**：当 Windows 3.1 与 Windows 95 登临王座时，微软在系统底层确立了 Windows-125x 系列代码页。例如著名的 **CP1252（Windows Latin-1）**——它悄悄利用了 ISO 8859-1 中原本保留给 C1 控制码的未分配盲区（`0x80`–`0x9F`），硬塞入了弯引号（‘ ’ “ ”）、破折号（—）、千分号（‰）、欧元符号（€）以及商标符号（™）。这种对国际标准的私自越轨修改，给日后全球跨平台数据交换埋下了无休止的“乱码炸弹”。

### 苹果编码系统（Apple Encodings）
苹果 Macintosh 系统完全走在另一条轨道上：苹果设计了自己的 **MacRoman** 编码，将高位空间分配给了优雅的排印标点、数学符号与带重音字母；对于中欧则推出了 MacCentralEurRoman。在 Mac 与 PC 之间通过软盘或局域网交换纯文本文档，在当时几乎必然以满屏错乱的乱码而告终。

## 早期的互联网：在 MIME 与 HTTP 的夹缝中求生

在 Web 浏览器席卷全球之前，互联网最核心的杀手级应用是**电子邮件（Electronic Mail）**。

早期的互联网邮件传输协议（SMTP, RFC 821）拥有极度苛刻的硬件历史包袱：**它是一条纯粹的 7 位信道（7-bit clean channel）**。如果直接将包含 8 位扩展字符（如 ISO 8859 或 GB 2312 汉字）的数据流送入 SMTP 服务器，许多古老的路由节点会毫不留情地强行抹掉每个字节的最高位（bit 7），导致整个邮件内容彻底毁损不可逆！

为了在 7 位信道上传输复杂的国际化多媒体与非拉丁文本，IETF 在 1990 年代初制定了划时代的 **MIME 协议规范（Multipurpose Internet Mail Extensions, RFC 2045–2049）**：
1. **Quoted-Printable 传输编码**：  
   对于主要由 ASCII 构成的西欧文本，将少数重音字符的高位字节编码为等号引导的十六进制表示（例如字符 ‘é’ 被编码为 `=E9`）；
2. **Base64 传输编码**：  
   将任意 8 位二进制流切分为 6 位的微小单元，并将每 6 位映射至由 64 个安全 ASCII 字符组成的字典集中，使汉字与二进制附件能够安然无恙地穿透任何 7 位中继网关；
3. **MIME 邮件标头与参数化**：  
   ```http
   Content-Type: text/plain; charset="iso-8859-1"
   Content-Transfer-Encoding: quoted-printable
   ```

万维网（The Web）的降临使得字符集声明成为了全球 Web 开发者必须面对的核心课题：Web 服务器必须在 HTTP 响应头中发送 `Content-Type: text/html; charset=...`，而 HTML 文档自身亦需在 `<head>` 中嵌入 `<meta http-equiv="Content-Type" content="text/html; charset=...">`。当服务器配置与网页内联声明发生冲突时，浏览器便陷入了进退维谷的竞态判定之中。

## 历史的必然：呼唤全球统一文字之网

回望前 Unicode 时代的编码全景，人类计算世界宛如一座被巴别塔语言之乱彻底撕裂的孤岛群：
* 西欧人无法在 Latin-1 中阅读中欧同事的邮件；
* 俄语世界在 ISO 8859-5、KOI8-R 与 Windows-1251 之间分崩离析；
* 跨平台的代码页映射表动辄充斥着冲突、未定义行为与数据丢失；
* 在多语言混合学术典籍、跨国经贸文书与全球化互联网面前，单字节与局部双字节编码体系已经彻底走到了历史的穷途末路。

正是这种令人窒息的碎片化与工程灾难，倒逼全球计算机科学家与工业巨头们放下彼此的偏狭壁垒，在二十世纪八十年代末开启了一项前所未有的宏伟史诗计划——**构建一套能够容纳全人类历史上一切已知文字的永恒通用字符集（Universal Character Set）**。

这，正是 Unicode 时代的破晓曙光。
