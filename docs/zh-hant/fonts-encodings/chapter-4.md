# 第四章 · 規範化、雙向演算法與東亞字元體系
### Chapter 4: Normalization, bidirectionality, and East Asian characters
**著者：雅尼斯·哈拉蘭布斯 博士（Yannis Haralambous, Ph.D.）**  
*選自《字型與編碼》（Fonts & Encodings）原著第 127–158 頁*

*譯者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

在理解了 Unicode 字元的基本定義、底層編碼形式與宏觀平面佈局之後，我們必須正視文字排印中最棘手的三大計算挑戰：**字元序列的等價正規化**、**多文種混排的雙向流動演算法**、以及**東亞表意漢字與音節文字的複雜拓撲結構**。

這三個領域分別對應著現代數字文字處理的核心靈魂：若沒有規範化，搜尋引擎將無法在海量異構文字中建立確定性的索引；若沒有雙向演算法，阿拉伯文與希伯來文將永遠無法與西方字母在同一段落內和諧共存；若沒有對東亞文字型系的深刻數理建模，包含數萬漢字的龐大資訊世界將陷入字元爆炸的泥潭。

## 分解與規範化（Decompositions and Normalizations）

Unicode 繼承了大量歷史編碼遺留下來的“預合成字元”（Precomposed Characters，例如帶有重音符的拉丁字母 ‘é’、‘ü’），同時也提供了“基礎字元 + 組合變音符”（Base Character + Combining Marks）的動態組合機制。

這就引發了一個嚴重的數學問題：對於人類視覺和語義完全相同的同一個文字單位，在計算機內部可能存在多種完全不同的二進位制碼位序列！例如，帶有上加抑音符的字母 ‘è’ 可以表示為：
* 單一預合成字元：`U+00E8`（LATIN SMALL LETTER E WITH GRAVE）；
* 基礎字元加組合標記：`U+0065`（LATIN SMALL LETTER E）+ `U+0300`（COMBINING GRAVE ACCENT）。

如果系統不對這些序列進行標準化規整，字串相等性比較、雜湊表查詢以及資料庫主鍵匹配將徹底失效。為此，Unicode 聯合創始人馬克·戴維斯（Mark Davis）與馬丁·迪爾斯特（Martin Dürst）共同制定了 **Unicode 標準附件第 15 號（UAX #15: Unicode Normalization Forms）**。

### 組合字元與規範結合類（Combining Characters & Combining Classes）

當一個基礎字元同時附帶多個不同方位的變音符號時（例如越南語或古希臘語中的多重重音字母），變音符號在資料流中的先後順序是否可以任意顛倒？

語言學與排版學表明：變音符號可以劃分為彼此正交的方位類別。如果在不同方位（例如一個在字元下方，另一個在字元上方），則它們的施加順序並不影響最終的印刷視覺形態；但如果兩個變音符號處於同一個物理方位（例如兩個都在字元上方依次疊放），則它們自下而上的堆疊順序就具有決定性的拓撲意義！

為了在數理上嚴格形式化這一規則，Unicode 為每一個組合字元分配了一個介於 $0 \sim 255$ 之間的整數屬性——**規範結合類（Canonical Combining Class, ccc）**：
* **Class 0（Spacing / Base Characters）**：所有基礎字元、不可見控制符以及普通空格；
* **Class 1（Overlay）**：覆蓋在字元中央的疊置標記（例如刪除線、斜槓橫槓）；
* **Class 7（Nukta）**：印度次大陸文字中緊隨子音的下方讀音微調點；
* **Class 8（Kana Voicing）**：日文假名的濁點（゛）與半濁點（゜）；
* **Class 9（Virama）**：印度系文字中用於消除子音固有母音、強制構成結合字的結音符（Halant / Virama）；
* **Class 200–214（Fixed Position Marks）**：希伯來文聖經吟誦音符等固定位置特殊標記；
* **Class 216（Attached Below / ATBL）**：緊貼在字元下方的字形變體（如羅馬尼亞文逗號）；
* **Class 218（Attached Below Right）**：緊貼字元右下方的標記；
* **Class 220（Below / B）**：位於字元正下方的變音符（如變音下加點 `U+0323`、軟音符 Cedilla）；
* **Class 222（Below Right / BR）**：位於字元右下方的獨立變音符；
* **Class 228（Above / A）**：位於字元正上方的變音符（如銳音符、抑音符、長音符 Macron `U+0304`、波浪符 Tilde）；
* **Class 230（Above Right / AR）**：位於字元右上方的變音符；
* **Class 232（Double Above / DA）**：橫跨在兩個連續字元上方的雙重變音符；
* **Class 240（Iota Subscript）**：古希臘文特有的下加 Iota 標記。

### 規範重排序演算法（Canonical Ordering Algorithm）

有了結合類，Unicode 確立了確定性的**規範重排序演算法（Canonical Ordering Algorithm）**：
1. 從左至右掃描字串；
2. 基礎字元（`ccc = 0`）的位置保持絕對不動；
3. 任何附屬於該基礎字元之後的連續組合字元序列，按照其**規範結合類數值（ccc）的大小升序排列**；
4. 若兩個相鄰組合字元的 `ccc` 數值完全相同，則保持它們原有的相對先後順序不變（保證同向堆疊層級不被篡改）。

例如，字元 ‘a’ 同時附帶下方加點（`U+0323`，`ccc = 220`）與上方長音符（`U+0304`，`ccc = 228`）：
* 序列一：`U+0061` + `U+0323`（下點 220）+ `U+0304`（長音 228）；
* 序列二：`U+0061` + `U+0304`（長音 228）+ `U+0323`（下點 220）。  
經過規範重排序演算法處理後，由於 $220 < 228$，序列二將被確定性地強制重排為序列一！

### 規範分解與相容分解

Unicode 定義了兩種不同層級的字元分解：
* **規範分解（Canonical Decomposition）**：  
  僅針對在語言學和排版功能上**完全等價、絕對無損**的字元對。例如將預合成的 ‘é’（`U+00E8`）分解為 ‘e’（`U+0065`）+ 抑音符（`U+0300`）；
* **相容分解（Compatibility Decomposition）**：  
  針對在排版樣式、歷史字模或遺留工業標準中存在細微視覺格式差異、但在純文字語義上等價的字元。例如：
  * 日本排版連字 ‘㎦’（`U+33A6`）相容分解為 ‘k’ + ‘m’ + 上標 ‘3’（`U+00B3`），上標 ‘3’ 進一步分解為普通數字 ‘3’；
  * 羅馬數字 ‘Ⅳ’（`U+2163`）相容分解為字母 ‘I’ + ‘V’；
  * 歐文印刷連字 ‘ﬁ’（`U+FB01`）相容分解為 ‘f’ + ‘i’；
  * 全形英文字母 ‘Ａ’（`U+FF21`）相容分解為普通 ASCII ‘A’；
  * 圓圈包圍字元 ‘①’（`U+2460`）相容分解為數字 ‘1’。

### 四大規範化形式（The Four Normalization Forms）

將上述兩種分解方式與規範重排序及規範合成相結合，便誕生了全球通用的四大規範化形式：

| 規範化形式 | 英文全稱 | 核心機制 | 典型適用場景 |
| :--- | :--- | :--- | :--- |
| **NFD** | Normalization Form D | 規範分解（Canonical Decomposition）+ 結合類升序重排序 | 語言學音標分析、變音符提取、字元搜尋引擎底層 |
| **NFC** | Normalization Form C | 先執行 NFD 規範分解，再透過演算法將字元重新**規範合成（Canonical Composition）** | **W3C、HTML、XML 及現代 Web 的絕對預設標準** |
| **NFKD** | Normalization Form KD | 相容分解（Compatibility Decomposition）+ 結合類升序重排序 | 語義文字抽取、模糊匹配、無格式純文字轉換 |
| **NFKC** | Normalization Form KC | 先執行 NFKD 相容分解，再執行規範合成 | 全域性搜尋引擎建立倒排索引、識別符號標準化 |

## 雙向排版演算法（The Bidirectional Algorithm / UAX #9）

在由西方字母構成的單向世界中，文字流淌的方向是單一而自然的：從左向右（LTR）。然而在近東文明中，阿拉伯文、希伯來文、敘利亞文與它拿字母均是從右向左（RTL）書寫。

當一篇現代科學文獻、法律條約或網路百科中同時出現英語、希伯來語、阿拉伯語與數學公式時，計算機排版系統面臨著極其驚心動魄的挑戰：
1. **段落閱讀的大方向與行內巢狀小方向的衝突**；
2. **文字在從右至左流動時，嵌入其中的阿拉伯數字卻是從左至右書寫的！**
3. **括號、引號與數學不等號在視覺呈現時必須根據文字流向發生物理映象翻轉！**
4. **多行排版時斷行（Line Breaking）位置的雙向邊界重組！**

這就是著名的 **Unicode 雙向排版演算法（Unicode Bidirectional Algorithm, 簡稱 Bidi 演算法，收錄於 UAX #9）**。

### 段落排印的宏觀流動與微觀斷行

作者在此給出了一個極富啟發的雙向排版斷行實驗：假設我們在一段英文（從左向右）中嵌入了一句從右向左書寫的阿拉伯語詩句。若以小寫反向拼寫來模擬從右向左的文字流動，這段嵌入文字呈現為：
> First second third fourth hthgie htneves htxis htfif  
> htneetriht htflewt htnevele htnet htnin fourteenth  
> fifteenth sixteenth seventeenth.

注意到第二行的排列：由於這是一段從右向左流動的段落，當第一行右端空間不足發生斷行時，文字並不是從第二行左側開始，而是**從第二行最右側繼續向左書寫**！當嵌入的從右向左段落結束後，英文文字（`fourteenth ...`）又恢復從左側排起。若沒有嚴格的數學演算法指導，排版軟體在計算折行座標時將產生毀滅性的視覺錯亂。

此外，數字的處理更是雪上加霜：在阿拉伯文與希伯來文中，**數字無論何時都必須從左向右書寫**。例如作者的生日寫作：
`Friday, February 16, 1962`
在阿拉伯語中，單詞部分從右至左，但數字 `1962` 與 `16` 卻必須保持從左至右。這意味著每一個數字串都被視為一個微觀的從左至右“孤島”。

### 雙向字元型別（Bidirectional Character Types）

為了精確控制每一個字元的雙向行為，Unicode 為全部 111 萬個碼位分配了唯一的雙向型別，共劃分為三大類 19 種屬性：

1. **強字元型別（Strong Types）**：  
   具有絕對固有的書寫方向，主導周圍文字的排版趨勢：
   * **L（Left-to-Right）**：所有拉丁字母、西裡爾字母、希臘字母、東亞漢字與假名；
   * **R（Right-to-Left）**：希伯來字母及相關閃米特子音文字；
   * **AL（Arabic Letter / Right-to-Left Arabic）**：阿拉伯字母及其專有標點（在數字處理上具有比 R 更強的語境推導力）。
2. **弱字元型別（Weak Types）**：  
   其方向性在很大程度上取決於其所處的上下文環境：
   * **EN（European Number）**：歐洲拉丁數字（`0`–`9`）；
   * **ES（European Number Separator）**：歐洲數字正負號（`+`、`-`）；
   * **ET（European Number Terminator）**：貨幣與百分比符號（`$`、`%`、`€`）；
   * **AN（Arabic-Indic Number）**：阿拉伯-印度數字（`٠`–`٩`）；
   * **CS（Common Number Separator）**：數字通用分隔符（冒號、逗號、小數點、不換行空格，共 11 個字元）；
   * **NSM（Non-Spacing Mark）**：組合變音符與變體選擇符（自動繼承其基底字元的方向型別）；
   * **BN（Boundary Neutral）**：排版邊界中性符（零寬連字/非連字控制符、語言標籤）。
3. **中性字元型別（Neutral Types）**：  
   本身完全沒有方向傾向，方向完全由周圍強字元決定：
   * **B（Paragraph Separator）**：段落分隔符（回車 `\r`、換行 `\n`）；
   * **S（Segment Separator）**：製表符 Tab；
   * **WS（Whitespace）**：所有非零寬度的普通空格；
   * **ON（Other Neutral）**：通用標點符號、數學運算子、幾何圖形、繪圖符號等（共 3,007 個字元）。
4. **顯式控制符（Explicit Formatting Codes）**：  
   排版人員可強行插入程式碼流以覆蓋預設演算法的 5 大特殊控制字元：`LRE`（左至右嵌入）、`RLE`（右至左嵌入）、`LRO`（左至右強制覆蓋）、`RLO`（右至左強制覆蓋）與 `PDF`（彈出方向格式化狀態）。

### 雙向演算法六大步驟（The Six Steps of UAX #9）

Bidi 演算法由六大緊密相扣的計算階段構成：
* **步驟一：確立段落基準級別（Base Level）**：  
  掃描段落中的第一個強型別字元；若為 L 則基準級別 $S_0 = 0$（預設 LTR）；若為 R 或 AL 則基準級別 $S_0 = 1$（預設 RTL）。
* **步驟二：解析顯式嵌入級別（Explicit Levels & Stack）**：  
  維護一個方向巢狀堆疊（最高支援 61 層，後續版本擴充套件至 125 層）。每遇到 `LRE`/`RLE`/`LRO`/`RLO` 便將新的級別壓棧，遇到 `PDF` 則退棧。偶數級別代表從左向右，奇數級別代表從右向左。
* **步驟三：解析弱型別（Resolving Weak Types, W1–W7）**：  
  * **W1**：所有 `NSM` 繼承其前驅基底字元的型別；
  * **W2**：若 `EN` 的左側最近強字元為 `AL`，則該 `EN` 變為 `AN`；
  * **W3**：所有 `AL` 轉為 `R`；
  * **W4**：夾在兩個 `EN` 之間的單個 `ES`（如 `1+1`）或夾在兩數之間的 `CS`（如 `3.14`）變為 `EN`；
  * **W5**：緊鄰 `EN` 前後的連續 `ET`（如 `$100`）變為 `EN`；
  * **W6**：所有未被吸收的孤立 `ET`、`ES`、`CS` 全部退化為 `ON`；
  * **W7**：若 `EN` 前面的最近強字元為 `L`，則該 `EN` 變為 `L`。
* **步驟四：解析中性型別（Resolving Neutral Types, N1–N2）**：  
  * **N1**：若一段連續中性字元（空格或標點）兩側的字元方向相同，則該中性段直接變為該方向；
  * **N2**：若兩側方向相反，則該中性段的型別退回到當前嵌入環境的基準方向。
* **步驟五：確定隱式級別（Resolving Implicit Levels, I1–I2）**：  
  依據字元最終確立的型別（L、R、AN、EN），對其所在的顯式級別進行最終調整微調（例如在偶數級別中的 R 需加 1 變成奇數）。
* **步驟六：行內重排與映象翻轉（Reordering & Mirroring, L1–L4）**：  
  找出當前行內的最高階別 $L_{\max}$，從最高階別逐步遞減到最低階別，對處於當前級別及以上的所有連續子串進行**逐級倒序反轉（Reverse）**！並在反轉完成後，對所有具備映象屬性的字元執行字形翻轉。

#### 巢狀反轉生動算例
考慮巢狀字串：`[0He said that “˝[1[2yes]2 means yes]1ˇ”.]0`  
* 級別 2 的子串 `[2yes]2` 最先發生第一級反轉；
* 隨後在級別 1 範圍內進行第二級反轉，內部已反轉的子串再次被整體反轉；
* 最終輸出完美的物理顯示序列。

### 映象屬性（Mirroring & BidiMirroring.txt）

雙向排版中最令人歎為觀止的細節莫過於**字元映象**。在西方語言中，左圓括號 ‘(’ 象徵著一段語句的“開始”；然而在從右向左流動的阿拉伯語或希伯來語文字文件中，“語句的開始”在物理空間的右側！因此，排版引擎在渲染右橫向文字時，如果遇到 ‘(’，絕不能直接畫出向右凸出的弧線，而必須動態將其翻轉為向左凸出的 ‘)’！

Unicode 專門釋出了標準化對映檔案 `BidiMirroring.txt`，其中收錄了多達 **320 對具有嚴格幾何映象關係的字元**：
* 各種括弧：`(` 與 `)`、`[` 與 `]`、`{` 與 `}`、`〈` 與 `〉`、`«` 與 `»`；
* 數學關係運算子：`<` 與 `>`、`≤` 與 `≥`；
* 幾何箭頭：$\leftarrow$ 與 $\rightarrow$。

## 東亞書寫系統（East Asian Scripts）

東亞表意文字系統是人類文字進化史上最壯麗的豐碑，同時也是計算機文字編碼最具挑戰性的領域。

### 中日韓漢字表意文字（Ideographs of Chinese Origin / CJK）

漢字起源於古代中國黃河流域的甲骨文與金文，歷經數千年演化，傳播至朝鮮半島、日本列島與越南，形成了橫跨多國的“漢字文化圈”。

然而，漢字與西方拼音文字存在根本差異：它不是由幾十個字母拼成的線形串，而是具有龐大字數、二維方塊結構以及一字多音多義的表意體系。僅《康熙字典》便收錄了 47,035 個漢字，而當今跨國學術與古籍整理涉及的漢字總量更是突破了十萬之巨！

面對如此浩瀚的字海，Unicode 聯合中日韓三方專家成立了**表意文字工作組（Ideographic Rapporteur Group, IRG）**，推進了計算歷史上最偉大的**中日韓漢字統合（Han Unification）**工程：
* 剔除字形上的微小異體寫法，確立以《康熙字典》214 個部首及筆畫拓撲結構為準則的統合規則；
* 構建統漢字資料庫（Unihan Database），為每個漢字記錄其在普通話、粵語、唐代中古音、日文音讀與訓讀、韓語音讀以及越南語中的全部讀音與交叉索引屬性。

#### 漢字結構描述字元（Ideographic Description Characters, IDC）

儘管 Unicode 收錄的漢字已達七萬餘個，但世界上總會存在某些地方誌、宋元刻本或古代碑帖中從未被標準編碼的罕見漢字。為了解決這一“外字（Gaiji）”危機，Unicode 在 $0\text{x2FF0} \sim 0\text{x2FFB}$ 區段引入了 **12 個表意文字描述字元（IDC）**。

這些字元不是可列印漢字，而是**字首二元或三元結構運算子**，採用波蘭字首表示式（Prefix Notation）描述漢字的二維幾何裝配結構：

| 碼位 | 字元符號 | 結構名稱 | 語法與含義 | 範例裝配 |
| :---: | :---: | :--- | :--- | :--- |
| `U+2FF0` | ⿰ | 左右結構（Left-to-Right） | 二元運算子：左部件 + 右部件 | ⿰ 禾 口 $\to$ 和 |
| `U+2FF1` | ⿱ | 上下結構（Above-to-Below） | 二元運算子：上部件 + 下部件 | ⿱ 艹 化 $\to$ 花 |
| `U+2FF2` | ⿲ | 左中右結構（Left-to-Middle-and-Right） | 三元運算子：左 + 中 + 右 | ⿲ 氵 木 ⿹ $\to$ 澍 |
| `U+2FF3` | ⿳ | 上中下結構（Above-to-Middle-and-Below） | 三元運算子：上 + 中 + 下 | ⿳ 𠂉 一 心 $\to$ 意 |
| `U+2FF4` | ⿴ | 全包圍結構（Full Surround） | 二元運算子：外框 + 內部件 | ⿴ 囗 大 $\to$ 因 |
| `U+2FF5` | ⿵ | 上三包圍（Surround from Above） | 二元運算子：上外框 + 內部件 | ⿵ 門 日 $\to$ 間 |

### 字元描述語言（Character Description Language, CDL）

在 1980 年代，精通中文的美國計算機學者湯姆·畢曉普（Tom Bishop）為了開發漢字教學軟體中動態展示筆畫順序的功能，發明了一套描述漢字內部幾何骨架的語言。伴隨著 XML 技術的風靡，畢曉普與理查德·庫克（Richard Cook）將其昇華為正式提交給 Unicode 技術委員會的 **字元描述語言（Character Description Language, CDL）**。

CDL 採用簡潔的 XML 語法，透過兩種機制精確構建漢字：
1. **元件巢狀複用（Component-based）**：使用已有的漢字或部首及其相對座標系拼合新字：
```xml
<cdl char="沰">
  <comp char="氵" points="0,0 40,128"/>
  <comp char="石" points="50,10 128,128"/>
</cdl>
```
2. **純筆畫裝配（Stroke-based）**：透過筆畫型別程式碼與起止控制點座標直接繪製基礎部件：
```xml
<cdl char="氵">
  <stroke type="d" points="30,10 40,25"/>
  <stroke type="d" points="25,45 35,60"/>
  <stroke type="t" points="10,110 50,80"/>
</cdl>
```

### 朝鮮語諺文（Hangul）與字母算術

在東亞所有書寫體系中，朝鮮語的**諺文（Hangul）**展現出了全人類文字史上最卓越的理知設計與數理純粹性。

1443 年，朝鮮王朝第四代君主**世宗大王（Sejong the Great）**有感於漢字深奧難通、普通百姓無法申訴冤屈，親自率領集賢殿學者歷時四年創造了《訓民正音》（Hunminjeongeum）。這是一套由 17 個基礎子音與 11 個基礎母音構成的拼音文字型系，其設計深刻凝聚了語音學與哲學智慧：

#### 子音的生理發音器官幾何象徵
* **‘ㄱ’（k/g）**：象形舌根閉塞咽喉之狀；
* **‘ㄴ’（n）**：象形舌尖抵住上顎齒齦之狀；
* **‘ㅁ’（m）**：象形嘴唇閉合之狀；
* **‘ㅅ’（s）**：象形門齒鋒利之狀；
* **‘ㅇ’（ng/零聲母）**：象形喉嚨圓通虛空之狀。  
在此基礎上，透過在基礎筆畫上**加畫（Stroke Addition）**來表達送氣清音：如在 ‘ㄱ’ 上加一橫變為送氣音 ‘ㅋ’；在 ‘ㄴ’ 上加橫變為 ‘ㄷ’，再加一橫變為送氣 ‘ㅌ’；在 ‘ㅁ’ 上加豎變為 ‘ㅂ’，再加橫變為送氣 ‘ㅍ’！

#### 母音的天地人三元宇宙觀
* **‘·’（天，圓）**：象徵無邊無際的穹蒼；
* **‘ㅡ’（地，平）**：象徵平坦遼闊的大地；
* **‘ㅣ’（人，立）**：象徵頂天立地的人類。  
三者交合化育萬物：‘·’ 居於 ‘ㅡ’ 之上為 ‘ㅗ’（陽），居於 ‘ㅡ’ 之下為 ‘ㅜ’（陰）；‘·’ 居於 ‘ㅣ’ 之右為 ‘ㅏ’（陽），居於 ‘ㅣ’ 之左為 ‘ㅓ’（陰）。

### 現代諺文音節塊的數字演算法藝術

儘管諺文在本質上是拼音字母（Jamo），但它在視覺排印上**絕不橫向線性排列**，而是將初聲子音（Initial, $L$）、中聲母音（Medial, $V$）與可選的終聲韻尾子音（Final, $T$）嚴格組裝為一個類似漢字的方塊音節塊！

一般音節結構遵循正則文法：
$$S = L + V + T^*$$

為了避免將初聲與終聲混淆，Unicode 規定了 19 個初聲（$L$）、21 箇中聲（$V$）與 28 種終聲狀態（$T$，包括 27 個韻尾及一個“無韻尾”的空狀態）。現代諺文全部可能的合法音節組合總數精確為：
$$N = 19 \times 21 \times 28 = 11{,}172$$

Unicode 在基本多語言平面的 $0\text{xAC00} \sim 0\text{xD7A3}$ 區段，完整開闢了這 11,172 個預合成音節塊。任何一個諺文音節的碼位，均可透過極其優美的高中代數方程無縫雙向計算：

$$\text{CodePoint} = \text{0xAC00} + (L_{\text{index}} \times 588) + (V_{\text{index}} \times 28) + T_{\text{index}}$$

其中：
* $588 = 21 \times 28$ 為每個初聲子音所統轄的連續音節跨度；
* $28$ 為每個中聲母音所統轄的連續終聲跨度。

#### 算例驗證：“한글”（Hangul）
以單詞 “한글” 為例：
1. **第一個音節 “한”（Han）**：
   * 初聲 ‘ㅎ’：索引 $L_{\text{index}} = 18$；
   * 中聲 ‘ㅏ’：索引 $V_{\text{index}} = 0$；
   * 終聲 ‘ㄴ’：索引 $T_{\text{index}} = 4$；
   * 碼位計算：$0\text{xAC00} + (18 \times 588) + (0 \times 28) + 4 = 0\text{xAC00} + 10584 + 4 = 0\text{xAC00} + 0\text{x295C} = 0\text{xD55C}$（即 `U+D55C`，한）。
2. **第二個音節 “글”（Geul）**：
   * 初聲 ‘ㄱ’：索引 $L_{\text{index}} = 0$；
   * 中聲 ‘ㅡ’：索引 $V_{\text{index}} = 18$；
   * 終聲 ‘ㄹ’：索引 $T_{\text{index}} = 8$；
   * 碼位計算：$0\text{xAC00} + (0 \times 588) + (18 \times 28) + 8 = 0\text{xAC00} + 504 + 8 = 0\text{xAC00} + 0\text{x0200} = 0\text{xAE00}$（即 `U+AE00`，글）。

透過這一純粹的整數算術，作業系統和文字引擎在處理諺文時完全無需查表，便能在單個 Jamo 字母與完整音節方塊之間實現飛一般的瞬時合成與分解，達到了理性與工程的最高和諧！
