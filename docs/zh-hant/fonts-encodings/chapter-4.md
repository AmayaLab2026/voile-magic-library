# 第 4 章：編碼方式、正規化與東亞文字體系

*譯者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

在本章中，我們將深入考察 Unicode 標準中三個高度專業化但對現代排版與文本處理具有決定性意義的核心領域。這三個領域雖然在語言學表面上看似各自獨立，但它們共同構成了高精度數字排版引擎的算法基石：
1. **字符的正規化與規範分解（Decompositions and Normalizations）**：解決字符序列在計算機表示中的多對一等價性與標準化存儲問題；
2. **雙向排版算法（The Bidirectional Algorithm，即 Unicode 附錄 UAX #9）**：解決從右向左書寫的文字（阿拉伯文、希伯來文）與從左向右書寫的文字（拉丁文、希臘文、西里爾文）在同一文本流中混合時的數學排版與視覺換向邏輯；
3. **東亞文字體系（East Asian Scripts）**：深入分析漢字文化圈中源自中國的表意文字（CJK Unihan 漢字）、字形描述語言（CDL）以及具有極致數學對稱性的韓國諺文（Hangul）音節構造模型。

## 1. 字符的分解與正規化（Decompositions and Normalizations）

在 Unicode 體系中，同一個人類肉眼可見的字形，往往可以通過不止一種底層的碼位序列在計算機內存中進行表達。例如帶抑揚符（Circumflex）的小寫字母 `â`，既可以編碼爲單一的預合成字符（Precomposed Character）`U+00E2`（LATIN SMALL LETTER A WITH CIRCUMFLEX），也可以由基礎拉丁字母 `a`（`U+0061`）後接非間距組合抑揚符（Combining Circumflex Accent）`U+0302` 組成的雙碼位序列來表示。

如果文本處理系統不對這種多義性制定嚴格的規範，那麼在文檔檢索、數據庫查詢、字符串散列比較（Hashing）以及網頁排版匹配時，就會產生災難性的“同字不同碼”失效。

### 1.1 組合字符與結合類（Combining Characters & Combining Classes）

在深入分解算法之前，必須首先對**組合字符（Combining Characters）**的物理吸附機制進行正交數學分類。在 Unicode 標準中，共有數百個組合字符，它們被嚴密地劃分爲 **53 個結合類（Combining Classes，簡稱 cc）**：

| 結合類代號 (cc) | 類別幾何方位描述 | 典型結合符示例 | 排版吸附行爲 |
| :---: | :--- | :--- | :--- |
| **0** | 間距基底字符（Spacing / Base Glyphs） | 普通字母 `a`, `B`, 數字 `1` | 具備獨立進深寬度，作爲後續組合符的幾何寄主 |
| **1** | 覆蓋疊加符（Overlay） | 粗斜線疊加符 `U+0338` (̸) | 從幾何正中心橫跨基底字符 |
| **7** | 努克塔符（Nukta） | 印度系文字核音變音點 | 緊密吸附於輔音字母右下角 |
| **8** | 假名半濁音/濁音符（Kana Voicing） | 日文濁音符 `U+3099` (゙) | 位於假名右上側 |
| **9** | 純輔音抑制符（Virama） | 梵文/印地文去元音符 `U+094D` | 促使輔音形成連寫合字（Conjuncts） |
| **202** | 附着於下方（Attached Below） | 下加尾形符（Cedilla `U+0327`）、反尾形符（Ogonek `U+0328`） | 物理筆畫直接焊連在基底字符底部 |
| **214** | 附着於上方（Attached Above） | 扁平橫線、特定重音符 | 物理筆畫焊連在基底字符頂端 |
| **216** | 附着於右上角（Attached Above Right） | 越南文角符（Horn `U+031B` ơ, ư） | 吸附於元音字母的右上肩部 |
| **218** | 附着於左下角（Attached Below Left） | 專用發音輔助圈記 | 吸附於左下基準點 |
| **220** | 絕對下方非附着（Below） | 下加點符（Dot Below `U+0323`）、下抑揚符（Caron Below `U+032C`） | 懸浮位於基底字符正下方，預留光學間隙 |
| **222** | 絕對右下方非附着（Below Right） | 下方右側輔助符 | 位於右下角光學間隙 |
| **228** | 絕對左方（Left） | 希伯來文/敘利亞文前置引導標 | 位於基底字符左側空間 |
| **230** | 絕對上方非附着（Above） | 銳音符（Acute `U+0301`）、抑音符（Grave `U+0300`）、抑揚符（Circumflex `U+0302`） | 懸浮位於基底字符正上方 |
| **232** | 絕對右上角非附着（Above Right） | 上加右角符 | 位於右上光學空間 |
| **234** | 頂端最上方（Top Above） | 多層重疊音調符的最外層 | 堆疊在其他上方重音之上的最高空域 |

這一分類體系蘊含着兩條關鍵的排版幾何公理：
1. **正交類別的幾何獨立性**：屬於不同非零結合類的組合字符（例如一個下方變音符 `cc=220` 和一個上方變音符 `cc=230`），在物理空間上互不干涉。無論它們在字符串中誰先誰後輸入，排版引擎渲染出的最終複合字形在視覺上是完全相同的。
2. **同類結合符的次序敏感性**：屬於相同非零結合類的兩個組合符（例如兩個同在下方的變音符），其輸入次序代表了自基底字符向外逐層堆疊（Stacking）的物理拓撲次序，交換它們的順序將產生不同的字形含義。

### 1.2 規範排序算法（Canonical Ordering Algorithm）

爲了消解由於正交結合符輸入次序不同導致的二進制不一致，Unicode 提出了**規範排序算法（Canonical Ordering Algorithm）**。

算法流程如下：
1. 遍歷待正規化的字符序列，確定每個字符的結合類數值 `cc`；
2. 找出所有連續的由非零結合類字符組成的子序列（即基底字符之後的一串組合變音符）；
3. 對該子序列執行**穩定排序（Stable Sort）**，排序鍵值爲各字符的 `cc` 屬性值。所謂“穩定”，是指當兩個字符的 `cc` 值相同時，算法必須嚴格保持它們在原始輸入流中的相對次序不變；而當兩個字符的 `cc` 值不同時，`cc` 較小的字符必須排在 `cc` 較大的字符之前。

#### 實例演練：複雜多重變音符排序
假設存在一個由基礎字母 `a` 以及三個變音符構成的輸入序列：
```
1. U+0061  (LATIN SMALL LETTER A)               [cc = 0]
2. U+0302  (COMBINING CIRCUMFLEX ACCENT, 上方)    [cc = 230]
3. U+032C  (COMBINING CARON BELOW, 下方)          [cc = 220]
4. U+0323  (COMBINING DOT BELOW, 下方)            [cc = 220]
```
- 組合符序列爲 `[U+0302 (230), U+032C (220), U+0323 (220)]`；
- 執行穩定排序後，由於 $220 < 230$，兩個下方變音符必須前移；且由於穩定排序保證相同鍵值保持相對順序，`U+032C` 依然位於 `U+0323` 之前；
- 排序後的標準化輸出序列爲：
```
1. U+0061  (a)         [cc = 0]
2. U+032C  (caron blw) [cc = 220]
3. U+0323  (dot blw)   [cc = 220]
4. U+0302  (circumflx) [cc = 230]
```

### 1.3 規範等價性與兼容等價性（Canonical vs Compatibility Equivalence）

Unicode 嚴格區分了兩種不同深度的等價概念：
1. **規範等價（Canonical Equivalence）**：指在純文本語義和排版表現上完全一致的等價。預合成字符與經過規範排序的分解序列之間即屬於規範等價。
   $$\text{U+00E2} \equiv \text{U+0061} + \text{U+0302}$$
2. **兼容等價（Compatibility Equivalence）**：指在純文本核心語義上等價，但在視覺風格、排版格式（如上標、下標、字體花體變體）、環繞圈記或度量佈局上存在差異的等價。
   - 上標數字與基底數字：$\text{U+00B2} \ ({}^2) \approx \text{U+0032} \ (2)$（帶有 `<sup>` 格式標籤）；
   - 帶圈數字：$\text{U+2460} \ (\text{①}) \approx \text{U+0031} \ (1)$（帶有 `<circle>` 標籤）；
   - 專用連字與寬字符：$\text{U+FB01} \ (\text{fi}) \approx \text{U+0066} + \text{U+0069}$（帶有 `<compat>` 標籤）；
   - 複合度量單位：$\text{U+33A1} \ (\text{km}^3) \approx \text{U+006B} + \text{U+006D} + \text{U+0033}$。

### 1.4 四大正規化形式（NFC, NFD, NFKC, NFKD）

結合上述兩種分解機制與重新合成邏輯，Unicode 定義了四種標準的文本正規化形式：

```
                    +--------------------+
                    |   Raw Text Stream  |
                    +---------+----------+
                              |
              +---------------+---------------+
              |                               |
       Canonical Decompose          Compatibility Decompose
              |                               |
              v                               v
       +-------------+                 +-------------+
       |     NFD     |                 |    NFKD     |
       +------+------+                 +------+------+
              |                               |
       Canonical Compose               Canonical Compose
              |                               |
              v                               v
       +-------------+                 +-------------+
       |     NFC     |                 |    NFKC     |
       +-------------+                 +-------------+
```

1. **NFD（Canonical Decomposition）**：規範分解形式。將所有合體字完全拆分爲基底字符與組合符，並按結合類執行規範排序。
2. **NFC（Canonical Decomposition followed by Canonical Composition）**：規範分解後進行規範合成。**這是萬維網聯盟（W3C）推薦的 Web 網頁標準文本傳輸形式**。文本先展開爲 NFD，隨後算法在可能的情況下，儘可能將基底字符與後續組合符重新融合成單一的預合成碼位。
3. **NFKD（Compatibility Decomposition）**：兼容分解形式。將所有兼容字符（連字、上標、圈記字符、分數）徹底展開爲基本語義字符序列，並執行規範排序。常用於全文搜索索引引擎，使搜索 `km3` 能精確召回含有 `km³` 的文檔。
4. **NFKC（Compatibility Decomposition followed by Canonical Composition）**：兼容分解後進行規範合成。在去除所有排版格式變體後，再執行可能的最大化規範預合成。

## 2. Unicode 雙向排版算法（The Bidirectional Algorithm / UAX #9）

在現代多語言排版體系中，最具算法挑戰性的工程難題當屬**雙向文本（Bidirectional Text，簡稱 Bidi）**。希伯來文（Hebrew）、阿拉伯文（Arabic）、敘利亞文（Syriac）以及馬爾代夫的塔安娜文（Thaana）均是從右向左（Right-to-Left，簡稱 RTL）書寫的；而拉丁字母、漢字、假名、希臘文則是從左向右（Left-to-Right，簡稱 LTR）書寫的。

### 2.1 雙向排版的微觀拓撲難題

假設在一篇由左向右書寫的英文論文中，引用了一句從右向左書寫的阿拉伯諺語：
- 如果這句阿拉伯諺語非常短，僅佔半行，排版引擎只需在英文行中劃出一塊局部區域，讓阿拉伯詞彙在此區域內從右向左排布；
- 但如果這句阿拉伯文字很長，**跨越了物理換行邊界**，問題立刻變得極度複雜：
  - 英文文本行從頁面的左邊距開始排布；
  - 阿拉伯文本在折行後，第一行的末尾應當停留在頁面的左邊緣還是右邊緣？第二行的起始詞應當靠在頁面的右邊距還是左邊距？
  - 遇到雙語夾雜的標點符號（句號、逗號）或括號（圓括號、方括號）時，標點究竟歸屬於外層英文字符流，還是歸屬於內層阿拉伯語流？

爲了給全球所有瀏覽器、文本編輯器與排版引擎提供唯一無歧義的排版標準，Unicode 聯盟制定了著名的 **Unicode 標準附錄第 9 號規範（UAX #9: Unicode Bidirectional Algorithm）**。

### 2.2 19 種雙向字符類型全表

UAX #9 根據字符在排版中的自然書寫方向傾向，爲每一個 Unicode 碼位賦予了唯一的 `Bidi_Class` 屬性，共計 19 種類型：

| 大類劃分 | 屬性代碼 | 類型技術全稱 | 涵蓋的典型字符羣 |
| :---: | :---: | :--- | :--- |
| **強方向類型 (Strong)** | **L** | Left-to-Right | 拉丁字母、漢字、日文假名、韓文諺文、希臘字母、西裏爾字母 |
| | **R** | Right-to-Left | 希伯來字母及相關的純右向左輔音字母 |
| | **AL** | Right-to-Left Arabic | 阿拉伯字母、波斯字母、烏爾都字母及阿拉伯語專屬標點 |
| **弱方向類型 (Weak)** | **EN** | European Number | 歐洲數字（ASCII 數字 `0`–`9`） |
| | **ES** | European Number Separator | 歐洲數字分隔符（正號 `+`、負號 `-`） |
| | **ET** | European Number Terminator | 歐洲數字終止符（百分號 `%`、貨幣符號 `$`, `€`, `¥`） |
| | **AN** | Arabic Number | 阿拉伯-印度數字（`٠`–`٩`） |
| | **CS** | Common Number Separator | 通用數字分隔符（小數點 `.`、千分位逗號 `,`、時間冒號 `:`） |
| | **NSM** | Nonspacing Mark | 非間距組合字符，繼承其所吸附的基底字符的方向屬性 |
| | **BN** | Boundary Neutral | 邊界中性符（零寬空格 `ZWSP`、不可見格式控制符） |
| **中性類型 (Neutral)** | **B** | Paragraph Separator | 段落分隔符（回車換行符 `\n`, `\r`） |
| | **S** | Segment Separator | 行內製表符（Tab `\t`） |
| | **WS** | Whitespace | 常規空格字符（ASCII Space） |
| | **ON** | Other Neutral | 其他中性標點與數學符號（`=`、`@`、引號等） |
| **顯示格式控制符** | **LRE** | Left-to-Right Embedding | 顯式開啓左向右嵌入層級（`U+202A`） |
| | **RLE** | Right-to-Left Embedding | 顯式開啓右向左嵌入層級（`U+202B`） |
| | **LRO** | Left-to-Right Override | 強制覆蓋所有後續字符爲左向右顯示（`U+202D`） |
| | **RLO** | Right-to-Left Override | 強制覆蓋所有後續字符爲右向左顯示（`U+202E`） |
| | **PDF** | Pop Directional Format | 終結最近一次顯式嵌入或覆蓋，彈出堆棧（`U+202C`） |

### 2.3 UAX #9 雙向算法的六大核心步驟

Bidi 算法的終極目標，是將文本在邏輯內存中的線性存儲序列（Logical Order），精確轉化爲在屏幕物理像素上的顯示排列序列（Visual Order）。整個算法被嚴謹地劃分爲 6 個階段：

```
+-------------------------------------------------------------+
| Step 1: 段落分割与基底方向确定 (P1 - P3)                      |
| * 扫描段落首个强方向字符，确立基底嵌入级别 (偶数 0 或奇数 1)      |
+------------------------------|------------------------------+
                               v
+-------------------------------------------------------------+
| Step 2: 显式格式控制符处理与方向堆栈维护 (X1 - X10)          |
| * 压入/弹出 LRE, RLE, LRO, RLO, PDF，确定每个字符的显式层级 |
+------------------------------|------------------------------+
                               v
+-------------------------------------------------------------+
| Step 3: 弱方向类型消解 (W1 - W7)                            |
| * 处理相邻数字、正负号、百分号、小数点，将弱类型提升为强类型 |
+------------------------------|------------------------------+
                               v
+-------------------------------------------------------------+
| Step 4: 中性类型与成对括号消解 (N1 - N2)                    |
| * 结合上下文双向边界，消解空格与标点；成对括号算法匹配方向    |
+------------------------------|------------------------------+
                               v
+-------------------------------------------------------------+
| Step 5: 隐式层级最终确定 (I1 - I2)                          |
| * 根据消解后的最终强类型，为每个字符赋予最终整数级别 Level  |
+------------------------------|------------------------------+
                               v
+-------------------------------------------------------------+
| Step 6: 视觉层级反转与字形镜像 (L1 - L4)                    |
| * 从最高级别到最低奇数级别递归反转子串；翻转成对镜像字符      |
+-------------------------------------------------------------+
```

1. **第一步：段落劃分與基底層級判定（Paragraph Level）**：
   - 將文本流以段落分隔符（`B`）切割爲獨立段落；
   - 掃描段落內出現的**第一個強方向字符（Strong Type）**：如果第一個強字符是 `L`，則本段的基底嵌入層級（Base Level）確定爲偶數 `0`（代表 LTR 主流）；如果首個強字符是 `R` 或 `AL`，則基底嵌入層級確定爲奇數 `1`（代表 RTL 主流）。
2. **第二步：顯式層級與堆棧推演（Explicit Levels）**：
   - 維護一個方向狀態棧，最大深度爲 125 層；
   - 遍歷字符流：遇到 `RLE` 則將當前層級提升至最近的更高奇數並壓棧；遇到 `LRE` 則提升至最近的更高偶數並壓棧；遇到 `PDF` 則出棧恢復上一層級。
3. **第三步：弱方向類型消解規則（Weak Types Resolution）**：
   - **W1 規則**：非間距組合符 `NSM` 轉換爲其前驅字符的類型；
   - **W2 規則**：緊隨阿拉伯強類型 `AL` 之後的歐洲數字 `EN` 轉換爲阿拉伯數字 `AN`；
   - **W4 規則**：夾在兩個同類型數字中間的數字分隔符（如 `12:30` 或 `1,000`）被轉換爲數字類型；
   - **W5 規則**：與歐洲數字直接相連的終止符（如 `100%` 或 `$50`）轉換爲歐洲數字 `EN`；
   - **W7 規則**：在 LTR 上下文中的歐洲數字 `EN` 最終被視同爲純左向右強類型 `L`。
4. **第四步：中性類型與括號匹配消解（Neutral Types & Paired Brackets）**：
   - **成對括號算法（Bidi Bracket Algorithm）**：檢查中性字符中的開閉括號對（如 `(` 與 `)`）。如果括號內部包含的內容屬於強方向，則將這一對括號的顯示方向調整爲與括號內強內容一致；
   - **N1/N2 規則**：夾在兩個相同強類型之間的中性符（如空格、連字符）轉變爲該強類型；否則退化爲當前段落的基底方向。
5. **第五步：隱式層級計算（Implicit Levels）**：
   - 經過弱類型與中性類型消解後，每個字符都獲得了最終的確定方向；
   - 根據字符類型與其所處層級的奇偶性，執行細微的層級加成（+1 或 +2），使每個字符分配到一個精確的整數**顯示層級（Resolved Embedding Level）**。
6. **第六步：視覺重排與鏡像翻轉（Reordering & Mirroring）**：
   - 找出整個段落中出現的最大層級數 $M$；
   - 從最大層級 $M$ 開始，向下循環遞減至段落內的最低奇數層級：在每一次循環中，找出所有連續層級大於或等於當前層級的字符子串，**將其整體順序進行鏡像反轉（Reverse）**！
   - **字形鏡像映射（Glyph Mirroring）**：在所有被判定爲奇數層級（RTL 區域）的字符中，檢索 Unicode 數據庫的 `BidiMirroring.txt` 文件。如果該字符存在鏡像對應項（例如開括號 `(` 必須翻轉爲閉括號 `)`），則通知排版引擎調用其在水平方向翻轉後的鏡像字形！

## 3. 東亞文字體系（East Asian Scripts）

東亞文字體系在世界文字史上獨樹一幟。由中國創造的漢字不僅承載了數千年的華夏文明，更在漫長的歷史交流中深度融入了日本、朝鮮半島與越南的語言文化，形成了舉世聞名的**漢字文化圈（Sinosphere）**。

### 3.1 中日韓統一表意文字（CJK Unified Ideographs）

在計算機字符編碼史上，漢字的處理曾經是一場曠日持久的技術紛爭：
- 中國大陸制定了 GB 2312、GB 12345、GBK 及後來的強制性國家標準 GB 18030；
- 中國臺灣制定了五大碼（Big5）與 CNS 11643；
- 日本製定了 JIS X 0208 與 JIS X 0213；
- 韓國製定了 KS X 1001 與 KS X 1002。

各個國家和地區在 20 世紀各自對數萬個漢字進行了彼此衝突的區位碼劃分，導致跨區域文檔交流時產生極其嚴重的“亂碼（Mojibake）”現象。

```
+-------------------------------------------------------------+
|                Unicode Han Unification Rules                |
|                                                             |
|   1. Source Separation Rule (源语素分离规则):                |
|      If two ideographs are distinguished in any primary     |
|      source standard (e.g. GB 2312 or JIS X 0208), they     |
|      MUST remain separated in Unicode (NO UNIFICATION).     |
|                                                             |
|   2. Cognate Analysis (同源认知分析):                       |
|      If two glyphs share historical etymology and abstract  |
|      topological structure, they map to the same codepoint. |
|                                                             |
|   3. Abstract Shape vs. Design Variation:                   |
|      Font designer differences in stroke slant / serif do   |
|      NOT justify creating new Unicode characters.           |
+-------------------------------------------------------------+
```

爲了徹底解決這一歷史遺留問題，中日韓三國專家與 Unicode 聯盟聯合成立了中日韓聯合研究組（JRG，後演進爲表意文字工作組 IRG），確立了著名的 **漢字統合原則（Han Unification）**：
1. **源語素分離規則（Source Separation Rule）**：這是一條神聖不可侵犯的鐵律——如果在任何一個創始源標準（如 GB 2312 或 JIS X 0208）中已經將兩個字分別賦予了兩個獨立編碼（即便它們在語言學上是完全同一字的繁簡變體），Unicode 就必須嚴格保留這兩個獨立編碼，絕不強行合併，以保證現有海量舊式數據庫能夠與 Unicode 實行 100% 無損往返轉換（Round-trip Compatibility）。
2. **抽象骨架同源判定（Cognate Analysis）**：如果來自不同國家的兩個字形，在歷史造字源頭上屬於同一個字，且兩者的抽象拓撲筆畫結構（部首、筆畫構件、相對空間排布）完全吻合，則被統一判定爲同一個 Unicode 碼位。
3. **字形設計變體分離（Design Variation）**：字體的地域性設計習慣（例如中文字體習慣將特定偏旁的豎畫寫直，而日文字體習慣帶鉤）被認定爲**字體設計風格差異（Font-level Glyphic Variation）**，而非編碼維度的不同字符，應通過 OpenType 的地域語言特性（如 `locl`）切換字形，而無需分配新的碼位。

### 3.2 表意文字描述字符（IDC, Ideographic Description Characters）

儘管 Unicode 目前收錄的漢字總數已突破 9 萬大關（涵蓋 Ext-A 至 Ext-I 擴展區），但人類在古籍文獻、人名地名、歷史宗譜中依然會不斷髮現無法在現有字庫中檢索到的未編碼罕見字。

爲解決這一“字符集永遠滯後於古籍發現”的矛盾，Unicode 引入了一組極其精妙的算子——**表意文字描述字符（Ideographic Description Characters，簡稱 IDC，碼位區間 U+2FF0 至 U+2FFB）**：

| 碼位 | 字符形態 | 技術名稱 | 運算目數 | 構字拓撲語法說明 |
| :---: | :---: | :--- | :---: | :--- |
| `U+2FF0` | ⿰ | Left to Right | 二目 | 將後序兩個構件左右並列排布（如 `⿰木木` $\to$ 林） |
| `U+2FF1` | ⿱ | Above to Below | 二目 | 將後序兩個構件上下垂直疊放（如 `⿱木木` $\to$ 𣏯） |
| `U+2FF2` | ⿲ | Left to Middle and Right | 三目 | 將後序三個構件自左至右橫向均分（如 `⿲木木木` $\to$ 𣡗） |
| `U+2FF3` | ⿳ | Above to Middle and Below | 三目 | 將後序三個構件自上而下縱向均分（如 `⿳一八口` $\to$ 𠀤） |
| `U+2FF4` | ⿴ | Full Surround | 二目 | 外框全包圍內嵌構件（如 `⿴囗大` $\to$ 因） |
| `U+2FF5` | ⿵ | Surround from Above | 二目 | 三包圍：自上方及左右兩側下垂包圍（如 `⿵门日` $\to$ 間） |
| `U+2FF6` | ⿶ | Surround from Below | 二目 | 三包圍：自下方及左右兩側向上包圍（如 `⿶凵凶` $\to$ 幽） |
| `U+2FF7` | ⿷ | Surround from Left | 二目 | 三包圍：自左側向上及向右包圍（如 `⿷匚矢` $\to$ 醫） |
| `U+2FF8` | ⿸ | Surround from Upper Left | 二目 | 兩包圍：自左上角向下向右展開（如 `⿸广林` $\to$ 麻） |
| `U+2FF9` | ⿹ | Surround from Upper Right | 二目 | 兩包圍：自右上角向下向左展開（如 `⿹气米` $\to$ 氣） |
| `U+2FFA` | ⿺ | Surround from Lower Left | 二目 | 兩包圍：自左下角向上向右墊底（如 `⿺辶走` $\to$ 辵） |
| `U+2FFB` | ⿻ | Overlaid | 二目 | 兩個構件相互穿插十字交叉疊加（如 `⿻十口` $\to$ 申） |

IDC 採用嚴密的**前綴波蘭表達式（Prefix Polish Notation）**語法。藉助這組算子，排版軟件即使在遇到尚未編入標準的生僻漢字時，也可以通過純文本串（如 `⿰氵⿱艹⿵门日`）向讀者傳達該字的結構全貌，甚至由動態排版引擎解析並在運行時自動拼接渲染出該未知漢字的臨時輪廓。

### 3.3 字形描述語言（Character Description Language, CDL）

在 1980 年代，漢學專家湯姆·畢曉普（Tom Bishop）與文林研究所開發了一種基於 XML 的矢量漢字描述規範——**CDL（Character Description Language）**。

CDL 摒棄了將漢字視爲孤立閉合貝塞爾曲線的傳統思路，而是將漢字建立在一個標準的 **$128 \times 128$ 虛擬座標網格** 之上，通過構件（Components）與筆畫（Strokes）的層級引證進行參數化構建：

```xml
<cdl char="明">
  <component char="日" points="0,0 55,128" />
  <component char="月" points="65,0 128,128" />
</cdl>
```

#### CDL 30 種基礎筆畫系統
CDL 提煉出構成一切漢字的 30 種不可再分的原子筆畫（如橫 `h`、豎 `s`、撇 `p`、捺 `n`、折 `z`、鉤 `g`），每個原子筆畫在 XML 中均由起點、控制點與終點的離散座標直接參數化驅動。這一架構不僅將整個漢字庫的物理存儲體積壓縮了 90% 以上，更使得計算機能夠精確知曉漢字的真實書寫筆順，成爲漢字書法動態教學、智能字形拉伸與光學補償的絕佳工程載體。

## 4. 韓國諺文（Hangul）的數學構造模型

如果說漢字代表了表意文字演化的高峯，那麼朝鮮王朝第四代君主**世宗大王（King Sejong the Great）**於 1446 年頒佈《訓民正音》（*Hunminjeongeum*）所創制的**諺文（Hangul）**，則代表了人類文字設計史上無與倫比的嚴密數學理性與音素構字奇蹟。

```
+-------------------------------------------------------------+
|             Hangul Syllabic Block Architecture              |
|                                                             |
|   1. Initial Consonant (初声 Choseong / L) : 19 types       |
|      [ᄀ ᄁ ᄂ ᄃ ᄄ ᄅ ᄆ ㅂ ᄈ ㅅ ᄊ ㅇ ㅈ ㅉ ㅊ ㅋ ㅌ ㅍ ㅎ] |
|                                                             |
|   2. Medial Vowel (中声 Jungseong / V) : 21 types           |
|      [ㅏ ㅐ ㅑ ㅒ ㅓ ㅔ ㅕ ㅖ ㅗ ㅘ ㅙ ㅚ ㅛ ㅜ ㅝ ㅞ ㅟ ㅠ ㅡ ㅢ ㅣ] |
|                                                             |
|   3. Final Consonant (终声 Jongseong / T) : 28 states       |
|      [None, ᆨ, ᆩ, ᆪ, ᆫ, ᆬ, ᆭ, ᆮ, ᆯ, ᆰ, ᆱ, ᆲ, ᆳ, ᆴ, ᆵ, ᆶ,  |
|       ᆷ, ᆸ, ᆹ, ᆺ, ᆻ, ᆼ, ᆽ, ᆾ, ㅋ, ㅌ, ㅍ, ㅎ]           |
|                                                             |
|   Total Permutations: 19 * 21 * 28 = 11,172 Syllable Blocks |
+-------------------------------------------------------------+
```

### 4.1 字母（Jamo）分類與語音發生學

諺文的基本構字單元稱爲**字母（Jamo，자모）**：
- **輔音字母的生理仿生設計**：世宗大王及其學者在設計輔音時，直接模擬了人類發音器官的物理幾何形態——舌根閉合喉部模擬爲 `ㄱ`，舌尖抵住上顎模擬爲 `ㄴ`，嘴脣閉合形態模擬爲 `ㅁ`，牙齒形態模擬爲 `ㅅ`，喉頭形態模擬爲 `ㅇ`；
- **元音字母的哲學宇宙觀**：元音的設計源自東方傳統的“三才”哲學——圓點 `·` 代表天（Heaven），橫線 `ㅡ` 代表地（Earth），豎線 `ㅣ` 代表人（Man）。

### 4.2 諺文音節塊的數學組合全景

一個完整的韓語音節塊必須包含一個**初聲輔音（Initial, L）**和一個**中聲元音（Medial, V）**，並可選包含一個**終聲輔音（Final, T / 支音）**：
- 初聲數量：$L_{\text{count}} = 19$；
- 中聲數量：$V_{\text{count}} = 21$；
- 終聲數量：$T_{\text{count}} = 28$（包含“無終聲”狀態）。

因此，所有可能構成的現代標準韓語音節總數精確等於：
$$N = 19 \times 21 \times 28 = 11,172 \ \text{个音节}$$

### 4.3 編解碼數學投影方程

Unicode 在 `U+AC00` 至 `U+D7A3` 的連續區間內，以極其嚴苛的代數順序完整收錄了這全部 11,172 個預合成音節塊。任何一個韓語音節塊的碼位 $S$ 與其組成字母 Jamo 索引之間，存在着嚴格的一一對應解析算術方程：

設基礎常數：
$$\text{SBase} = \text{0xAC00}$$
$$L_{\text{count}} = 19, \quad V_{\text{count}} = 21, \quad T_{\text{count}} = 28$$
$$N_{\text{count}} = V_{\text{count}} \times T_{\text{count}} = 21 \times 28 = 588$$

#### 1. 正向合成計算公式（Composition）
給定初聲索引 $L_{\text{index}} \in [0, 18]$、中聲索引 $V_{\text{index}} \in [0, 20]$ 和終聲索引 $T_{\text{index}} \in [0, 27]$，其預合成音節的絕對 Unicode 標量值 $S$ 爲：

$$S = \text{SBase} + (L_{\text{index}} \times 588) + (V_{\text{index}} \times 28) + T_{\text{index}}$$

#### 2. 反向算術分解算法（Decomposition）
給定任意一個處於預合成區間的韓語音節碼位 $S$（$\text{0xAC00} \le S \le \text{0xD7A3}$），計算其音節內偏移量：
$$S_{\text{index}} = S - \text{SBase}$$

則其各組成 Jamo 的精確索引可通過純整數除法與取模運算瞬間得出：
$$L_{\text{index}} = \lfloor S_{\text{index}} / 588 \rfloor$$
$$V_{\text{index}} = \lfloor (S_{\text{index}} \bmod 588) / 28 \rfloor$$
$$T_{\text{index}} = S_{\text{index}} \bmod 28$$

#### 3. 生產級 Python 算法實現
```python
def decompose_hangul(codepoint: int):
    # 将预合成韩语音节码位无损分解为 (L, V, T) Jamo 索引
    SBase = 0xAC00
    LBase = 0x1100
    VBase = 0x1161
    TBase = 0x11A7
    
    if not (0xAC00 <= codepoint <= 0xD7A3):
        return None  # 非预合成音节
        
    s_index = codepoint - SBase
    l_index = s_index // 588
    v_index = (s_index % 588) // 28
    t_index = s_index % 28
    
    l_char = chr(LBase + l_index)
    v_char = chr(VBase + v_index)
    t_char = chr(TBase + t_index) if t_index > 0 else ""
    
    return l_char, v_char, t_char

# 测试：分解 "한" (U+D55C)
# 预期：L=ㅎ (U+1112), V=ㅏ (U+1161), T=ㄴ (U+1102)
print(decompose_hangul(0xD55C))
```

這種極致的數學對稱性，使得現代計算機系統無需維護任何龐大的外部查找字典，僅憑几條基礎 CPU 算術移位指令，即可在極微秒內完成韓語音節的無損正反向轉碼與拼寫檢查，堪稱計算機文字編碼學中最優雅的工程傑作之一。
