# 第三章 · Unicode 字符的屬性體系
### Chapter 3: Properties of Unicode characters

**著者：雅尼斯·哈拉蘭博斯（Yannis Haralambous, Ph.D.）**  
*選自《Fonts & Encodings》第 95–126 頁*  
*譯者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

---

我們在本章中所關注的，是 Unicode 爲每一個字符所提供的全部屬性信息（Information）。依照我們此前所確立的嚴格定義，**字符**（Character）是對某一特定字形類（Class of Glyphs）的抽象描述。而在該類所有的具體字形中，會選出一個代表性字形（Representative Glyph）展示在 Unicode 標準的代碼圖表之中——無論是在其厚重的紙質實體卷冊 [335] 中，還是在互聯網上發佈的官方 PDF 文檔 [334] 內。

Unicode 將一個字符的**身份**（Identity）定義爲其抽象描述（Description）與代表性字形的結合。另一方面，一個字符的**語義**（Semantics）則是由其字符身份連同其**規範屬性**（Normative Properties）所共同賦予的。

這便引出了我們本章的核心論題：**字符屬性**（Character Properties）。這些屬性是歷經漫長歲月沉澱、爲每一個字符系統收集建立的數據資產，其目的在於幫助我們更加精準高效地運用 Unicode。例如，字符最基礎的規範屬性之一便是其**通用分類**（General Category）。在諸多的可能分類中，包含着諸如“標點符號”（Punctuation）這一範疇。如此一來，軟件開發者便能輕而易舉地獲知某個書寫系統中的哪些字符屬於標點符號——從而在進行文本排序（Sorting）時自動忽略這些符號——而完全無需預先掌握該書寫系統本身的複雜語言學細節。

另一個屬性（儘管在此範例中它屬於非強制的描述性屬性，因而存在更多的語境模糊性）則是**大寫/小寫對應關係**（Uppercase/Lowercase Correspondence）。Unicode 爲此提供了完備的對應表，軟件可以直接調用這些規則將字符串從一種大小寫形式轉換爲另一種形式（前提是該書寫系統確實存在大小寫概念）。

當然，無論何種文本操作（無論是文本排序還是大小寫轉換），都絕不可能做到百分之百的純機械自動化。正如所有自然語言處理（NLP）領域的客觀規律一樣，由於語言本身及其語法結構所固有的歧義性，處理過程中永遠伴隨着一定程度的不確定性。然而，字符屬性依然使得文本處理的絕大部分工序得以實現高度自動化；開發者所需要做的，只是在界面與機制上賦予用戶糾正那些因規則普適化套用而偶然產生的極少數偏差的權利。

那麼，究竟存在哪些字符屬性？我們又該在何處查閱並獲取它們？本章接下來的全部篇幅便將完整解答這兩個關鍵問題。

## 基礎屬性（Basic Properties）

### 字符名稱（Name）

字符的官方名稱（Name），正是我們此前所稱的“字符描述”（Description）。在 Unicode 編碼空間內，依照字符編碼位置排列的官方英文名稱列表公佈於以下核心數據文件之中：

```text
http://www.unicode.org/Public/UNIDATA/UnicodeData.txt
```

該文件以極其緊湊的計算機友好格式容納了浩瀚的字符數據：每一行代表一個字符，由分號（Semicolon `;`）分隔爲整整十五個文本字段（Fields）。以下摘錄該文件開篇的若干典型數據行：

```text
0020;SPACE;Zs;0;WS;;;;;N;;;;;
0021;EXCLAMATION MARK;Po;0;ON;;;;;N;;;;;
0022;QUOTATION MARK;Po;0;ON;;;;;N;;;;;
0023;NUMBER SIGN;Po;0;ET;;;;;N;;;;;
0024;DOLLAR SIGN;Sc;0;ET;;;;;N;;;;;
```

在這套數據結構中，前兩個字段分別代表字符的編碼位置（Position，亦稱**碼點** `Code Point`）與字符名稱（Name）。在計算機索引中，這兩個字段編號分別爲第 0 號與第 1 號字段（遵循從 0 開始計數的慣例）。關於後續字段的詳細語義，我們將在後文中逐一剖析。

字符名稱的設立絕非僅供人類肉眼閱讀查閱；現代編程語言（Programming Languages）同樣能夠直接理解並解析它們。例如在 Perl 語言中，若要引用切羅基文（Cherokee）字母 ‘Ꭰ’，程序員可以直接編寫 `\N{CHEROKEE LETTER A}`，這與直接使用其十六進制碼點表達 `\x{13A0}` 在語義上是完全等價的。

### 區塊與書寫系統（Block and Script）

這些屬性規定了全體字符在編碼空間中的宏觀宏構分佈，主要依據字符所歸屬的書寫系統（Script）或它們在功能上的同質性來進行區塊（Block）切分。由此，我們不僅擁有亞美尼亞文字符區塊（Armenian），亦擁有象形圖形符號區塊（Dingbats）、專用控制代碼區塊（Specials）等等。

所有官方分配的連續區塊範圍完整列載於核心文件 `Blocks.txt` 之中。以下爲該文件的局部摘錄：

```text
0000..007F; Basic Latin
0080..00FF; Latin-1 Supplement
0100..017F; Latin Extended-A
0180..024F; Latin Extended-B
...
10450..1047F; Shavian
10480..104AF; Osmanya
```

在支持高級正則表達式（Regular Expressions）的編程環境中，區塊屬性賦予了開發者強大的文本匹配能力。例如，正則表達式 `/\p{InShavian}/` 能夠精準匹配落在蕭伯納字母（Shavian）區塊範圍內的任意字符。

然而，我們必須在此釐清一個極爲關鍵的概念分野：**區塊屬性**（Block Property）與**書寫系統屬性**（Script Property）有着本質的不同。一個字符所處物理區塊的名稱，並不必然代表它所歸屬的真實書寫系統。例如，希臘字母 ‘͵’（希臘文下角點，U+0375 `GREEK LOWER NUMERAL SIGN`）物理上位於希臘字母與科普特文字塊中，但它同時具有獨特的標點或數字修飾屬性；而拉丁目母在全角/半角形式塊（Halfwidth and Fullwidth Forms）中亦有分佈。若我們要根據字符實際所屬的文字系統進行匹配，應當使用書寫系統屬性（如 Perl 5.8+ 中的 `\p{IsCherokee}` 或 `\p{Script=Greek}`），該屬性記錄於專門的 `Scripts.txt` 文件之中。

### 誕生版本與紀年（Age）

每一字符何時被正式接納並編入 Unicode 國際標準，由**紀年屬性**（Age Property）嚴格記錄，具體記載於 `Age.txt` 數據庫內。由於 Unicode 標準具有神聖不可侵犯的**前向兼容性承諾**（Forward Compatibility Guarantee）——即任何一旦被編碼分配的字符永不刪除、碼點永不挪用——因此字符的生命週期只有“誕生”，而無“消亡”。

該屬性記錄了接納該字符的首個標準版本號：`1.1`、`2.0`、`2.1`、`3.0`、`3.1`、`3.2`、`4.0`、`4.1`、`5.0` 等。當軟件需要在異構系統之間交換文本、或需要向下兼容舊版 Unicode 處理引擎時，紀年屬性便成爲了判定目標系統是否具備該字符解析能力的基準判據。

### 通用分類（General Category）

在 `UnicodeData.txt` 的全部十五個字段中，第 2 號字段承載着至關重要的**通用分類**（General Category，簡記爲 `gc`）。這是一項極其重要的規範屬性（Normative Property），它爲每一個字符賦予了一個由兩個英文字母構成的分類代碼。

首字母代表該字符的**頂級分類**（Major Class）：
- `L`：字母（Letter）
- `M`：修飾標誌 / 附加符號（Mark）
- `N`：數字（Number）
- `P`：標點符號（Punctuation）
- `S`：符號（Symbol）
- `Z`：分隔符（Separator）
- `C`：其他 / 控制（Other / Control）

次字母則指示該頂級範疇下的具體子分類。以下我們對各大子類別進行細緻解析：

#### 字母（Letters）

- **`Lu`（大寫字母，Uppercase Letter）**：如標準的拉丁大寫字母 ‘A’、希臘大寫字母 ‘$\Omega$’、西里爾大寫字母 ‘$\Phi$’ 等。
- **`Ll`（小寫字母，Lowercase Letter）**：如小寫字母 ‘a’、‘$\omega$’、‘$\phi$’ 等。
- **`Lt`（詞首大寫 / 標題字母，Titlecase Letter）**：這是一個初見時常令非語言學專業學者感到困惑的獨特類別。某些語言在書寫複合二合字母（Digraphs）時，若該詞處於句首或標題位置，傳統習慣是僅將二合字母的前半部分大寫，而保持後半部分爲小寫。
  最典型的例證見於克羅地亞語（使用拉丁字母）與塞爾維亞語（使用西裏爾字母）的雙向轉寫體系。例如，西裏爾字母 ‘Џ’（發音類似 judge 中的 j）在克羅地亞拉丁字母中寫作 ‘D’ 與 ‘ž’ 的組合。在 Unicode 中，爲了確保與南斯拉夫國家標準編碼的單字符一對一轉換，該二合字母被賦予了獨立的單字符碼點：
  1. 全大寫形式（`Lu`）：`U+01C4` ‘Ǆ’（`LATIN CAPITAL LETTER DZ WITH CARON`）
  2. 詞首大寫形式（`Lt`）：`U+01C5` ‘ǅ’（`LATIN CAPITAL LETTER D WITH SMALL LETTER Z WITH CARON`）
  3. 全小寫形式（`Ll`）：`U+01C6` ‘ǆ’（`LATIN SMALL LETTER DZ WITH CARON`）
  類似的二合字符還包括 ‘Ǉ / ǈ / ǉ’（`LJ`）與 ‘Ǌ / ǋ / ǌ’（`NJ`）。此外，在多調希臘文（Polytonic Greek）中，帶有下寫字標（Iota Subscript）的大寫字母若以旁寫字標（Prosgegrammeni）排印在標題詞首時（如 ‘$\Omega\iota$’ 融合成單字符），亦歸入 `Lt` 分類。
- **`Lm`（修飾字母，Modifier Letter）**：獨立佔據水平進幅間距、但在語言學功能上用於修飾前驅或後繼字母發音的字符，如上標音標字符、聲調修飾字母（Tone Letters）等。
- **`Lo`（其他字母，Other Letter）**：涵蓋所有在文字系統中不具備大小寫二元區分（Casing distinction）特徵的字母與表意文字。漢字（CJK Ideographs）、希伯來字母（如 Alef ‘א’）、阿拉伯字母、泰文字母等統統歸入此類。

#### 附加符號（Diacritical Marks / Marks）

- **`Mn`（非進幅符號，Nonspacing Mark）**：在渲染時不產生獨立的水平進幅寬度（Advance Width 均爲 0），而是懸浮附着於基底字符（Base Character）之上、之下或內部的變音符號。例如拉丁文的銳音符（Acute Accent `U+0301`）、希伯來文的元音點（Niqqud）等。
- **`Mc`（進幅結合符號，Spacing Combining Mark）**：與基底字符結合成一個語音單元，但自身在排版上佔據獨立視覺寬度的附加標記。在印度系文字（Indic Scripts，如天城文、孟加拉文）的元音附標中極其普遍。
- **`Me`（包圍結合符號，Enclosing Mark）**：在視覺上將基底字符完全圈入其內部的符號，如結合用圓圈（Combining Enclosing Circle `U+20DD`）或方框。

#### 數字（Numbers）

- **`Nd`（十進制數字，Decimal Digit Number）**：遵循標準十進制進位制、且完整具備 0 至 9 連續數字序列的書寫字符。包括普通的 ASCII 數字 `0..9`，以及天城文數字 `०..९`、阿拉伯-印度數字等。
- **`Nl`（字母數字，Letter Number）**：由字母形態演變而來、或在功能上充當數字的特殊符號，如古羅馬數字符號（Roman Numerals `Ⅰ, Ⅱ, Ⅲ...`）、愛琴海數字符號等。
- **`No`（其他數字，Other Number）**：不屬於上述兩類的各類散亂數字符號，如普通分數符（½、¼）、帶圈數字（`①, ②`）、上標數字等。

#### 標點符號（Punctuation）

- **`Pc`（連接標點，Connector Punctuation）**：如用於連接兩個詞素的下劃線 ‘_’（Underscore）。
- **`Pd`（破折號與連字符，Dash Punctuation）**：包括連接號（Hyphen ‘-’）、半字線（En Dash ‘–’）、全字線（Em Dash ‘—’）等。
- **`Ps`（成對標點開啓端，Open / Start Punctuation）**：所有開括號，如左圓括號 ‘(’、左方括號 ‘[’、左花括號 ‘{’ 等。
- **`Pe`（成對標點閉合端，Close Punctuation）**：所有閉括號，如右圓括號 ‘)’、右方括號 ‘]’、右花括號 ‘}’ 等。
- **`Pi`（起始引號，Initial Quote Punctuation）**：如左雙引號 ‘“’，在某些語言排版中亦指特定開引號。
- **`Pf`（終結引號，Final Quote Punctuation）**：如右雙引號 ‘”’，或法文書名號的閉合端。
- **`Po`（其他標點，Other Punctuation）**：句號、逗號、感嘆號、問號、分號、冒號等常規標點。

#### 符號（Symbols）

- **`Sm`（數學符號，Math Symbol）**：如加號 ‘+’、等號 ‘=’、小於號 ‘<’、積分號 ‘$\int$’ 等。
- **`Sc`（貨幣符號，Currency Symbol）**：如美元符 `$`、歐元符 `€`、英鎊符 `£`、日元/人民幣符 `¥` 等。
- **`Sk`（修飾符號，Modifier Symbol）**：獨立佔據空間、但表示某種修飾屬性的符號，如單獨成字的聲音符（U+005E 脫字符 ‘^’、U+0060 重音符 ‘`’）。
- **`So`（其他符號，Other Symbol）**：各類雜項圖案符號，如撲克牌花色、麻將牌面、國際象棋棋子、商標符 ‘™’、版權符 ‘©’ 等。

#### 分隔符（Separators）

- **`Zs`（空白分隔符，Space Separator）**：標準空格（ASCII Space）、不換行空格（NBSP）、細空格（Thin Space）、全角空格（Em Space）等。
- **`Zl`（行分隔符，Line Separator）**：專門用於無條件強制換行但不斷段的代碼 `U+2028`。
- **`Zp`（段落分隔符，Paragraph Separator）**：專門用於強制分段的代碼 `U+2029`。

#### 其餘特殊類別（The Remaining Categories）

- **`Cc`（控制字符，Control Character）**：繼承自 ASCII 與 ISO 8859 系列的 C0 與 C1 控制字符集（`0x00..0x1F` 與 `0x7F..0x9F`），如換行（LF）、回車（CR）、製表符（TAB）。
- **`Cf`（格式控制字符，Format Character）**：對排版、雙向文本流動或字形連筆產生隱式控制但本身完全透明無視覺印跡的代碼。典型代表包括：零寬連字符（ZWJ, `U+200D`）、零寬不連字符（ZWNJ, `U+200C`）、從左至右標記（LRM, `U+200E`）、從右至左標記（RLM, `U+200F`）、字節順序標記（BOM, `U+FEFF`），以及用於高階數學公式排版的不可見操作符（Invisible Operators，如 `U+2061` 函數應用符、`U+2062` 不可見乘號、`U+2063` 不可見分隔符）。
- **`Cs`（代理對碼點，Surrogate）**：保留用於 UTF-16 編碼機制的特殊碼位（`0xD800..0xDFFF`）。它們在真實世界中永遠不代表獨立字符。
- **`Co`（專用私用區字符，Private Use）**：供各組織、字體設計師或軟件廠商私下約定分配的保留區域（BMP 中的 `0xE000..0xF8FF`，以及平面 15 與 16 全域）。
- **`Cn`（未分配碼點，Unassigned）**：尚未被 Unicode 標準分配任何字符的純粹空置碼位。

## 其他通用屬性（Other General Properties）

除了 `UnicodeData.txt` 主文件所包含的基礎屬性外，Unicode 聯合會（Unicode Consortium）還在附加屬性列表文件 `PropList.txt` 以及一系列專門派生文件（Derived Property Files）中維護了極其龐大的細分屬性體系。

### 空白符（Spaces / White_Space）
屬性 `White_Space` 涵蓋了所有視覺呈現爲空白或導致光標發生進幅位移的字符。除了分類爲 `Zs` 的各類空格外，該集合還納入了控制字符中的水平製表符（HT, `0x0009`）、換行符（LF, `0x000A`）、垂直製表符（VT, `0x000B`）、換頁符（FF, `0x000C`）、回車符（CR, `0x000D`）以及行/段分隔符。

### 字母性（Alphabetic Characters）
屬性 `Alphabetic` 包含所有屬於 `L` 類別的字符，以及具有字母發音衍生功能的若干特殊附加符號（`Mn`）。這對於編程語言詞法分析器（Lexer）判定標識符的合法拼寫範圍至關重要。

### 非字符（Noncharacters）
在 Unicode 浩瀚的 1,114,112 個碼位中，有整整 66 個碼位被永久性地宣告爲**非字符**（Noncharacters）。它們絕不能用於在開放系統間交換文本數據，而僅供系統內部作爲哨兵值（Sentinel Values）或魔數（Magic Numbers）使用。它們包括：
1. 每一個平面的最後兩個碼點：`0xFFFE` 與 `0xFFFF`，`0x1FFFE` 與 `0x1FFFF`，直至 `0x10FFFE` 與 `0x10FFFF`（共 34 個）；
2. 基本多語言平面（BMP）中的一段連續保留區：`0xFDD0..0xFDEF`（共 32 個）。

### 默認可忽略字符（Default_Ignorable_Code_Point）
這一屬性標記了一批在舊版軟件或未實現對應渲染特效的排版引擎中，應當被安全“靜默吞沒”而不引發方框亂碼（Tofu）的特殊格式字符。例如軟連字符（Soft Hyphen `0x00AD`）、零寬字符、以及未分配的格式控制碼。

### 廢棄字符（Deprecated Characters）
儘管 Unicode 恪守永不刪除字符的鐵律，但對於早期標準因認知侷限或歷史失誤而錯誤收錄的冗餘字符，聯合會會將其打上**已廢棄**（Deprecated）標記，強烈建議現代系統停止使用，並以正規的字符組合序列予以取代。例如過時的交替格式字符羣（`0x206A..0x206F`）。

### 邏輯順序例外（Logical-Order Exceptions）
Unicode 文本的絕對核心準則是**邏輯存儲順序**（Logical Order）——即字符必須嚴格按照人們發音或閱讀的時間先後順序存儲於內存中。然而，全球數千種書寫系統中存在着極其罕見的例外：泰文（Thai）與老撾文（Lao）的某些元音符號在視覺排印時，必須繪製在聲母輔音字母的左側（物理前置）。
由於當地傳統打字機與遺留編碼早已習慣先鍵入左側元音、再鍵入輔音，Unicode 爲維持與泰國國家標準 TIS 620 的完全兼容，被迫對這五個泰文字母（`0x0E40..0x0E44`）與老撾文字母做出了妥協。它們被賦予了 `Logical_Order_Exception` 屬性，排版渲染引擎在執行雙向重排或注音解析時，必須對此類字符執行反向預處理。

### 軟點字母（Soft-Dotted Letters）
在拉丁字母 ‘i’ 與 ‘j’ 的小寫形態中，字頭上天生具有一顆小圓點（Tittle / Dot）。當在這兩個字母上方疊加其他變音符（如重音符、揚抑符或長音符）時，傳統排版習慣通常要求隱去其原本的小圓點（即變爲無點基底），以避免雙重符號發生難看的縱向重疊與墨團擠壓。然而，在立陶宛語（Lithuanian）等特定語言的正字法中，重音符必須疊加在原有圓點之上保留顯現！
擁有 `Soft_Dotted` 屬性的字符（包括加羅林長 s ‘ſ’ 在某些字體中的變體、以及西里爾小寫字母 ‘і’）提示着智能排版與字體設計引擎：其點狀結構具有特殊的形態消失或共存邏輯。

### 數學、引號與標點專有屬性
- **`Math`**：收納全體數學符號、數學字母數字變體（如黑板粗體 $\mathbb{R}$、花體 $\mathcal{F}$ 等）。
- **`Quotation_Mark`**：統一索引世界各種書寫系統所使用的全部形制配對或單體引號。
- **`Dash`** 與 **`Hyphen`**：對各類連字符、減號、長破折號進行精確的功能拓撲劃分。
- **`Terminal_Punctuation`**：標記句末終結標點（如句號、歎號、阿拉伯文分句符），用於段落拆分與分句算法。
- **`Diacritic`**：標記所有具有變音功能的附加或獨立符號。
- **`Extender`**：標記那些在視覺上將前驅字符在水平方向予以幾何“拉長”的特殊文字成分，如阿拉伯文的延伸字線（Kashida / Tatweel `U+0640`）、平假名與片假名的長音符（`U+30FC`）。
- **`Join_Control`**：僅由兩個最具魔力的格式字符獨佔：零寬連字符（ZWJ `U+200D`）與零寬不連字符（ZWNJ `U+200C`）。

### Unicode 1.0 舊名稱與 ISO 註釋
在 `UnicodeData.txt` 的第 10 與 11 號字段中，保留了歷史沿革數據：
- **第 10 字段**：Unicode 1.0 版最初賦予該字符的舊名稱。這在早期標準因更名而產生歷史文檔斷層時提供了可貴的追溯依據。
- **第 11 字段**：國際標準化組織 ISO/IEC 10646 標準對該字符所附帶的正式官方註釋文本。

## 大小寫相關屬性（Properties That Pertain to Case）

對於擁有大小寫雙軌制的字母文字（如拉丁文、希臘文、西里爾文、亞美尼亞文以及格魯吉亞語的歷史變體），大小寫的精確轉換與等價判定構成了計算語言學中最古老卻又暗藏無數暗礁的課題。

### 簡單大小寫映射（Simple Case Mappings）
記錄於 `UnicodeData.txt` 的最後三個字段：
- 第 12 字段：簡單大寫映射（Simple Uppercase Mapping）
- 第 13 字段：簡單小寫映射（Simple Lowercase Mapping）
- 第 14 字段：簡單詞首大寫映射（Simple Titlecase Mapping）

所謂“簡單”，意味着其映射關係被嚴格限制爲**單一碼點到單一碼點**（1:1）的對稱替換。例如小寫字母 ‘a’（`U+0061`）的第 12 字段填入大寫 ‘A’（`U+0041`）。

### 特殊大小寫映射（Special Case Mappings）
然而，自然語言的真實演化絕非單碼點映射所能完全涵蓋。爲此，Unicode 創立了專門的高階數據庫文件 `SpecialCasing.txt`。該文件解決了三大類極端複雜的語言學難題：

1. **一對多擴展映射（1:Many Mappings）**：
   德語小寫銳 S 字母 ‘ß’（Eszett, `U+00DF`）在傳統德語正字法中完全不存在原生大寫形態（直到 2017 年官方纔有限度採納大寫 ẞ `U+1E9E`）。在傳統全大寫排版中，‘ß’ 必須無條件展開爲兩個獨立的英文字母大寫：“SS”。此外，諸多帶有複合變音符的多調希臘字母在轉爲全大寫時，其下寫字標必須被拆卸解構並展開爲普通大寫 Iota（如 ‘ᾂ’ 展開爲三個大寫字符）。
2. **上下文敏感映射（Context-Dependent Mappings）**：
   在希臘文正字法中，大寫字母 Sigma ‘$\Sigma$’ 轉爲小寫時具有高度的語境依存性：若該字母處於單詞的中間位置，其小寫形態爲普通的 ‘$\sigma$’；然而，若該字母恰好處於**單詞的終末末尾**，它必須自動蛻變爲專有的詞尾 Sigma ‘$\varsigma$’（`U+03C2`）。任何合格的現代文本引擎都必須依據詞邊界上下文狀態機來實現這一精準轉換。
3. **語言區域敏感映射（Locale-Dependent Mappings）**：
   最爲經典的案例莫過於土耳其語（Turkish）與阿塞拜疆語（Azeri）的正字法悖論。在英語與通用拉丁語境中：
   - ‘i’ 的大寫是 ‘I’；‘I’ 的小寫是 ‘i’。
   然而在土耳其語中，存在着兩對彼此完全獨立的平行的元音字母：
   - **帶點組**：小寫 ‘i’（帶點）對應大寫 ‘İ’（帶點大寫，`U+0130`）；
   - **無點組**：小寫 ‘ı’（無點小寫，`U+0131`）對應大寫 ‘I’（無點大寫）。
   如果一個通用的英文大小寫算法在土耳其語環境下粗暴地將小寫 ‘i’ 轉換爲普通的無點大寫 ‘I’，就會徹底改變單詞的詞義甚至造成嚴重誤解！`SpecialCasing.txt` 通過引入 ISO 639 語言標籤（如 `tr`、`az`）精確隔離了此類區域特化規則。

### 大小寫摺疊（Case Folding）
當計算機需要判斷用戶輸入的搜索詞或數據庫查詢是否與目標字符串匹配時，我們往往期望實現“忽略大小寫”（Case-Insensitive Match）。

簡單的做法是將兩者統統轉爲大寫或統統轉爲小寫後再逐字節比對。然而，由於德語 ‘ß’ 與 “SS” 的單雙字符不對稱、以及希臘文詞首詞中 ‘$\sigma$’ 與詞尾 ‘$\varsigma$’ 的異構問題，單向轉換極易發生假陰性失配。

Unicode 爲此專門設立了獨立的規範文件 `CaseFolding.txt`，制定了一套中立的**大小寫摺疊**（Case Folding）算法。該算法爲每個字符確立了摺疊狀態（Status）：
- `C`（Common）：常規單字符摺疊映射；
- `F`（Full）：全字符集深度摺疊（如將 ‘ß’ 強制摺疊爲 “ss”）；
- `S`（Simple）：限制在單字符範圍內的保守摺疊；
- `T`（Turkic）：土耳其語系專屬特化摺疊。

兩串原本大小寫各異、寫法不同的文本，只需分別經過完整大小寫摺疊算法的標準化規範清洗，即可直接進行二進制等價性比對。

## 渲染與書寫屬性（Rendering Properties）

### 阿拉伯文與敘利亞文的連筆塑形

在世界文字體系中，以阿拉伯文（Arabic）與敘利亞文（Syriac）爲代表的閃米特語系文字展現出一種高度複雜的藝術化特質：**全手寫草書連筆體**（Cursive Script）。

在這類文字中，字母並不是像拉丁字母那樣彼此孤立排列，而是如同流水行雲般依靠筆畫的基線相互連接。因此，一個字母的實際視覺呈現形狀，完全取決於它在單詞中所處的相對拓撲位置：
1. **孤立位（Isolated Form）**：當字母單獨出現或前後均不發生連筆時；
2. **詞首位（Initial Form）**：當字母位於連筆詞組的開端、僅向左側（書寫流動方向）引出連接線時；
3. **詞中位（Medial Form）**：當字母兩端均與鄰近字母緊密相連時；
4. **詞尾位（Final Form）**：當字母位於詞組末端、僅承接右側連接線時。

更具挑戰性的是，阿拉伯字母表並非所有字母都能夠“四面逢源”。事實上，阿拉伯字母被嚴格劃分爲兩大陣營：
- **雙向連接字母**：具備完整的四種形態位格（詞首、詞中、詞尾、孤立）；
- **單向（右側）連接字母**：只能與右側的先行字母相連（呈現詞尾或孤立形態），卻嚴禁向左側引出連線（如字母 Alif ‘ا’、Dal ‘د’、Ra ‘ر’ 等）。一旦遇到此類字母，連筆鏈條即告中斷，其後繼字母被迫以詞首或孤立形態重新起筆。

爲了讓排版引擎與 OpenType 字體能夠精準計算字形替換，Unicode 在覈心屬性中確立了**連接類型**（Joining Type，記錄於 `ArabicShaping.txt`）：

| 連接類型代碼 | 英文全稱 | 連筆行爲特徵與規則定義 |
| :--- | :--- | :--- |
| **`D`** | Dual-joining（雙向連接） | 能夠自由與左右兩側的字符相互連接，完整具備四種上下文形態。 |
| **`R`** | Right-joining（右向連接） | 僅能與右側（先行）字符連接；絕不向左側引出連筆線。僅有詞尾與孤立兩種形態。 |
| **`L`** | Left-joining（左向連接） | 僅能與左側（後繼）字符連接。極度罕見，主要存在於特定敘利亞文變體中。 |
| **`U`** | Non-joining（不連接） | 完全獨立孤立，絕不與任何方向的相鄰字符發生物理連筆。 |
| **`C`** | Join-causing（引發連接） | 強制誘發連筆效果，其代表正是零寬連字符（ZWJ `U+200D`）與延伸字線 Kashida。 |
| **`T`** | Transparent（透明無阻） | 對連筆邏輯完全透明的字符（如各類發音短元音變音符）。排版引擎在掃描連筆鏈條時視其如空氣，直接跳過並貫通其前後的輔音連筆。 |

### 字素簇管理（Managing Grapheme Clusters）

在計算機底層，一個“字符”（Character）只是編碼表上的一個數字碼點；然而在普通讀者的直觀視覺與心理認知中，一個“字”（Grapheme）往往是由一個基底字母及其周遭附着的一系列變音記號共同構成的不可分割的有機整體。

例如，越南語中的字母 ‘$\tilde{\hat{\text{E}}}$’（帶有揚抑符與硬顎波浪符的小寫 e），在內存中可能由基底字符 ‘E’ 緊隨兩個獨立的組合變音碼點（`U+0302` 與 `U+0303`）拼合而成。當用戶在文本編輯器中按下鍵盤退格鍵（Backspace）、或使用光標左右箭頭穿行文本、亦或軟件執行換行與單詞加亮時，軟件絕不能野蠻地將光標停駐在字母 ‘E’ 與其變音符之間，更不能只刪掉半個變音符而留下一堆破碎的亂碼。

爲了徹底規範文本交互中的基本視覺單元，Unicode 專門發佈了 **第 29 號技術報告**（Unicode Standard Annex #29, UAX #29），確立了**用戶感知字符**——即**字素簇**（Grapheme Cluster）的形式化邊界算法。

標準嚴格區分了：
1. **傳統字素簇**（Legacy Grapheme Cluster）
2. **擴展字素簇**（Extended Grapheme Cluster）

該規範依靠一組精密的布爾邏輯與字符邊界屬性（如 `Grapheme_Cluster_Break` 包含的 `CR`、`LF`、`Control`、`Prepend`、`Extend`、`SpacingMark` 等），構築起現代文本編輯光標與排版折行絕不可逾越的護城河。

## 數值屬性（Numeric Properties）

在 `UnicodeData.txt` 的主數據列中，整整分配了三個並行的字段（第 6、7、8 號字段）用於記錄字符的數學數值（Numeric Properties）：
- **第 6 字段（Decimal Digit Value）**：十進制數碼數值。若字符屬於標準進位制十進制數字（分類 `Nd`），則填入其 0 至 9 的整數值；否則留空。
- **第 7 字段（Digit Value）**：數碼數值。包括某些雖然代表數碼但具有特殊排印修飾的符號（如帶圈數字 `③` 的該字段值爲 3）。
- **第 8 字段（Numeric Value）**：通用廣義數值。能夠接納一切表示數量概念的字符，包括常規分數（如 `½` 記作 `1/2`）、羅馬數字（如 `Ⅻ` 記作 `12`）、甚至漢字大寫數字（如 ‘億’ 記作 `100000000`）。

## 標識符與語法規範（Identifiers and Pattern Syntax）

任何一門現代計算機編程語言（無論是 Python、Java、C# 還是 Rust）在編譯源代碼時，詞法分析器面對的第一個嚴峻挑戰便是：**源代碼中的變量名、函數名與類名允許包含哪些 Unicode 字符？**

若缺乏統一的標準約束，開發者可能會隨意使用肉眼無法辨識的不可見格式字符作爲變量名，甚至利用希臘字母 ‘$\omicron$’（Omicron）與拉丁字母 ‘o’ 的視覺同形（Homoglyph）製造極其危險的安全木馬漏洞。

爲此，Unicode 頒佈了權威的 **第 31 號技術報告**（UAX #31: Identifier and Pattern Syntax）。該規範將字符空間劃分爲四大基礎屬性：
- **`ID_Start`**：允許作爲合法程序標識符**首字符**的集合（涵蓋所有大寫字母、小寫字母、詞首大寫字母、漢字等，但堅決排除數字與連接標點）；
- **`ID_Continue`**：允許作爲標識符**後續字符**的集合（在 `ID_Start` 基礎上，納入十進制數字、下劃線及非進幅修飾標記）；
- **`Pattern_Syntax`**：專門爲編程語言語法關鍵字、運算符與分隔語法保留的不可變字符集；
- **`Pattern_White_Space`**：被明確界定爲源代碼合法語法留白的空白字符集。

## 深入研讀 Unicode 區塊（Reading a Unicode Block）

爲了讓讀者真正領略 Unicode 規範典籍的宏偉與嚴謹，在原書第 121 與 122 頁中，作者（經由 Unicode 聯合會麗莎·摩爾 Lisa Moore 的正式特許授權）完整重印了官方權威典籍 [335] 中的兩個原版頁面。它們展示的正是著名的**拉丁文擴展-A**（Latin Extended-A）區塊——該區塊收錄了那些過於冷僻而未能擠入 ISO 8859-1、但又尚未古怪到被貶入“拉丁文擴展-B”的珍貴歐洲拉丁文字符。

首先呈現在我們眼前的是展示區塊二維拓撲結構的官方代碼圖表（Code Chart）。在圖表中，每一列代表高位十六進制編碼，每一行代表低位十六進制偏移；在每一個代表性字形的下方，均清清楚楚地印刻着對應字符的唯一十六進制碼點。

我們在此區塊中立刻與四位久違的“老朋友”重逢——它們正是因歷史遺憾慘遭 ISO 8859-1 遺漏、而在第一章中令排版工匠苦不堪言的四個歐洲字符：
- 法文連字 ‘Œ’（`0x0152`）與 ‘œ’（`0x0153`）；
- 帶分音符的大寫 ‘Ÿ’（`0x0178`）；
- 以及古典長 s ‘ſ’（`0x017F`，The Long "s"）。

現在，讓我們將目光轉向原書第 122 頁上的官方字符描述列表（Character Names List）。該頁面頂端粗體黑體字印刷的副標題“European Latin”（歐洲拉丁文），表明了該數據表依照字符現實應用領域所進行的語義細分（在本區塊中，這是唯一的分類子項）。

對於每一個字符條目，官方文檔均以極其嚴謹的三列布局縱向展開：
- **第一列**：字符的十六進制絕對碼點（Hexadecimal Code Point）；
- **第二列**：該字符的代表性字形（Representative Glyph）；
- **第三列**：字符的終身法定名稱（Character Name）以及豐富詳盡的修飾細節。

字符名稱一律採用大寫英文排印：例如 `LATIN CAPITAL LETTER A WITH MACRON`（帶長音符的拉丁大寫字母 A）。**這一名稱一旦被正式定稿頒佈，即享有永恆不朽的絕對不可變更性**（Immutable for all of eternity）。哪怕數十年後人們發現當初的命名中存在拼寫錯誤或地理歷史學誤判，這些錯誤也將作爲標準的組成部分被永久保留在編碼表中，與人類文明的計算機系統共存始終。

然而，爲了彌補名稱不可修改所帶來的侷限，Unicode 聯合會保留了對字符條目追加**註釋**（Annotations）與**說明**的權力：
1. **導引圓點註釋（`•`）**：以黑色實心圓點開頭的條目，屬於無強制約束力的**信息性說明**（Informative Note），旨在輔助排版工匠與軟件人員正確應用該字符。在圖版中我們可以看到極其豐富的文獻考據：例如註明 ‘ģ’ 是拉脫維亞語字母、‘ć’ 是波蘭語與克羅地亞語字母、帶撇號的 ‘ď’ 是捷克語排版中“帶抑揚符的 d”（d with háček）的首選視覺形態、以及警告排版人員絕不可將克羅地亞語的 ‘Đ’ 與美洲原住民文獻中的 ‘Ð’ 相互混淆等等。
2. **等號別名（`=`）**：代表字符的非正式輔助別名（Alternative Name）。例如在後續頁面中，法文連字 ‘œ’ 擁有如下珍貴別名：

```text
œ
LATIN SMALL LIGATURE OE
= ethel (from Old English eðel)
• French, IPA, Old Icelandic, Old English, ...
→ 00E6 æ  latin small letter ae
→ 0276 œ  latin letter small capital oe
```

由此我們驚奇地獲知：‘œ’ 連字不僅效力於法蘭西語言，而且在古英語（Old English）中曾擁有一個極爲優雅的名字——“eðel”，並且在古冰島語（Old Icelandic）中亦廣爲流傳。

### 交叉引用與不等式警告（`→`）
凡是以箭頭 `→` 開頭的行，要麼是嚴厲的**顯式不等式**（Explicit Inequalities），要麼指示着深厚的**語言學親緣關係**（Linguistic Relationships）。

例如，在字符 `0x0110`（`LATIN CAPITAL LETTER D WITH STROKE`，帶橫槓的拉丁大寫字母 D）下方，我們可以查閱到如下指引：
- `→ 00D0 Ð  latin capital letter edh`（顯式不等式：嚴正警告開發者絕不可與冰島語的 Eth 字母混淆！）
- `→ 0111 đ  latin small letter d with stroke`（交叉引用：直接鏈接至其對應的小寫字母，即表格中的下一項）
- `→ 0189 Đ  latin capital letter african d`（顯式不等式：警告不可與西非埃維語 Ewe 所使用的非洲大寫 D 混淆！）

而在其小寫條目 `0x0111` 下方，赫然列有：
- `→ 0452 ђ  cyrillic small letter dje`（語言學親緣關係：告知該克羅地亞字母在塞爾維亞西里爾文中的完全等價對應物正是字母 ‘ђ’，爲兩套字母表之間的精密音譯轉換提供了官方錨點）。

### 規範等價分解（`≡`）與兼容等價分解（`≈`）

當數據行以恆等號 **`≡`** 開頭時，宣告該字符可以被無損解構還原爲其他基礎字符的組合序列——這便是**規範分解**（Canonical Decomposition）。根據定義，規範分解具有絕對的數學唯一性，並且必然由一個基底字符與一個或兩個結合變音符拼接而成。例如：

`Ā`（`0x0100`）的規範分解爲基底字母 `A`（`0x0041`）緊隨結合長音符（`0x0304`）：
```text
Ā ≡ 0041 A + 0304 [combining macron]
```

在排版渲染與信息檢索中，預組合單字符 ‘Ā’ 與拆分組合序列 “A + ̄” 被視爲同一存在的兩種等價表象。

另一方面，當數據行以約等號 **`≈`** 開頭時，則揭示了另一種深刻的排版妥協——**兼容分解**（Compatibility Decomposition）。
兼容分解代表着當軟件環境或字體技術受限、無法原生駕馭該特定字符時所能採取的次優降級方案。

典型例證見於南非荷蘭裔白人所使用的阿非利卡語（Afrikaans）中的特殊冠詞複合字母 ‘ʼn’（`0x0149` `LATIN SMALL LETTER N PRECEDED BY APOSTROPHE`）。該字符在官方規範中的完整定義如下：

```text
0149
ʼn
LATIN SMALL LETTER N PRECEDED BY APOSTROPHE
= LATIN SMALL LETTER APOSTROPHE N
• Afrikaans
• this is not actually a single letter
≈ 02BC ʼ  006E n
```

其兼容分解明確指示：在視覺上，它可以降級模擬爲一個修飾字母撇號（`U+02BC`）外加一個小寫字母 ‘n’。
然而我們必須牢記：**兼容分解永遠伴隨着語義信息的不可逆流失**。如果一位嚴謹的文獻作者在其文檔中顯式鍵入了阿非利卡語專用的 ‘ʼn’，他必然懷有極其深刻的學術理由。但是，若面對一套技術處於“石器時代”的古董排版軟件，讓它用撇號加小寫 n 來完成基本的檢索與顯示，總好過拋出一堆不可辨識的亂碼方塊——這正是工程嚴謹性（Rigor）與現實可用性（Efficiency）之間永恆的平衡藝術。

### 兼容格式化標籤全景剖析（Formatting Tags）

既然談到了視覺模擬，爲何不在兼容分解中進一步賦予排版渲染引擎具體的樣式提示？Unicode 爲此量身打造了整整 **16 種格式化標籤**（Formatting Tags）。這些標籤大量湧現在各類符號與排版變體的兼容分解描述之中：

1. **`<font>`（字體樣式模擬）**：
   通過精選特定歷史字體來完美模擬該字符的視覺神韻。此標籤在 Unicode 中被高頻調用了不下 1,038 次！
   例如數學中表示覆數實部的專有符號 ‘$\Re$’（`0x211C` `BLACK-LETTER CAPITAL R`），其官方兼容分解正是：
   ```text
   ≈ <font> 0052 R  latin capital letter r
   ```
   換言之，若軟件缺乏該專有數學符號的獨立矢量輪廓，只需調用一套正統的德意志黑體（Fraktur）字體並排印其中的英文字母 ‘R’，便能達到幾可亂真的完美重現！至於應當選取何種古典黑體，研讀本書第十一章必能給讀者帶來無盡的靈感。
2. **`<noBreak>`（不換行控制）**：
   指示該字符爲其後繼內容的絕對不換行版本。例如不換行連字符 ‘‑’（`0x2011` `NON-BREAKING HYPHEN`），其兼容分解爲：
   ```text
   ≈ <noBreak> 2010 -  hyphen
   ```
   它向排版引擎施加了鐵的紀律：此處嚴禁折行斷句。
3. **`<initial>`、`<medial>`、`<final>`、`<isolated>`（上下文書寫形態）**：
   專門用於阿拉伯文與敘利亞文演示形區塊（Presentation Forms），分別明確綁定字符在詞首、詞中、詞尾與孤立位的特定幾何拓撲。
4. **`<circle>`（圈號修飾）**：
   指示該字符爲加圈符號，如帶圈字母 ‘Ⓡ’、帶圈數字 ‘⑩’ 等。
5. **`<super>` 與 `<sub>`（上標與下標）**：
   指示文字應當以數學上標（如 ‘¹’、‘ᵃ’）或下標（如 ‘₁’、‘ₙ’）的幾何比例進行縮小並垂直平移排印。
6. **`<vertical>`（縱排專有形態）**：
   指示該字符專供豎排文本流使用。例如豎排左括號 ‘（’（`0xFE35` `PRESENTATION FORM FOR VERTICAL LEFT PARENTHESIS`），其兼容分解爲：
   ```text
   ≈ <vertical> 0028 (
   ```
   以此在缺乏 OpenType 豎排特性的古老環境中鎖死括號在直排下的旋轉姿態。
7. **`<wide>` 與 `<narrow>`（全角與半角轉換）**：
   對應東亞排版中全角 ASCII 字符（Fullwidth Forms，佔據整整一個漢字方塊寬度）以及半角片假名字符（Halfwidth Katakana，如 `｢ｺﾒ･｣`）。
8. **`<small>`（小型變體）**：
   專用於臺灣 CNS 11643 兼容區塊（`0xFE50..0xFE6B`）中所收錄的小型標點符號。
9. **`<square>`（方塊字組字）**：
   將若干西文字符或假名微縮拼接在一個標準漢字方塊空間內，如公制單位組合字符 ‘㎦’（立方千米）：
   ```text
   ≈ <square> 006B k  006D m  00B3 3
   ```
10. **`<fraction>`（分數斜線組合）**：
    指示標準分數結構。例如分數四分之一 ‘¼’：
    ```text
    ≈ <fraction> 0031 1  2044 /  0034 4
    ```
    注意此處使用的是專有分數斜線（Fraction Slash `U+2044`），絕不可與普通的 ASCII 斜槓 ‘/’（`0x002F`）混爲一談。
11. **`<compat>`（通用未分類兼容）**：
    涵蓋其餘一切無法歸入上述專門標籤的雜項兼容形態，在 `UnicodeData.txt` 中用於明確劃清兼容分解與規範分解的技術界河。
