# 第10章：フォントとワールドワイドウェブ（Web）
**ヤニス・ハラランボス（Yannis Haralambous, Ph.D.）著**
*『Fonts & Encodings』第 315–366 頁より*

*訳者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

---

ティム・バーナーズ＝リー（Tim Berners-Lee）が最初に HTTP（Hypertext Transfer Protocol）プロトコルと HTML（Hypertext Markup Language）マークアップ体系を定義したとき、わずか20年後に全世界の人々が「.com」を口にするようになるとは夢にも思っていなかったであろう。ワールドワイドウェブ（World Wide Web）の爆発的な普及は、間違いなく20世紀末における人類情報科学技術史上の最も輝かしい金字塔の一つである。

HTML はマークアップシステムであり、タグの構造と意味論を規定する規則の集合体である。これは SGML（Standard Generalized Markup Language、標準汎用マークアップ言語）から派生したものである。ここでの「汎用（Generalized）」とは、それ自体が固有の意味論を持たず、形式的な記述構文のみを提供するという意味である。SGML 文書はいくつかの**要素（Elements）**から構成される。各要素は通常、開始タグ（`<name>` の形式）と終了タグ（`</name>` の形式）のペアで表される。このタグのペアの間に要素の内容（Content）が存在し、その中にはテキストや他のネストされたタグを含めることができる。要素はまた、**属性（Attributes）**と呼ばれる任意の数のメタデータを保持できる。属性は「キー＝値（key-value）」の形式で開始タグの内部に記述され、その数量と順序は原則として任意である。

SGML 文書には通常、**文書型定義（Document Type Definition, DTD）**が付随しており、これは文書内部に直接埋め込むことも、独立した外部ファイルとして保存することもできる。DTD には2つの重要なデータが含まれる。第一に、当該 SGML 文書内で出現が許可される全要素のリスト、ならびにそれらが保持できる属性とそのデータ型である。第二に、要素間のネストと組み合わせの振る舞いを規定する文法規則である。例えば、ある特定要素の内部に別の特定要素を何回含められるか、要素が空（Empty Element）でなければならないか、あるいは任意の内容を保持できるかなどを DTD で厳密に規定できる。

HTML は本質的に特定の SGML DTD であり、同時に具体的なマークアップ構文でもある。これは、HTML 文書で使用可能なタグの集合があらかじめ厳密に定義されており、タグ同士のネストや相互作用の規則も固定されており、さらに各タグの組版表示や文書意味論上の具体的な意味と適用場面を解説した詳細な仕様書が存在することを意味する。

しかし、すべてのコマンドの基底実行意味論が極めて厳密である LATEX のような組版言語とは異なり（LATEX では各コマンドが厳密な手続き型命令であり、その実行プロセスを TEX エンジンの深奥まで追跡可能である。換言すれば、LATEX のコマンドは後方定義された「タグ」であり、その意味論は TEX や $\Omega$ のコンパイル時における実際の組版効果によって完全に決定される）、HTML がタグに付与したものは往々にして極めて曖昧で近似的な意味論に過ぎず、主要ブラウザベンダーがそれぞれの思惑で勝手に解釈することを許してしまった。HTML はその初期において、タグをめぐるこの「芸術的曖昧さ（artistic fuzziness）」に悩まされ続けた。初期の主要ブラウザベンダーは、基礎構文システムに独自のプライベートタグを勝手に追加する権利（さらには義務）があると信じ込み、その結果 HTML 標準は断片化された混乱に陥り、多くの標準改定は最大シェアを持つブラウザの既成事実に追従するだけのものとなった。

上述の欠点が存在したにもかかわらず、我々は歴史を客観的に見つめなければならない。Macintosh、Windows PC、そして多様な Unix ワークステーション間の相互通信が悪夢であった時代において、HTML は（TEX、そして少し後に登場した Adobe Acrobat PDF と並び）すべての主要 OS を真に横断する初のユニバーサルな「文書フォーマット（Document Format）」となったのである。HTML の標準枠組みを崩壊させることなく次々と湧き上がる新たな要求に応えるため、W3C と産業界は基底マークアップの上に2つの新たな情報レイヤーを順次重ね合わせた。その一つが **JavaScript** である。これはネットスケープ社（Netscape）が開発し、後に ECMA によって ECMAScript として標準化された軽量プログラミング言語であり、HTML ページの動的対話ロジックを処理することを主眼とする。もう一つが**カスケーディング・スタイル・シート（Cascading Style Sheets, CSS、W3C 標準）**であり、HTML ページの視覚表現と組版外観を構造から分離して精密に記述するために特化したスタイル言語である。

これら3層の情報（HTML 構造、JavaScript 対話、CSS スタイル）は同一文書内で協調し、調和して共存する。それだけでなく、**ドキュメントオブジェクトモデル（Document Object Model, DOM）**と呼ばれる統一オブジェクト指向プログラミングインターフェースのおかげで、HTML タグ、CSS スタイルプロパティ、スクリプト実行ロジックは完全な三位一体となった。プログラマは JavaScript を通じて任意の要素のコンテンツとスタイルプロパティをリアルタイムに直接読み書き・操作できる。この三位一体の強力なアーキテクチャこそが、21世紀初頭のダイナミック HTML（DHTML）およびリッチインターネットアプリケーション（RIA）の爆発的発展を支える絶対的な基盤となった。

しかし、万維網技術の急速な進化の歴史において、**デジタルフォントの組版制御と画面表示（Screen Typography）**は、常に最も解決が困難で矛盾が激しく衝突する中核領域の一つであり続けた。その根本的原因は極めて単純である。**文書内の通常のテキストや図版とは決定的に異なり、フォントはデジタル文書において所有権が通常文書作成者自身に属さない唯一の中核リソースだからである**。フォントが文書作成者に属さない理由は、知的財産権と商業ソフトウェアライセンス契約（License）によって厳格に拘束されており、作成者はそれを全世界に向けて勝手に公開・再配布する法的権利を一切持たないためである。

Web ページ上でテキストを組版・レンダリングする際、従来のアプローチはクライアントのローカル OS にあらかじめインストールされている既存フォントの使用に限定せざるを得なかった。しかしそれでは、設計者は各 OS のフォント命名規則をあらかじめ予見するか、さもなければ極めて大まかな総称フォント名（Generic Family Names）に甘んじるほかなかった。Web デザイナーが組版美学、コーポレートアイデンティティ、あるいは主要 OS でネイティブサポートされていない稀少な民族文字や古文字を正確に表示するために特定フォントを**どうしても**使用しなければならない場合、サーバー側からクライアントへフォントリソースを安全にプッシュ配信する技術的パイプラインが不可欠となり、これこそが無数の困難な技術的ボトルネックと厳しい著作権紛争の交差する台風の目となったのである。

万維網におけるフォント技術の発展の系譜を概観すると、産業界は主として3つの明確に異なる技術的アプローチから探索を進めた。これらが本章の3大主軸を構成している：

1. **構造およびスタイル層の標準仕様**：HTML 標準自体が提供する基礎的なテキストスタイルタグ、ならびに組版の中枢である CSS（カスケーディング・スタイル・シート）仕様が確立した精密なフォントプロパティ宣言とマッチングアルゴリズム体系。これらは、ローカルフォントであれネットワークからオンデマンドで取得されるダウンロード可能フォント（Downloadable Fonts）であれ、(X)HTML ページ内で呼び出されるフォント特性を網羅的に記述する。
2. **商用 Web フォント埋め込みツールとランタイムプラグイン**：歴史上、2大技術巨頭がクロスプラットフォームでのフォント動的配信に対応するプロプライエタリなプラグインシステムを開発し、ブラウザが Web ページのレンダリングに必要なフォント資産を動的に取得できるようにした。その一つが **Bitstream** 社の **TrueDoc** 動的フォント技術であり、もう一つが**マイクロソフト社**（Microsoft）の OpenType アーキテクチャに基づく **Web フォント埋め込み技術**（Font Embedding / EOT）である。Bitstream は初期に Netscape Communicator 4.x、Windows 版 IE、Mac 版 iCab など一部ブラウザで支持を獲得した。一方、マイクロソフトの EOT 技術は長期間 Windows 版 Internet Explorer の独占であったものの、全世界の開発者に極めて完成度の高い専用フォントパッキング・埋め込みツールが無償提供された点で際立っていた。また、スウェーデンの em2 Solutions 社は GlyphGate と呼ばれるサーバーサイドの動的グリフゲートウェイミドルウェアを投入し、クライアントのレンダリング能力に応じて多彩なハイブリッド戦略で高精度グリフ配信を実現した。
3. **ベクターグラフィックス標準に基づく自己完結型フォント体系**：**SVG**（Scalable Vector Graphics、W3C 標準）。純粋な XML ベクターグラフィックス記述言語として、SVG は通常の CSS 機構を通じて外部フォントを呼び出すだけでなく、標準規格内部に **SVG フォント仕様（SVG Fonts）**を直接創設した。これにより、各文字のベジェ輪郭ベクターパスを XML タグの形式でグラフィックス文書内部に直接完全に埋め込むことが可能となり、OS 基底のフォントラスタライザを完全にバイパスして、絶対的なクロスプラットフォーム高忠実度ベクターレンダリングを達成した。

## 標準 HTML 要素と書体指定

CSS スタイルシートが全面的に普及する以前、初期の HTML 仕様は文書作成者の基礎的な視覚的要求を満たすため、文字の外観に直接作用する物理的・論理的スタイルタグを順次導入した：

* `<b>` と `</b>`：内部のテキストを**太字（Boldface）**で表示。
* `<i>` と `</i>`：内部のテキストを**イタリック体（Italics）**で表示。
* `<tt>` と `</tt>`：内部のテキストを**等幅タイプライターフォント（Teletype / Monospace）**で表示。
* `<em>` と `</em>`：論理強調（Emphasis）。主要ブラウザではデフォルトでイタリック体としてレンダリングされる。
* `<strong>` と `</strong>`：強い論理強調（Strong Emphasis）。主要ブラウザではデフォルトで太字としてレンダリングされる。
* `<code>` と `</code>`：インラインのコンピュータソースコード断片（Code）。等幅フォントで表示される。
* `<samp>` と `</samp>`：プログラムのサンプル出力（Sample Output）。等幅フォントで表示される。
* `<kbd>` と `</kbd>`：ユーザーのキーボード入力（Keyboard Input）。等幅フォントで表示される。
* `<var>` と `</var>`：プログラム変数または数学変数（Variable）。イタリック体で表示される。
* `<dfn>` と `</dfn>`：用語の定義箇所（Defining Instance）。通常イタリック体で表示される。
* `<cite>` と `</cite>`：作品の引用または文献の出典（Citation）。通常イタリック体で表示される。
* `<small>` と `</small>`：1段階小さいフォントサイズで表示（Smaller Font）。
* `<big>` と `</big>`：1段階大きいフォントサイズで表示（Bigger Font）。
* `<sub>` と `</sub>`：下付き文字（Subscript）。フォントサイズを縮小し、ベースラインより下方にシフト。
* `<sup>` と `</sup>`：上付き文字（Superscript）。フォントサイズを縮小し、ベースラインより上方にシフト。
* `<font>` と `</font>`：HTML 3.2 で導入され、その後の HTML 4.01 Strict および XHTML 1.0 で完全に廃止された物理的組版タグ。その短い歴史の中でサポートされた中核属性は下表の通りである：

| 属性名（Attribute） | Netscape 対応バージョン | Explorer 対応バージョン | 代表的構文例 |
| :--- | :--- | :--- | :--- |
| `color` | ≥ 2 | ≥ 3 | `color="#660099"` |
| `face` | ≥ 3 | ≥ 3 | `face="Helvetica, Arial, sans-serif"` |
| `point-size` | 4 | - | `point-size="12"` |
| `size` | 全バージョン | 全バージョン | `size="-2"` |
| `weight` | 4 | - | `weight="300"` |

Web デザイン哲学の成熟に伴い、`<font>` のような物理表現タグを文書本文に混在させる手法は、メンテナンスコストの暴走、コードの肥大化、そして視覚表現と文書構造の深刻な癒着という破滅的結果を招いた。W3C は「構造（HTML）と表現（CSS）の完全分離」という黄金律を確立し、フォントファミリーの選択、フォントウェイト、イタリック傾斜、サイズ比率などのすべての組版制御権は、CSS 仕様へと全面的に委ねられた。

## CSS フォントモジュール仕様（CSS Fonts Module）

CSS Level 1 から CSS Level 2、さらには現代の CSS Fonts Module に至るまで、スタイルシート言語は伝統的なタイポグラフィの規範に合致した極めて完成度の高いプロパティ体系を構築した。

### フォント指定の中核 CSS プロパティ

CSS において、テキストが採用すべきフォントの視覚的特徴を正確に記述するための中核プロパティには、以下の項目が含まれる：

#### 1. `font-family`（フォントファミリー）
優先して適用するフォント名の候補リストを指定する。宣言値は2つのタイプの識別子の混合で構成される：
* **具体的フォントファミリー名（Family Names）**：`"Times New Roman"`, `"Helvetica"`, `"Palatino Linotype"`, `"Georgia"` など。フォント名に空白や特殊記号が含まれる場合は、必ず引用符で囲む必要がある。
* **総称フォントファミリー名（Generic Font Families）**：万維網フォント体系における最後の「安全弁」である。ユーザーのローカル環境に先述の具体的フォントが存在しない場合、ブラウザはその大分類に適合する OS 内のプリセットフォントへ自動的にマッピングする。CSS は以下の5つの標準総称ファミリーを規定している：
  * `serif`：セリフ（うろこ・飾り）を持つ書体ファミリー（Times, Georgia, Minion, Palatino など）。
  * `sans-serif`：セリフを持たないサンセリフ書体ファミリー。端点が直線的で画面上の明瞭性に優れる（Arial, Helvetica, Verdana, Trebuchet MS など）。
  * `monospace`：すべての文字が厳密に同一の水平送り幅を持つ等幅フォントファミリー（Courier New, Consolas, Monaco, Lucida Console など）。
  * `cursive`：手書きの筆致、続け字、またはカリグラフィ的装飾傾向を持つ筆記体ファミリー（Comic Sans MS, Zapf Chancery, Brush Script など）。
  * `fantasy`：装飾性が高く、劇的・舞台的な視覚的誇張を持つファンタジー装飾書体ファミリー（Impact, Western など）。

#### 2. `font-style`（フォントスタイル）
フォントの傾斜状態を制御する：
* `normal`：通常の直立正体（Roman / Upright）。
* `italic`：書体デザイナーがイタリック専用に設計した真正の草体・イタリック体（True Italic）。その骨格とセリフ構造は手書き筆致の特徴を色濃く反映する。
* `oblique`：機械的に傾斜させた斜体（Slanted / Oblique）。正体を幾何学的に右側へ一定角度シアー（傾斜）させて生成されることが多い。

#### 3. `font-variant`（フォントバリエーション）
スモールキャピタル（小型大文字、Small Capitals）の表示を制御する：
* `normal`：標準の通常大小文字グリフ。
* `small-caps`：小文字の高さを小文字の x-height に近似させたスモールキャピタルに置き換える。フォント自体に真正のスモールキャピタルグリフが内蔵されている場合、ブラウザはプロ仕様の設計グリフを優先表示する。内蔵されていない場合、ブラウザは大文字を機械的に縮小して擬似合成（Synthetic Small Caps）することがある。

#### 4. `font-weight`（フォントウェイト）
フォントのストロークの太さ（筆画の太さ）を制御する。CSS は以下のキーワードおよび9段階の絶対数値体系をサポートする：
* `normal`：標準の太さ。数値の `400` と等価。
* `bold`：太字。数値の `700` と等価。
* `bolder`：親要素の計算ウェイトに対して相対的に1段階太くする。
* `lighter`：親要素の計算ウェイトに対して相対的に1段階細くする。
* `100`, `200`, `300`, `400`, `500`, `600`, `700`, `800`, `900`：極細（Thin / Ultralight）から極太（Black / Ultrabold）に至る精密な階調スケール。

#### 5. `font-stretch`（フォントストレッチ）
フォントの水平方向の凝縮（コンデンス）および伸張（エクスパンド）の度合いを制御する：
* `normal`：伸縮のない通常の書体。
* `ultra-condensed`, `extra-condensed`, `condensed`, `semi-condensed`：4段階の凝縮。
* `semi-expanded`, `expanded`, `extra-expanded`, `ultra-expanded`：4段階の伸張。
* `wider`, `narrower`：親要素の現在の伸縮状態に対する相対調整。

#### 6. `font-size`（フォントサイズ）
フォントのボディサイズを決定する。極めて柔軟な指定方法が用意されている：
* **絶対サイズキーワード（Absolute Size）**：`xx-small`, `x-small`, `small`, `medium`, `large`, `x-large`, `xx-large`。W3C 仕様では隣接ステップ間で約 1.2〜1.5 倍のスケーリング比率が推奨され、`medium` は通常ブラウザのデフォルト閲覧サイズ（一般に 16px）となる。
* **相対サイズキーワード（Relative Size）**：`larger`, `smaller`。親要素から継承したサイズに基づき、絶対サイズスケールを1段階上下にシフトする。
* **物理および画面長単位（Length Units）**：
  * `pt`（ポイント、1/72 インチ、印刷・組版の古典的絶対単位）。
  * `px`（ピクセル、画面表示における参照ピクセルであり、解像度やスケーリングの影響を受ける）。
  * `em`（現在の要素の計算フォントサイズに相対的な単位。1em は現在のフォントのボディサイズに等しい）。
  * `ex`（現在のフォントの x-height に相対的な単位。フォントに当該メトリクスがない場合は通常 0.5em と推測される）。
* **パーセンテージ（Percentage）**：`120%` など。`em` 単位と同様に、親要素の計算フォントサイズを基準にスケーリングする。

#### 7. `font-size-adjust`（アスペクト比調整）と x-height の幾何法則

画面閲覧とタイポグラフィの美学において、非専門家が見落としがちな決定的な秘密がある。それは、**画面上におけるテキストの視覚的可読性と明瞭度を決定づけるのは、フォントサイズ（font-size）そのものではなく、小文字の実際の高さ——すなわち x-height（x-高度）であるという事実である**！

異なるフォントファミリー間で、技術的に同一のフォントサイズ（例えば 100 pt）が指定されていたとしても、デザイン思想や歴史的流派の違いにより、小文字の実際の高さは天と地ほども異なる。我々はフォントの**アスペクト比（Aspect Value、記号 $a$）**を次のように定義する：
$$a = \frac{\text{x-height}}{\text{font-size}}$$

デザイナーが `font-family` でフォントのフォールバック候補リストを指定した場合（例えば第1候補を Verdana、代替フォントを Times New Roman とした場合）、ユーザー環境に第1候補が存在しなければブラウザは代替フォントへと切り替える。しかし、Verdana は極めて巨大な x-height を持ち（$a \approx 0.58$）、Times New Roman の x-height は比較的小さい（$a \approx 0.45$）。ひとたびフォールバックが発生すると、同一フォントサイズ下での Times New Roman は視覚的に突如として極小かつ薄暗く判読困難となり、本来の組版バランスと可読性が壊滅的に崩壊してしまう。

この深刻な問題を解決するため、CSS は画期的な `font-size-adjust` プロパティを導入した。このプロパティにより、デザイナーは第1候補フォントの基準アスペクト比 $a$ を明示的に宣言できる。ブラウザが第1候補を欠き、ある代替フォントを採用せざるを得なくなった場合（その代替フォント固有のアスペクト比を $a'$ とする）、ブラウザは実際のレンダリング時におけるフォントサイズ（調整後フォントサイズを $c$ とする）を自動的に調整する。その計算式は以下の通りである：
$$c = \left(\frac{a}{a'}\right) \times s$$
ここで $s$ は元々宣言された `font-size` である。この動的補正メカニズムにより、代替フォントが画面に表示される際の小文字の高さは $c \times a' = a \times s$ というあらかじめ意図された設計寸法に厳密に保たれ、クロスプラットフォームかつフォント置換時においても視覚的明瞭度と快適な読書体験が見事に維持されるのである！

#### 8. `font` 複合プロパティとシステムフォントキーワード

CSS は強力な1行複合短縮プロパティ `font` を提供し、以下の厳格な構文順序に従って複数のフォントプロパティを一度に宣言できる：
```css
font: [font-style || font-variant || font-weight || font-stretch]? font-size [/ line-height]? font-family;
```
さらに、`font` プロパティは例外的に特定の**システムフォントキーワード（System Fonts）**の使用を許可しており、Web ページの UI 要素をユーザーの OS ネイティブなデスクトップウィジェットの外観へ完全に融合させることができる：
* `caption`：キャプション付きコントロール（ボタン、ドロップダウンなど）用。
* `icon`：デスクトップアイコンのラベル用。
* `menu`：システムドロップダウンメニュー用。
* `message-box`：モーダルダイアログやメッセージボックス用。
* `small-caption`：小型コントロールのサブヘッダー用。
* `status-bar`：ウィンドウ下部のステータスバー用。

### CSS フォントマッチングアルゴリズム（Font Matching Algorithm）

HTML 要素に一連の CSS フォント宣言が適用された際、ブラウザの内部処理系は盲目的に探索を行うのではなく、W3C 仕様によって厳密に規定された確定的な6ステップのマッチングアルゴリズムを実行する：

1. **ローカルフォントデータベースの構築**：ユーザーエージェント（ブラウザ）はまず現在の OS および利用可能なダウンロード可能フォントリソースを走査し、フォントファミリー名、ウェイト階調、傾斜状態、伸縮属性、および Unicode 収録範囲テーブルを含む、すべての利用可能フォントの完全な組版メトリクスを抽出・インデックス化する。
2. **フォントファミリー名の照合**：ブラウザは `font-family` 宣言を左から右へと順次検索する。指定された具体的名称に一致するものがなく、宣言末尾に総称フォント名（`serif` など）が指定されている場合、ローカルデータベースから対応するプリセット総称フォントを選択する。
3. **フォントスタイルの照合**：優先して `italic` を検索する。選択されたフォントに専用のイタリック体がないがデータベースに `oblique` が存在する場合、斜体で代用する（逆も同様）。双方が存在しない場合、ラスタライザが正体に対して幾何学的シアーを適用して擬似斜体を合成する。
4. **フォントバリエーションの照合**：スモールキャピタル（`small-caps`）がネイティブに用意された字形を優先検索し、存在しない場合は擬似合成処理へと移行する。
5. **フォントウェイトの階調照合**：要求されたウェイト数値が完全に一致しない場合、ブラウザは以下の確定的なヒューリスティックスケールに従って最も近い代替ウェイトを決定する：
   * 要求ウェイトが `500` の場合、まず下方の `400` を検索し、なければ上方の `600` 以上を検索する。
   * 要求ウェイトが `400` 未満の場合、厳格に数値の減少方向に向かってより細い字形を検索し、なければ上方を検索する。
   * 要求ウェイトが `500` 超の場合、厳格に数値の増加方向に向かってより太い字形を検索し、なければ下方を検索する。
6. **サイズのスケーリングとラスタライズ**：現代のスケーラブルベクターフォント（TrueType / OpenType / Type 1）では、計算された目標フォントサイズに従ってベジェ輪郭曲線をスケーリングし、グリッドフィッティング（ヒンティング）を実行する。極めて稀な旧式のビットマップフォントの場合、最も近いプリレンダリング済みビットマップを検索し、必要に応じてリサンプリングを施す。

### ダウンロード可能フォント規格（@font-face）

早くも CSS Level 2（1998年）仕様において、W3C は `@font-face` 規則を通じてネットワークから独自のフォント資産を動的にロードする標準化構想を極めて先進的に提示していた。標準的な `@font-face` 規則は、一連の**フォント記述子（Font Descriptors）**によって構成される：

```css
@font-face {
  font-family: "RoboScript";
  src: url("https://example.com/fonts/roboscript.otf") format("opentype"),
       url("https://example.com/fonts/roboscript.woff") format("woff");
  font-weight: normal;
  font-style: normal;
  unicode-range: U+0000-007F, U+0100-017F;
}
```

CSS2 仕様で定義された詳細なフォント記述子の一覧には以下のものが含まれる：
* `font-family`：現在のスタイルシートのスコープ内で当該 Web フォントを参照するための識別子。
* `src`：フォントの外部 URI ロケータおよびフォーマットヒント（`format(...)`）。
* `font-style`, `font-variant`, `font-weight`, `font-stretch`：当該 Web フォントがスタイルシートのマッチングツリー内でどのスタイルスロットに対応するかを定義する。
* `unicode-range`：当該 Web フォントに含まれる字形がカバーする Unicode コードポイントの区間を宣言する。この機構は極めて決定的なネットワーク最適化をもたらす。ブラウザがテキストを解析する際、現在のページ内にその区間の文字が一切出現しないと判明した場合、大容量のフォントファイルのダウンロードをインテリジェントにスキップできるのである！
* `units-per-em`：フォントの設計 em 正方形グリッド単位（1000 や 2048 など）。
* `panose-1`：フォントの 10 バイト PANOSE 分類コード。高度な類似性フォールバック置換に用いられる。
* `stemv`, `stemh`：字形の主要な縦ストローク（Vertical Stem）および横ストローク（Horizontal Stem）の太さメトリクス。
* `slope`：イタリック字形の垂直傾斜角度。
* `cap-height`：大文字の頭頂部からベースラインまでの高さ。
* `x-height`：小文字の頭頂部からベースラインまでの x-height。
* `ascent`, `descent`：フォントのアセンダ最大上昇量およびディセンダ最大下降量。
* `widths`：各グリフの水平送り幅のコンパクトなエンコーディングテーブル。
* `bbox`：設計座標系において全グリフ輪郭が形成するグローバル外接矩形（Bounding Box）。
* `definition-src`：フォントのより詳細な組版メタデータを含む外部定義ファイルのアドレス。

## 初期の Web フォント配信・埋め込み技術

Web フォント史の黎明期において、ブラウザが TTF/OTF を直接取得・レンダリングできる時代はまだ到来していなかった。著作権侵害の防止とカスタム組版の実現という両極の間で商業的妥協を図るため、歴史を画する2大技術ソリューションが誕生した：

### 1. Bitstream 社の TrueDoc 動的フォント技術（PFR）

Bitstream 社が提唱した **TrueDoc** 体系は、互いに補完し合う2つの中核コンポーネントから構成されていた：
* **文字形状レコーダー（Character Shape Recorder, CSR）**：サーバーまたはデザイナーのワークステーションに導入され、システム内のベクターフォント（TrueType または PostScript Type 1）をフック・解析し、そのストローク骨格と輪郭データを高度に圧縮・暗号化して、極めて軽量コンパクトな**ポータブルフォントリソース（Portable Font Resource、拡張子 `.pfr`）**へとカプセル化する。
* **文字形状プレイヤー（Character Shape Player, CSP）**：クライアントブラウザに組み込まれた微小なレンダリングエンジン。ネイティブなブラウザモジュール（Netscape 4.x 内蔵など）として、あるいは ActiveX コントロールや Java Applet として動作し、描画時に PFR を動的に復号してメモリ上でグリフをラスタライズする。

### 2. マイクロソフトのフォント埋め込み技術：WEFT と EOT

マイクロソフト社は Web フォントの課題に対し、自社 OS の技術的蓄積を深く活かした戦略を採用した。1997 年に**エンベッデッド OpenType（Embedded OpenType、拡張子 `.eot`）**フォーマットを策定し、全世界に向けて**Web フォント埋め込みツール（Web Embedding Fonts Tool, WEFT）**を無償提供した。

EOT フォーマットは、標準的な TrueType / OpenType フォントファイルに対して高度なスリム化と専用のカプセル化を施したものである：
1. **RootString ルートドメインセキュリティ保護**：EOT はファイルヘッダーに承認済みサイトのドメイン文字列リスト（RootStrings）を書き込む。Internet Explorer が EOT をロードする際、リクエストを発行した現在のページ URL がこれらのルートドメインまたはその正当なサブドメインに属しているかを厳密に検証し、一致しなければロードを拒絶する。この設計により、商用タイプファウンドリが恐れていたフォントファイルの無制限なダウンロード・盗用という懸念が払拭された。
2. **MicroType 圧縮と TrueType ヒンティングの完全保持**：WEFT は Agfa 社の MicroType 圧縮アルゴリズムをサポートし、グリフ輪郭データに対して驚異的な可逆圧縮を施すとともに、元フォントの TrueType Hinting（微調命令）を完全に保持する。これにより、Windows ClearType や低解像度ビットマップ環境においても極めてシャープな刃先のようなエッジ品質が保証された。
3. **OS/2 テーブルの埋め込み許可フラグの厳格な遵守**：WEFT は知的財産権の保護において極めて厳格であり、フォント解析時に `OS/2` テーブル内の `fsType` ライセンスビットを厳格に照合する。「埋め込み制限（Restricted License Embedding）」が設定されている商用フォントについては、WEFT は UI 上で赤色アイコンとともに明示的に変換を拒絶した。

## SVG 形式とネイティブベクターフォント体系

W3C が **SVG（Scalable Vector Graphics）**を策定したとき、万維網の視覚表現能力は天地を覆す飛躍を遂げた。100% 純粋な XML 構文仕様に基づくオープンなベクターグラフィックス標準として、SVG はビットマップ画像と静的テキストの間に横たわっていた旧来の溝を完全に打破した。

### SVG におけるテキストとフォント選択機構

SVG 文書内において、テキストはもはや固定されたラスタピクセルではなく、`<text>` 要素によって統括される一級のベクターグラフィックスオブジェクトである：
```xml
<svg width="600" height="200" xmlns="http://www.w3.org/2000/svg">
  <text x="50" y="100" 
        font-family="Georgia, serif" 
        font-size="48" 
        fill="#336699" 
        font-style="italic">
    Typography on the Web
  </text>
</svg>
```
SVG は中核的な CSS フォントプロパティをすべて継承・サポートしている。それだけでなく、`<tspan>`（インライン局所の座標微調整や独立スタイルオーバーライド）や `<textPath>`（ベジェ曲線で定義された任意の幾何パスに沿ってテキストを滑らかに湾曲配置）を通じて、SVG は Web デザイナーに未曽有の前衛的組版の自由度を与えた。

---

### 原生 SVG フォントアーキテクチャ（SVG Fonts）

しかし、SVG の最も先駆的で伝統的な組版界を震撼させた特性は、それが標準内部に直接創設した**原生 SVG フォント仕様（SVG Fonts）**にほかならない。

従来のコンピューティング環境では、文字のレンダリングは基底 OS の複雑なフォントサブシステム（Windows GDI/DirectWrite、Mac Quartz 2D、Linux FreeType）に全面的に依存していた。それに対し SVG 仕様では、**フォントそのものが純粋な XML タグの集合としてグラフィックス文書内部に直接完全に記述・内包される**のである！

完全な SVG フォント定義は `<font>` 要素の内部にカプセル化され、その典型的な構造は以下の通りである：

```xml
<font id="MyCustomFont" horiz-adv-x="1000">
  <font-face font-family="MyCustomFont"
             units-per-em="1000"
             ascent="800"
             descent="-200"
             cap-height="700"
             x-height="500" />
  <missing-glyph horiz-adv-x="500" d="M0,0 L500,0 L500,800 L0,800 Z" />
  <glyph unicode="A" horiz-adv-x="650" d="M100,0 L300,700 L350,700 L550,0 ... Z" />
  <hkern u1="A" u2="V" k="-80" />
</font>
```

#### SVG フォントメトリクスと font-face 属性

#### 水平および垂直組版の原点と送り量
SVG は欧文の伝統的な左から右への水平組版のみならず、東アジアの伝統的な上から下への縦組（垂直組版）をもネイティブにサポートしている：
* 水平組版時、グリフは**水平原点（Horizontal Origin、通常座標 $(0,0)$）**から描画を開始し、描画完了後に X 軸方向に沿ってその水平送り幅（$dx$、属性 `horiz-adv-x`）だけ前進する。
* 垂直組版時、グリフは**垂直原点（Vertical Origin、`vert-origin-x` および `vert-origin-y` で指定）**から描画を開始し、描画完了後に Y 軸方向に沿って下方へその垂直送り高（$dy$、属性 `vert-adv-y`）だけ前進する。

### 実践解剖：古典的活字グリフを純粋な SVG ベクターパスへ変換する

XML 内部におけるベクター字形の数学的動作機構を解き明かすため、本書の著者ヤニス・ハラランボスは現代フランス屈指の書体設計の巨匠ジャン・フランソワ・ポルシェ（Jean François Porchez）の名作——『Le Monde Livre』書体の大文字 **‘R’** を例に取り、極めて詳細な微視的解体を展開している。

::: tip 図 10-10：Le Monde Livre 書体の文字 ‘R’ を SVG ベジェベクター輪郭パスへ変換した幾何学的解剖図。文字輪郭の各3次ベジェ曲線の制御点と始終端アンカーポイントのシーケンスを明瞭に表示
![図 10-10：Le Monde Livre 書体の文字 ‘R’ を SVG ベジェベクター輪郭パスへ変換した幾何学的解剖図](/images/fonts-encodings/fig10-10.png)
*図 10-10：Le Monde Livre 書体の文字 ‘R’ を SVG ベジェベクター輪郭パスへ変換した幾何学的解剖図。文字輪郭の各3次ベジェ曲線の制御点と始終端アンカーポイントのシーケンスを明瞭に表示。*
:::

`<glyph>` 要素の `d` 属性内において、字形の輪郭はコンパクトで高効率な1文字の描画コマンドと連続座標シーケンスによって記述される：
* `M x,y`（Move To）：描画カーソルを持ち上げ、新たな開始座標点 $(x, y)$ へ瞬間移動する。
* `L x,y`（Line To）：現在の位置から目標点 $(x, y)$ へ直線を描画する。
* `H x`（Horizontal Line To）：横座標 $x$ へ水平線を描画する。
* `V y`（Vertical Line To）：縦座標 $y$ へ垂直線を描画する。
* `C x1,y1 x2,y2 x,y`（Cubic Bézier Curve）：$(x_1, y_1)$ および $(x_2, y_2)$ を制御点とし、終点 $(x, y)$ へ向けて滑らかな3次ベジェ曲線を描画する。
* `Z`（Close Path）：現在の点から本輪郭の開始点へと直線を引いて自動閉鎖し、閉じた塗りつぶしループ（Contour）を形成する。

図 10-10 に記された精緻な数値座標軌跡を辿ると、以下の手順が明白に浮かび上がる：
1. 描画コマンドは大文字 ‘R’ の主ステム（垂直幹）左下基底から始まり、`M` コマンドで始点を設定する；
2. 続いて主ステムの左側エッジを上方へ描き、上部セリフ（Serif）へと滑らかに移行する；
3. 次に一連の優美で連続した `C`（3次ベジェ）曲線により、‘R’ 上部の豊かに外へ膨らんだ円弧ボウル（Bowl）を描き出す；
4. その勢いのまま下方へ向かい、この字形において最も特徴的でカリグラフィ的な緊張感に満ちたエレガントな右下レッグ（Leg）と、その繊細に反り返った端部を描出する；
5. 最後に反転して上方へ向かい外輪郭を閉じた後、第2の内部サブパス（Inner Contour）を開いて内側の閉じた孔（カウンター、Counter）を精密にくり抜く！

高精度な曲線をプロプライエタリなバイナリコンテナから完全に切り離し、プレーンテキストの形式で Web 標準仕様の内部に直接提示するというこの構想は、組版技術史において比類なき先駆的意義を有している。SVG フォント仕様は、画面全体の微細なグリッドフィッティング（ヒンティング）機構の欠落や、巨大な極東フォントを解析する際のパフォーマンスの限界により、後にあらゆる場面に適した WOFF/WOFF2（Web Open Font Format）へと道を譲ることとなった。しかし、それが確立した文字の数学的ベクター表現ロジックは、今日においてもあらゆる現代デジタルフォントおよび Web グラフィックスエンジンの魂の基盤であり続けている。

# 結語

ワールドワイドウェブ初期におけるフォントの進化史を振り返ると、そこに見出されるのは妥協と衝突、そして知恵の火花に満ちた壮大な技術叙事詩である。一方では、Web 作成者は無味乾燥なデフォルトのシステムフォントの束縛から脱却し、高度な芸術的表現力と学術的正確性を兼ね備えた個性的な組版を希求した。他方では、商用タイプファウンドリによる著作権保護への正当な懸念、OS 覇者間の独自標準のせめぎ合い、そして帯域幅が極度に制約されていた初期ネットワークインフラが、一見して乗り越えがたい障壁を幾重にも築き上げていた。

Netscape/Bitstream の TrueDoc からマイクロソフトの WEFT/EOT に至るまで、初期の CSS フォント記述子の模索から自己完結型の SVG 原生フォント構想に至るまで、この世代の先駆者たちによる不断の技術的試行錯誤と標準の進化こそが、ワールドワイドウェブを全ベクター、全プラットフォームでの自由な流通を可能にした現代のユニバーサルオープンフォント時代（WOFF/WOFF2 および現代の CSS タイポグラフィ）へと導く、堅固にして広大な礎石となったのである！
