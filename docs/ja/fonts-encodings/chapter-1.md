日常のコンピュータ利用において曖昧に用いられがちな諸概念に対して、厳密な数学的・学術的定義を下そうと試みるとき、それらの厳密な内実が通俗的な常識よりも遥かに深遠であることにしばしば気付かされる。

文字符号化の壮大な歴史の絵巻を繙く前に、我々はまず本書全体の礎石を成す中核的概念体系を明確にしておかねばならない。
* **文字（Character）**：書記言語においてテキスト情報を組織化・制御・表現するための最も基本的な抽象意味要素（ラテン文字 ‘A’、アラビア文字 ‘Ba’、漢字の「字」、復帰改行の指令など）。それは純粋に形而上学的な概念である。
* **文字集合（Character Set）**：明確に定義され、曖昧さのない文字の集合。
* **符号位置／コードポイント（Code Point）**：文字集合における特定の論理的位置または整数インデックス。
* **符号化文字集合（Coded Character Set, CCS）**：「抽象文字」と「非負整数コードポイント」の間に厳密な一対一の写像関係を確立する数学的照合表（例えば ASCII 規格において文字 ‘A’ を十進整数 65 に対応付けること）。
* **文字符号化方式（Character Encoding Scheme, CES）**：整数コードポイントを、低水準の物理的コンピュータ記憶装置やネットワーク伝送に必要な具体的バイト列（Byte Sequence）へと一意に変換するための規則群（例えば UTF-8 や ISO 2022 エスケープストリームなど）。
* **バイト（Byte）とオクテット（Octet）**：
  * **オクテット（Octet）**：厳格に 8 個の二進ビット（Bits）で構成されるデータ単位であり、数値範囲は常に $0 \sim 255$（十六進で `0x00` から `0xFF`）である。
  * **バイト（Byte）**：コンピュータのハードウェアアーキテクチャによって決定される最小アドレス可能メモリ単位。1956 年、IBM 7030（Stretch スーパーコンピュータ計画）の主任設計者ヴェルナー・ブッフホルツ（Werner Buchholz）が **“byte”** という用語を考案した――タイプミスや口頭伝達においてビット（bit）と混同されるのを防ぐため、彼は意図的に bite ではなく byte と綴った。初期の計算機科学史において、1 バイトの物理的幅は機種ごとに異なっていた。6 ビット、7 ビット、8 ビット、さらには 9 ビットまでもが一世を風靡した。ドナルド・クヌース（Donald E. Knuth）が『The Art of Computer Programming』（TAOCP）において構想した仮想計算機 MIX のアーキテクチャに示されているように、クヌースは 1 バイトを「64 から 100 種類の異なる離散状態を保持できるもの」と定義し、ハードウェア上で 6 ビットバイトと十進 2 桁バイトの共存を許容した。1970 年代にマイクロプロセッサ業界の標準化が確立されて初めて、業界は事実上 1 バイト（Byte）と 1 オクテット（Octet）を同等とみなすようになったのである。

この厳密な術語体系を携えて、文字記号を電気信号へと変換してきた人類の波瀾万丈たる技術進化史の扉を開くこととしよう。

## 軍用デジタル通信の先駆：FIELDATA 体系

民生用コンピュータ産業がいまだ標準化されていなかった冷戦前夜、デジタル文字符号化の最初の突破口は軍用通信分野からもたらされた。1956 年、アメリカ陸軍通信隊（US Army Signal Corps）は主要国防調達企業（UNIVAC、Sylvania など）と連携し、世界初の汎用野戦データ伝送標準である **FIELDATA** を主導開発した。

当時のテレタイプ端末（Teletype）は、19 世紀にエミール・ボード（Émile Baudot）が発明した 5 単位コード（Baudot Code）に広く依存していた。5 ビット二進符号は $2^5 = 32$ 通りの状態しか表現できず、「文字シフト」（Letters Shift, LTRS）と「数字記号シフト」（Figures Shift, FIGS）という機械的な切り替えキーを用いて同一キー上で文字と数字を共用していた。この方式は、電波障害や雑音の激しい過酷な野戦環境においてシフトコードが脱落しやすく、その結果として以降の電文全体が解読不能な文字化けの残骸と化す致命的脆弱性を抱えていた。

FIELDATA は煩雑な機械的シフトを完全に排除し、現代のデジタルプロセッサに向けた固定長符号化構造をいち早く確立した。
* **基本単位は 6 ビット（64 コードポイント）および 7 ビット（128 コードポイント）**。
* 各文字はメモリ内で 6 ビットの有効ペイロードを占有し、ハードウェアパリティ検査（Parity Bit）のための第 7 ビットを備える。
* 軍はこれを **Plate 1-1** に示すように、$8 \times 8$ の論理状態マトリクスとして厳密に区分した。

::: tip 歴史的組版図版：FIELDATA 文字マトリクス全貌（Plate 1-1）
![Plate 1-1: FIELDATA Character Matrix](/images/fonts-encodings/plate1-1-fieldata-table.png)
*図版 1-1：FIELDATA 文字符号化マトリクス（原著第 29 頁より）。左側の高位行 `000`〜`111` と上端の低位列 `000`〜`111` が交差し、64 個の基本コードポイントを織り成す。*
:::

このマトリクスを精査すると、現代の文字コードの原初の胎動を明瞭に見て取ることができる。
* **大文字ラテン字母 `A`〜`Z`** は、`011 000`（八進 30）から始まる連続領域を占める。
* **アラビア数字 `0`〜`9`** は、`110 000` から `111 001` に集中配置されている。
* 専用のハードウェア制御信号が初めて導入された。マスタースペース（Master Space, `ms`）、大文字・小文字制御コード（Upper Case / Lower Case, `uc/lc`）、ブロック開始（Start of Block）、停止符（Stop）などである。

FIELDATA 規格は NATO 軍の統一規格として数十年にわたり運用され、UNIVAC 1100 シリーズ大型汎用機の文字体系を確立したのみならず、制御文字と図形文字を厳格に分離・配置するというその思想は、後の ASCII 規格の誕生を直接的に導くこととなった。

## ASCII の誕生と標準化の歩み

1950 年代末、商用コンピューティングと遠距離通信網の急激な爆発に伴い、主要コンピュータ製造企業（IBM、Remington Rand、Burroughs、GE）はそれぞれ独自路線を歩み、全米は互換性のない数十種もの私設文字集合で溢れかえっていた。機器間で磁気テープを交換することは、バベルの塔のごとき混乱を極めた。

この事態を収拾するため、米国標準化協会（ASA、現在の ANSI）は 1960 年に X3.4 委員会を設立した。「ASCII の父」と称される計算機科学者**ロバート・ベーマー（Bob Bemer）**の指揮のもと、全米情報交換標準コード――**ASCII（American Standard Code for Information Interchange）**の策定が開始された。

### 1. 7 ビット空間の合理的アーキテクチャ
6 ビット（64 文字。小文字や十分な約物を収容できない）と 8 ビット（256 文字。当時の高価な磁芯メモリや穿孔紙テープにおいて過剰なコストを要する）の激しいせめぎ合いの中で、委員会は先見性に満ちた妥協案に達した。**7 ビット符号化フレームワーク（$2^7 = 128$ コードポイント）を確立し、8 ビット通信チャネルにおいては最上位の第 8 ビットを物理伝送パリティ検査（Parity Check）として留保する**という設計である。

ASCII の 128 コードポイントは、**Plate 1-2** に示すように二大陣営へと整然と区分された。

::: tip 歴史的組版図版：ASCII-1963 と 1967 標準マトリクス対比（Plate 1-2）
![Plate 1-2: ASCII-1963 / 1967 Character Matrix](/images/fonts-encodings/plate1-2-ascii-table.png)
*図版 1-2：ASCII-1963 および 1967 符号化マトリクス（原著第 30 頁より）。第 0 列と第 1 列（0x00–0x1F）は C0 端末制御コード、第 2 列から第 7 列（0x20–0x7F）は印字可能図形文字。*
:::

* **先頭 32 位置（`0x00`〜`0x1F`）および末尾 `0x7F`：通信および端末制御文字（Control Characters, C0 集合）**  
  これら制御コードは、当時のテレタイプ端末やモデムの物理伝送に直接寄与した。
  * **改行（Line Feed, LF, `0x0A`）**：印字プラテンを垂直方向に 1 行送り出す。
  * **復帰（Carriage Return, CR, `0x0D`）**：重量のあるタイプキャリッジを機械レールに沿って左端へと跳ね戻す。
  * **ベル鳴動（Bell, BEL, `0x07`）**：端末内部の物理的な小型真鍮鐘を鳴らし、電信オペレータに警告を発する。
  * **水平タブ（Horizontal Tab, HT, `0x09`）** および **バックスペース（Backspace, BS, `0x08`）**。
  * **伝送制御**：ヘッダ開始（SOH）、テキスト開始（STX）、テキスト終了（ETX）、肯定応答（ACK）、否定応答（NAK）。
* **印字可能図形文字領域（`0x20`〜`0x7E`）**：
  * 空白文字（Space）は `0x20` に配置され、区切り記号と印字文字の二重の性質を担う。
  * 数字 `0`〜`9` は `0x30`〜`0x39` に配置された。この設計は極めて秀逸である。**数字の二進数値を抽出するには、ASCII コードの上位 4 ビットをマスク（ビット単位 AND `& 0x0F`）するだけで瞬時に数値が得られるのである！**
  * 大文字 `A`〜`Z`（`0x41`〜`0x5A`）と小文字 `a`〜`z`（`0x61`〜`0x7A`）の間には、厳密に 32 コードポイントの差（二進数の第 6 ビットの反転）が保たれている。大文字・小文字の変換は、プロセッサ内部で単純な単一サイクルの XOR または OR 指令によって瞬時に実行可能である。

### 2. ASCII-1963 と ASCII-1967 の変遷の波紋
1963 年に正式公布された ASCII 初版（ASA X3.4-1963）は、決して完全なものではなかった。小文字の位置は未定義のまま空白とされ、`0x5E` には上向きの実線矢印（$\uparrow$）、`0x5F` には左向きの矢印（$\leftarrow$）が割り当てられていた。

ロバート・ベーマーの粘り強い推進により、1967 年の全面改訂版において現代 ASCII の全容が確立された。
* **小文字 `a`〜`z`** の全面的な受容。
* ベーマーがプログラミング論理のために特に設計した特殊記号の導入：
  * **バックスラッシュ（Backslash, `\`，`0x5C`）**：後に DOS / Windows でディレクトリパス区切り文字に採用され、クヌースの $\TeX$ 組版システムにおいてすべてのマクロ命令のエスケープ文字に選ばれた。
  * **垂直バー（Vertical Bar, `|`，`0x7C`）**：ベル研究所のケン・トンプソンとデニス・リッチーにより、Unix 端末のパイプラインリダイレクト演算子（Pipe）に採用された。
  * **波括弧とチルダ**：波括弧 `{}`、チルダ `~`、脱字記号（キャレット） `^`。

1968 年、リンドン・ジョンソン米大統領は行政命令に署名し、米連邦政府が調達するすべてのコンピュータシステムと電気通信機器に対して ASCII の無条件サポートを義務付けた。これにより ASCII は情報化社会における最初の人類共通の礎石となり、1983 年には国際標準化機構によって **ISO 646 国際規格** として正式に承認された。

## IBM の帝国障壁：EBCDIC 体系とパンチカードの力学的遺伝

科学界と通信産業が ASCII の統一に歓声を上げていたその時、コンピュータ界の巨人 IBM はまったく異なる道を歩み始めた。

1964 年、IBM は全世界の産業界を震撼させた大型汎用機 **System/360 ファミリー** を発表した。しかし、S/360 に搭載されたのは誕生したばかりの ASCII ではなく、IBM 独自の **EBCDIC（Extended Binary Coded Decimal Interchange Code、拡張二進化十進コード）** であった。

なぜ IBM は共通標準を破ってまで EBCDIC を強行したのか？ その答えは、19 世紀の機械式計算機の古い力学構造の中に眠っている。

### 1. ホレリス・パンチカードの電気機械原理
1890 年、ハーマン・ホレリス（Herman Hollerith、彼が創設した会社が後に IBM となる）は**電気式パンチカード作表機（Punched Card Tabulating Machine）**を発明した。

**Figure 1-1** に示すように、標準的な IBM 80 桁パンチカードには 12 の水平穿孔行が存在する。

::: tip アーカイブ工学図版：ISO 1681 標準 80 桁パンチカード（Figure 1-1）
![Figure 1-1: A punch card (ISO 1681 standard)](/images/fonts-encodings/fig1-1-punch-card-iso-1681.png)
*図 1-1：ISO 1681 標準 80 桁パンチカード（原著 Figure 1-1 より）。カード上部の第 12 ゾーン孔、第 11 ゾーン孔、第 0 ゾーン孔、および下部の 1〜9 の数字孔から構成される。*
:::

ホレリスのカード読取機では、金属ブラシがカード上を通過する。
* カードに穴が開いていれば、ブラシが穴を貫通して下方の水銀槽や銅製ローラーに接触して回路が閉じ、カウンタリレーが 1 打進む。
* **数字 0〜9**：対応する行に単一の穴を開けるだけで表現できる。
* **文字 A〜Z**：単一の穴では 26 文字を区別できない。ホレリスは画期的な**「複合孔」機構**を考案した。最上部の 3 行を**ゾーン孔（Zone Punches）**と定義したのである――第 12 行（最上部ゾーン）、第 11 行（中間ゾーン）、第 0 行（ゼロゾーン）。
  * **文字 `A`〜`I`**：**第 12 ゾーン孔** と **数字孔 1〜9** の組み合わせで穿孔（`A` = 12+1, `B` = 12+2 など）。
  * **文字 `J`〜`R`**：**第 11 ゾーン孔** と **数字孔 1〜9** の組み合わせ（`J` = 11+1, `R` = 11+9 など）。
  * **文字 `S`〜`Z`**：**第 0 ゾーン孔** と **数字孔 2〜9** の組み合わせ（単独の数字 0 との重複を避けるため数字孔 1 は空けておく）。

### 2. EBCDIC 文字マトリクスと字母分断の謎
IBM が S/360 の内部バイト集合を設計した当時、世界中の企業の倉庫にはすでにパンチされた数十億枚もの商用カードが山積みされていた。既存のカード読取機のデコーダ回路を改修する手間を避けるため、IBM のエンジニアは乱暴にも**パンチカードのゾーン孔と数字孔の電気信号を、そのまま 8 ビットバイトの上位ニブルと下位ニブルにハードコードしたのである！**

この工学的妥協が生み出したのが、**Plate 1-3** に示す極めて奇怪な EBCDIC マトリクスである。

::: tip 歴史的組版図版：EBCDIC 8 ビット文字符号化マトリクス（Plate 1-3）
![Plate 1-3: EBCDIC Character Matrix](/images/fonts-encodings/plate1-3-ebcdic-table.png)
*図版 1-3：EBCDIC 文字符号化マトリクス（原著第 32 頁より）。大文字アルファベットが 0xC1–0xC9、0xD1–0xD9、0xE2–0xE9 の間で二箇所にわたり大きく断裂している構造が明瞭に示されている。*
:::

このマトリクスを精査すれば、初期の C 言語プログラマを悩ませ続けた歴史的謎が氷解する。**なぜ EBCDIC 文字集合において、26 個のアルファベットは数値軸上で連続していないのか？**
* 大文字 `A`〜`I` のコードは `0xC1`〜`0xC9`（上位 `C` は第 12 ゾーン孔に対応）。
* 続く `0xCA`〜`0xCF` には、実に **6 つの空白の断崖** が口を開けている！
* 続く `J`〜`R` は `0xD1`〜`0xD9` に配置される（上位 `D` は第 11 ゾーン孔に対応）。
* 続く `0xDA`〜`0xDF` にもまた **6 つの空白** が存在する！
* 最後に `S`〜`Z` が `0xE2`〜`0xE9` に収まる（上位 `E` は第 0 ゾーン孔に対応）。

ASCII システムでは、ある文字がアルファベットであるかを判定するには簡潔な一行のコードで済む。
```c
if (c >= 'A' && c <= 'Z') /* ASCII では完全に合法だが、EBCDIC では間の無関係な記号まで誤認してしまう！ */
```
しかしメインフレームの EBCDIC 環境下では、プログラマは苦痛に満ちた判定式を書かねばならなかった。
```c
if ((c >= 'A' && c <= 'I') || (c >= 'J' && c <= 'R') || (c >= 'S' && c <= 'Z'))
```

世界市場に対応するため、IBM は後に 57 種もの国別 EBCDIC コードページを派生させた。国ごとに大括弧、波括弧、アクセント文字の配置が食い違い、エンタープライズ分散コンピューティングにおいて数十年に及ぶ悪夢となったのである。

## ISO 2022 エスケープシーケンスと 8 ビット空間の四分割

1970 年代に入ると、コンピュータは急速に英米圏を飛び出し世界へと広がった。7 ビット ASCII は 128 個の記号しか保持できず、西欧のフランス語、ドイツ語、スペイン語の基本的なアクセント文字すら表現できず、ギリシャ文字、キリル文字、アラビア文字、そして数万の東アジアの漢字に至っては論外であった。

既存の 7 ビットおよび 8 ビット伝送基盤を覆すことなく全人類の言語を包摂するため、国際標準化機構は 1986 年、チューリングマシンの状態遷移の色彩を色濃く帯びた壮大なメタ規格――**ISO 2022（ECMA-35 規格に対応）**を発表した。

### 1. 8 ビット空間の四分天下構造
ISO 2022 規格は、標準的な 8 ビットバイト空間（256 コードポイント）を **Figure 1-2** に示すように 4 つの独立した領域へと厳格に分割した。

::: tip 体系構造図版：ISO 2022 8 ビット空間四分割モデル（Figure 1-2）
![Figure 1-2: Subdivisions of an 8-bit space in ISO 2022](/images/fonts-encodings/fig1-2-iso-2022-subdivisions.png)
*図 1-2：ISO 2022 による 8 ビット空間の細分化モデル（原著 Figure 1-2 より）。左半分（0x00–0x7F）は C0 制御領域と GL 図形左領域、右半分（0x80–0xFF）は C1 制御領域と GR 図形右領域。*
:::

これら 4 つの領域は明確な境界線によって隔離されている。
1. **C0 制御領域（`0x00`〜`0x1F`）**：32 個の端末制御文字を厳格に収容。デフォルトで古典的 ASCII 制御文字に束縛される。
2. **GL 図形左領域（Graphic Left, `0x20`〜`0x7F`）**：94 個または 96 個の図形文字を収容。デフォルトで無条件に ASCII 図形文字に束縛される（ASCII 互換性の死守）。
3. **C1 制御領域（`0x80`〜`0x9F`）**：拡張制御プロトコルのために追加確保された 32 個の高度制御文字領域。
4. **GR 図形右領域（Graphic Right, `0xA0`〜`0xFF`）**：各国の拡張文字集合を動的に投影するために開放された第二の図形文字ウィンドウ。

### 2. 状態機械スロットとエスケープ機構（Escape Sequences）
ISO 2022 の神髄は、**動的な状態機械スロット構造**にある。
* 端末内部には 4 つの図形文字集合スロット（$G_0, G_1, G_2, G_3$）が常駐する。
* 端末の起動時や動作時、**エスケープシーケンス（Escape Sequences、`ESC` に続く一連のバイト、例えば `ESC ( B` など）**を送信することにより、国際登録簿（ISO-IR）に登録された特定の文字集合（フランス文字集合、ギリシャ文字集合、さらには 2 バイト漢字集合など）を $G_0 \sim G_3$ の各スロットへ動的にマウントできる。
* 続いて、**シングルシフト指令（SS2, SS3）**や**ロッキングシフト指令（LS0, LS1, LS2, LS3）**を発行することで、タイピングの途中で特定のスロット $G_n$ を現在の GL または GR ウィンドウへと瞬時に切り替えて投影できる。

ISO 2022 の思想は極めて先進的であり、日本のインターネットメール標準である **ISO-2022-JP** や、現代の Linux 端末のエスケープシーケンス（ANSI Escape Sequences）の理論的バックボーンを形成した。

## ISO 8859 ファミリー：欧州諸言語の地理的分割

ISO 2022 は理論上無限の拡張性を備えていたが、パーソナルコンピュータ普及の黎明期において、その複雑なマルチ状態機械と連鎖的エスケープシーケンスは、当時の軽量 OS（DOS、初期 Unix）にとって過大な処理負荷であり、1 バイトのパケット脱落で端末全体がロックする危険を孕んでいた。

業界が切望したのは、**静的で決定的かつ単一バイトで完結する 8 ビット符号化標準**であった――エスケープ指令を送信することなく、上位 128 コードポイントが確定した拡張文字を表す方式である。

これに応え、ISO 委員会は 1987 年に名高き **ISO 8859 シリーズ標準** を始動させた。その鉄則は以下の通りである。**下位領域（0x00–0x7F）は標準 ASCII を完全に継承し、上位領域（0xA0–0xFF）は地理的地域に応じて 16 の互換性のない並行コードページに分割する！**

### 1. 旗艦規格：ISO 8859-1（Latin-1）と ISO 8859-15（Latin-9）
1987 年に公布された **ISO 8859-1（通称 Latin-1）** はシリーズの旗艦であり、西欧の主要言語（英、仏、独、西、葡、伊、蘭など）をカバーした。その GR 高位マトリクスは **Plate 1-4** に示されている。

::: tip 歴史的組版図版：ISO 8859-1（Latin-1）高位文字マトリクス（Plate 1-4）
![Plate 1-4: ISO 8859-1 (Latin-1) Table](/images/fonts-encodings/plate1-4-iso8859-1-table.png)
*図版 1-4：ISO 8859-1（Latin-1）高位領域（0xA0–0xFF）文字マトリクス（原著第 37 頁より）。西欧のアクセント文字、逆感嘆符・逆疑問符（¡, ¿）、ドイツ語エスツェット（ß）、マイクロ記号（µ）を含む。*
:::

しかし、ISO 8859-1 は制定当初から深刻な文化的不配慮と脱漏を犯していた。
* **フランス語合字の遺漏**：独立した `o` と `e` は収容したものの、フランス語において極めて重要な合字字母 **`œ` および大文字 `Œ`**（*cœur*, *œil* など）を欠落させた！ フランスのアカデミズムはこの脱落を自国文化に対する冒涜と激しく批判した。
* **オランダ語合字の遺漏**：オランダ語の二重字 `ĳ / Ĳ` が欠如していた。
* **フィンランド語／エストニア語字母の欠落**：キャロン（Caron）を伴う `š/Š` および `ž/Ž` が存在しなかった。
* **ユーロ記号の欠如**：20 世紀末の欧州経済通貨同盟の発足に伴い統一通貨**ユーロ（Euro, €）**が誕生したが、ISO 8859-1 制定当時は誰も使わない汎用通貨記号 `¤`（Currency Sign, `0xA4`）しか配置されていなかった。

この不備を救済するため、ISO は 1999 年に緊急改訂版 **ISO 8859-15（通称 Latin-9）** をリリースした。
* `0xA4` から記号 `¤` を廃止し、新しい**ユーロ記号 `€`** を配置。
* 使用頻度の低い記号枠を徴用し、フランス語合字 `œ / Œ`、フィンランド語字母 `š / Š` および `ž / Ž` を補完した。

### 2. 中東欧とバルカンの標準：ISO 8859-2（Latin-2）と ISO 8859-16（Latin-10）
ポーランド、チェコ、スロバキア、ハンガリー、クロアチアなどの中東欧スラブ諸言語に対応する **ISO 8859-2（Latin-2）** は、中欧諸言語特有の複雑なダイアクリティカルマーク（オゴネク鼻音化符 `ą, ę`、キャロン `č, š, ž`、二重鋭アクセント `ő, ű`）を集中的に収容した。

2001 年にシリーズの掉尾を飾って発表された **ISO 8859-16（Latin-10、東南欧）** の高位マトリクスは **Plate 1-5** に示されている。

::: tip 歴史的組版図版：ISO 8859-16（Latin-10）文字マトリクス（Plate 1-5）
![Plate 1-5: ISO 8859-16 (Latin-10) Table](/images/fonts-encodings/plate1-5-iso8859-16-table.png)
*図版 1-5：ISO 8859-16（Latin-10）高位マトリクス（原著第 39 頁より）。ルーマニア語、アルバニア語、スロベニア語など東南欧諸言語向けにカスタマイズされた。*
:::

ここにはタイポグラフィ史における数十年に及ぶ権利回復の物語が刻まれている。ルーマニア語の字母 `s` と `t` の下部には微小な**コンマ（Comma Below, `ș, ț`）**を付さねばならない。しかし初期の ISO 8859-2 では、西欧の学者たちがこれをフランス語の**セディーユ（Cedilla, `ş, ţ`）**と無頓着に混同してしまった。ISO 8859-16 の制定によって、正当なコンマ付き文字はようやく標準規格への復権を果たしたのである。

### 3. 南欧、地中海、北欧の各規格
* **ISO 8859-3（Latin-3）**：エスペラント語およびマルタ語向け。**Plate 1-6** 参照。トルコ語は当初この規格に組み込まれたが、必要な字母の欠如に対する激しい抗議を受け、ISO は単独で **ISO 8859-9（Latin-5、トルコ語専用）** を公布し、トルコ語固有の「点なし小文字 i（`ı`）と点つき大文字 I（`İ`）」のペア体系を解決した。

::: tip 歴史的組版図版：ISO 8859-3（Latin-3）地中海マトリクス（Plate 1-6）
![Plate 1-6: ISO 8859-3 (Latin-3) Table](/images/fonts-encodings/plate1-6-iso8859-3-table.png)
*図版 1-6：ISO 8859-3（Latin-3）高位マトリクス（原著第 40 頁より）。エスペラント固有のサーカムフレックス付き字母（ĉ, ĝ, ĥ, ĵ, ŝ, ŭ）を収容。*
:::

* **ISO 8859-10（Latin-6、北欧）**：**Plate 1-7** に示すように、アイスランド、フェロー諸島、極北ラップランドの先住民族サーミ語（Sami）、グリーンランドのイヌイット語（Inuit）のために策定された。

::: tip 歴史的組版図版：ISO 8859-10（Latin-6）北極圏マトリクス（Plate 1-7）
![Plate 1-7: ISO 8859-10 (Latin-6) Table](/images/fonts-encodings/plate1-7-iso8859-10-table.png)
*図版 1-7：ISO 8859-10（Latin-6）高位マトリクス（原著第 41 頁より）。古アイスランド語のソーン（Thorn, þ）や軟口蓋鼻音字母（Eng, ŋ）など、極北先住民族言語の書素を網羅。*
:::

* **非ラテン文字体系の限界**：
  * **ISO 8859-5（キリル文字）**：ソ連の 1987 年国家標準 GOST 19768 を継承したが、PC 上で Microsoft Windows-1251 と KOI-8 の挟み撃ちに遭い、普及には至らなかった。
  * **ISO 8859-6（アラビア文字）**：書道の現実から乖離し、孤立形の標称コードのみを記録して語頭・語中・語末の文脈依存変形を一切考慮しなかったため、印刷実務においては事実上の死文字規格となった。
  * **ISO 8859-7（ギリシャ文字）**：現代ギリシャ語のモノトニック（単アクセント）正書法のみをサポートし、古典古代ギリシャ語の豊かなポリトニック（鋭アクセント、鈍アクセント、曲アクセント、下付きイオタ）体系を完全に排除したため、欧州中の古典文献学者から指弾された。
  * **ISO 8859-8（ヘブライ文字）**：初期インターネットにおいて、左から右への視覚的順序（Visual Order）と右から左への論理的順序（Logical Order）の反転地獄に陥った。

## 極東の文字体系（The Far East）：漢字とマルチバイト符号化の挑戦

欧米の計算機科学者たちが 1 バイト 256 コードポイントの中でアクセント文字を巡り議論を交わしていた頃、東アジアの CJK（日中韓）諸国は、まったく桁違いの壮大な課題に直面していた。**漢字（Chinese Ideographs）は広大無辺であり、日常的な通用字だけでも数千、康熙字典や古典籍に至っては 5 万字を超える！**

単一バイト構造は完全に無力化し、東アジアの先駆者たちは ASCII を基盤としながら**マルチバイト符号化（Multi-Byte Encodings）**という前人未踏の領域を切り開かねばならなかった。

### 1. 日本の先駆的探求：JIS X 0208 と Shift_JIS
日本は東アジアにおいて最も早くコンピュータ用漢字標準を確立した。
* **JIS X 0208（区面点構造）**：名高き $94 \times 94$ の二次元マトリクス構造（94 の「区」、各区に 94 の「点」）を創案した。各漢字は 2 バイトで表され、第 1 バイトが区番号、第 2 バイトが点番号を表す（制御文字を避けるため各バイトに `0x20` のオフセットを加算）。
* **Shift_JIS（パソコン時代の工学的傑作）**：1980 年代の DOS/V や PC-98 端末において、ASCII の英語互換性を維持し、半角カタカナを円滑に入力し、同時に膨大な 2 バイト漢字を処理する必要が生じた。アスキーの西和彦と IBM は共同で **Shift_JIS（SJIS）** を開発した。
  * `0x00–0x7F` を ASCII として厳格に保持。
  * `0xA1–0xDF` を半角カタカナとして確保。
  * 膨大な JIS X 0208 漢字空間を、数学的シフト演算によって残された二つの間隙領域へと圧縮した。第 1 バイトは `0x81–0x9F` および `0xE0–0xFC` に収まり、第 2 バイトは `0x40–0x7E` および `0x80–0xFC` に配置される。テキスト処理ソフトウェアは、第 1 バイトが特徴的な範囲にあるかを検出するだけで、極めて少ないハードウェアリソースで 1 バイト文字と 2 バイト文字を継ぎ目なく切り替えることができた。

### 2. 中国大陸の標準進化：GB 2312 から GB 18030 へ
* **GB 2312-80（情報交換用漢字符号化文字集合・基本集）**：1980 年に国家標準総局が公布。6,763 字の簡体字漢字と 682 字の非漢字図形記号を収録。同様に区位コード設計を採用（94 区、各区 94 位）。Unix 環境においては、最上位ビット（MSB）を強制的に 1 に設定する（`0xA0` オフセットを加算する）ことで、著名な **EUC-CN** 標準へと発展した。
* **GBK 拡張仕様（1995）**：パソコンが政府や金融、出版システムに普及するにつれ、GB 2312 の 6,763 字では人名の希少文字、地名、古典籍、繁体字の需要を満たせなくなった。国家情報技術標準化技術委員会はマイクロソフト等と連携し、2 バイトの未使用空間を全面的に利用して、下位互換性を保ちながら 21,886 字の簡繁漢字および記号を収容した。
* **GB 18030（強制的国家統一規格）**：2000 年および 2005 年に公布された国家強制執行標準。1 バイト（ASCII）、2 バイト（GBK 互換）、4 バイト（Unicode 全平面の 160 万コードポイントを網羅）による可変長符号化体系を構築し、チベット文字、ウイグル文字、モンゴル文字、イ文字などの少数民族文字を正式に規格内へ包摂した。

### 3. 香港・台湾の繁体字中国語：Big5（大五碼）
1984 年、台湾の資訊工業策進会は主要コンピュータ企業 5 社（Acer、MiTAC、FIC 等）と共同で **Big5（大五碼）** を策定した。固定 2 バイト構造を採用し、第 1 バイトは `0xA1–0xF9`、第 2 バイトは `0x40–0x7E` および `0xA1–0xFE` で、13,060 字の繁体字漢字を収録した。Big5 は香港・台湾のパーソナルコンピュータ、BBS、初期インターネットコミュニティの隆盛と共に、繁体字圏におけるデファクトスタンダードとしての地位を確立した。

## マイクロソフト・コードページ（Code Page）と DOS 罫線文字アート

パーソナルコンピュータ用 OS の独占史において、マイクロソフトは「**コードページ（Code Page）**」という概念を創出し、DOS と Windows の二つの時代を通じてタイポグラフィに消し難い足跡を刻んだ。

### 1. MS-DOS Code Page 437 と罫線文字アート（ANSI Art）の黄金時代
1981 年、初代 IBM PC（Model 5150）が出荷された際、グラフィックカードの ROM チップに焼き付けられていたのは、マイクロソフトと IBM が共同カスタマイズした **Code Page 437（United States）** であった。その上位 128 文字の分布は **Plate 1-8** に示されている。

::: tip 歴史的組版図版：MS-DOS Code Page 437 文字および罫線マトリクス（Plate 1-8）
![Plate 1-8: MS-DOS Code Page 437 Table](/images/fonts-encodings/plate1-8-cp437-table.png)
*図版 1-8：MS-DOS Code Page 437 高位文字テーブル（原著第 45 頁より）。単線・二重線の罫線枠、シェーディングブロック、ギリシャ数学記号を完備。*
:::

この図版を観察すると、初期 DOS プログラマたちの驚くべき芸術的創意を味わうことができる。
* マウスもグラフィカルウィンドウもなく、解像度がわずか $80 \times 25$ の単色テキスト文字であった時代、デザイナーたちは `0xB0`〜`0xDF` に配置された **ボックス描画文字（Box-Drawing Characters）** を駆使した。
  * 単横線（`─`）、二重横線（`═`）、単縦線（`│`）、二重縦線（`║`）。
  * 四隅のコーナー、十字交差、T 字継手。
  * 陰影文字：薄い点状シェード（`░`）、中度シェード（`▒`）、高密度グリッド（`▓`）、完全な黒いブロック（`█`）。
* プログラマやデジタルアーティストは、純粋なテキスト文字を用いて、黒と緑の蛍光画面上に擬似 3D の立体浮彫シャドウを持つポップアップメニューやダイアログボックスを組み上げ、コンピュータサブカルチャー史に不滅の名を残す **ASCII / ANSI アート（BBS ANSI Art）** の文化を開花させた。

### 2. Code Page 850（Multilingual）のタイポグラフィの悲劇
しかし IBM PC がヨーロッパへ輸出された際、西欧のユーザーは CP437 に大量の必須アクセント文字が欠落していることに衝撃を受けた。マイクロソフトは直ちに **Code Page 850（MS-DOS Latin 1）** を投入した（**Plate 1-9** 参照）。

::: tip 歴史的組版図版：MS-DOS Code Page 850 多言語マトリクス（Plate 1-9）
![Plate 1-9: MS-DOS Code Page 850 Table](/images/fonts-encodings/plate1-9-cp850-table.png)
*図版 1-9：MS-DOS Code Page 850 文字テーブル（原著第 46 頁より）。西欧アクセント文字のために罫線枠記号の多くが強引に置き換えられた。*
:::

この妥協は破滅的な画面レイアウト崩壊を引き起こした。
* マイクロソフトはフランス語やドイツ語のアクセント文字を無理やり詰め込むため、**CP437 の二重罫線記号や交差継手の半分を無慈悲に削ぎ落とした**。
* その結果、米国のソフトウェア（Norton Commander や初期の Lotus 1-2-3 など）を欧州仕様の CP850 端末で実行すると、流麗なウィンドウ枠の交差点がすべて `ë` や `á` などのアクセント文字に化け、整然としていたメニュー枠組みは無残に四散崩壊してしまったのである！

### 3. Windows Code Page 1252（ANSI）の商業的突破
Windows 3.1 のグラフィカル GUI 時代に入ると、OS は真のビットマップおよびベクトルフォントを装備し、無骨なテキスト罫線文字を必要としなくなった。マイクロソフトは ISO 8859-1 への回帰を決断したが、ここで同社特有の商業的手法を披露した。**Windows Code Page 1252（通称 Windows ANSI）** の制定である（**Plate 1-10** 参照）。

::: tip 歴史的組版図版：Windows Code Page 1252（ANSI）拡張マトリクス（Plate 1-10）
![Plate 1-10: Windows Code Page 1252 (ANSI) Table](/images/fonts-encodings/plate1-10-cp1252-table.png)
*図版 1-10：Windows Code Page 1252 が C1 制御領域（0x80–0x9F）に独自開拓したタイポグラフィ文字特区（原著第 47 頁より）。*
:::

ISO 8859 規格において、`0x80`〜`0x9F` は非表示の通信制御文字のために予約された不可侵の「禁則区（C1 Zone）」であった。しかしマイクロソフトは、デスクトップ PC にそのような旧式端末制御命令は一切不要であることを鋭く見抜いていた。

マイクロソフトは大胆にも**この 0x80–0x9F の禁則区を全面的に占拠し**、その中に本格的な出版組版に不可欠な高品質印刷文字を詰め込んだ。
* 正真正銘のタイポグラフィ用二重引用符（`“ ”`）および単一引用符（`‘ ’`）。
* 出版水準のエムダッシュ（Em-dash, `—`）およびエンダッシュ（En-dash, `–`）。
* 商標記号（`™`）、パーミル記号（`‰`）、行頭ビュレット（Bullet, `•`）。
* そして後に、誕生したばかりのユーロ記号（`€`）を真っ先に `0x80` に固定配置した。

Windows 95/98 の圧倒的な市場シェアにより、Code Page 1252 は黎明期インターネットにおける事実上の Web ページ標準文字セットとなり、Unix や Mac 環境で不正文字を生じさせて無数のクロスプラットフォーム開発者を悩ませることとなった。

## Apple コンピュータの美学的規範：Classic Mac OS MacRoman

IBM PC の実利主義や妥協とは対照的に、Apple 社は 1984 年の初代 Macintosh 誕生の日から、その遺伝子をタイポグラフィ芸術とデスクトップパブリッシング（DTP）に深く根差していた。スティーブ・ジョブズがリード大学時代に聴講したカリグラフィ講義の美意識は、**MacRoman 文字体系**へと直接結実した（**Plate 1-11** 参照）。

::: tip 歴史的組版図版：Classic Mac OS MacRoman 文字マトリクス（Plate 1-11）
![Plate 1-11: Classic Mac OS MacRoman Table](/images/fonts-encodings/plate1-11-macroman-table.png)
*図版 1-11：Classic Mac OS MacRoman 8 ビット文字符号化マトリクス（原著第 48 頁より）。*
:::

MacRoman マトリクスを子細に観察すると、高品質なタイポグラフィに対する Apple の並々ならぬ執念が伝わってくる。
* 1980 年代初頭にしてすでに、古典的欧文組版の**合字 `fi`（`0xDE`）および `fl`（`0xDF`）**をシステム標準文字セットにハードコードしていた。
* 完備された微積分数学記号（$\pi, \int, \sqrt{}, \Delta, \sum$）。
* 極めて純粋なタイポグラフィ的三点リーダー（`…`）、アクセント記号、著作権表示。
* さらに `0xF0` には、同社独自の**リンゴのブランドマーク（Apple Logo, ）**が埋め込まれていた！

組版師が Macintosh 上で Aldus PageMaker や QuarkXPress を用いて雑誌を編纂するとき、MacRoman は比類なき美学的整合性を発揮し、Macintosh を全世界の出版・印刷業界における揺るぎない王者の座へと押し上げたのである。

## 電子メールとインターネット MIME プロトコルの伝送革命

ARPANET が現代のインターネットへと急速な変貌を遂げる中で、人類はかつてない全地球規模の異機種間文字交換の危機に直面した。

初期のインターネット電子メールのルーティングは、1982 年に制定された **RFC 821（SMTP プロトコル）** に基づいていた。このプロトコルは厳格に「純粋な 7 ビット伝送路（7-bit Transport）」として設計されていた。冷戦時代の旧式ゲートウェイやルータのハードウェアマイクロコードは、デフォルトで**各バイトの最上位ビットを無残に切り落とす（8th-bit Stripping）**動作を行ったのである！ `0x7F` を超える文字を含む 8 ビットメールは、大洋を越えるルーティングホップを通過する過程で、すべてのアクセント文字や漢字が最上位ビットを剥ぎ取られ、一瞬にして判読不能なゴミへと変貌した。

多言語通信の崩壊を防ぐため、IETF（インターネット技術標準化タスクフォース）は 1993 年から 1996 年にかけて、画期的な **MIME 体系（Multipurpose Internet Mail Extensions, RFC 2045–2049）** を打ち出した。

### 1. MIME の中核ヘッダ構造
MIME はプレーンテキストメールに前例のないメタデータヘッダを付与した。
```http
MIME-Version: 1.0
Content-Type: text/plain; charset="ISO-8859-1"
Content-Transfer-Encoding: quoted-printable
```

### 2. 二大コンテンツ転送符号化アルゴリズム
* **Quoted-Printable 符号化（軽度のアクセント付きテキスト向け）**：
  * 標準の 7 ビット ASCII 文字は平文のまま透過出力する。
  * 127 を超える 8 ビットバイト（および等号自身）は、等号と 2 桁の大文字十六進数へとエスケープする（例えば Latin-1 で `0xE9` の文字 `é` は `=E9` と符号化される）。
  * 行末にソフト改行（`=`）を挿入し、いかなる 1 行の長さもルータの物理的上限である 76 文字を決して超えないように保証する。
* **Base64 符号化（非ラテン語系テキストおよびバイナリ添付ファイル向け）**：
  * 純粋なビットストリーム再構成アルゴリズムを採用。入力ストリーム内の連続する 3 つの 8 ビットバイト（合計 $3 \times 8 = 24$ ビット）を、連続する 4 つの 6 ビット単位（$4 \times 6 = 24$ ビット）へと再分割する。
  * 各 6 ビット単位の値は $0 \sim 63$ の範囲に収まり、極めて安全な 64 個の ASCII 文字（大文字 `A–Z` が 0–25、小文字 `a–z` が 26–51、数字 `0–9` が 52–61、プラス `+` が 62、スラッシュ `/` が 63）からなるテーブルへと直接写像される。
  * 末尾が 3 バイトに満たない端数は、パディング文字である等号（`=`）で埋められる。

Quoted-Printable と Base64 の導入により、非英米圏の人々は歴史上初めて、7 ビットの古いインターネット回線を通じて、自国語のアクセント詩文、ロシア語の詩、そして中国語の書簡を、大陸を越えて安全無傷に伝送できるようになったのである！

## 黎明期ワールドワイドウェブ（The Web）の文字集合交渉と歴史的教訓

1990 年代にワールドワイドウェブ（WWW）が指数関数的な爆発を見せた際、ハイパーテキスト転送プロトコル（HTTP）とハイパーテキスト記述言語（HTML）は、MIME の文字セット宣言思想を全面的に継承した。

### 1. 二重の文字セット宣言メカニズム
Web サーバーは HTTP レスポンスヘッダを通じてブラウザにエンコーディングを通知する。
```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=Shift_JIS
```
さらに HTML 文書内部において、開発者はフェイルセーフ防御としてメタデータタグを埋め込むことができる。
```html
<meta http-equiv="Content-Type" content="text/html; charset=GB2312" />
```

### 2. HTML 文字実体参照（Character Entity References）
特定のエンコーディングのみをサポートする Web ページにおいて、稀少な外国語文字を一時的に混在させるため、HTML 規格は実体エスケープ機構を導入した。
* **名前付き実体参照（Named Entities）**：例えば `&eacute;` で `é` を、`&copy;` で `©` を表現。
* **十進数値実体参照（Decimal Numeric Entities）**：例えば `&#233;` でコードポイントを直接指定。
* **十六進数値実体参照（Hexadecimal Entities）**：`&#xE9;` で十六進コードポイントを指定。

## 歴史の省察：バベルの塔崩壊前の最後の残響

20 世紀末のデジタル世界の版図において、人類文明は互いに通じ合わない数百もの「孤島」へと分断されていた。
* 同一の十六進バイト `0xE9` であっても：
  * **ISO 8859-1（西欧）** では、優美なアクセント字母 **`é`** を意味した。
  * **ISO 8859-5（キリル文字）** では、ロシア文字 **`щ`** を意味した。
  * **ISO 8859-7（ギリシャ文字）** では、ギリシャ文字 **`θ`** を意味した。
  * **ISO 8859-8（ヘブライ文字）** では、ヘブライ文字 **`ט`** を意味した。
  * **MS-DOS Code Page 437** では、微積分数学記号 **`Θ`** を意味した。
  * そして **MacRoman** では、カリフォルニアの数学者が愛用する上付き記号を意味していた！

受信側のコンピュータ環境に適切なコードページが存在しない場合、あるいは Web サーバーが誤った HTTP ヘッダを返した場合、本来格調高かった文章は画面全体を埋め尽くす解読不能な「文字化け」（Mojibake）の廃墟へと瞬時に崩壊した。

多言語が同一文書内に混在する場合（例えば、英仏両語で記述されたロシア語と日本語の漢学研究論文など）、従来の単一バイトや地域的マルチバイト符号化は完全に限界に達した。いかなるシステムも、単一の 8 ビットコードページ内でキリル文字、仮名、漢字、アラビア連結文字を同時に調和させることは不可能だったからである。

世界は、人類のあらゆる消滅した古代文字、現生する文字体系、科学記号、絵文字を統括できる、普遍的で大一統の文字集合を渇望していた。

コンピュータの文字のバベルの塔に終止符を打つ壮大なる革命――**Unicode と国際符号化文字集合（Universal Character Set, UCS）**が、地平線の彼方に黎明の光を放ち始めていたのである。
