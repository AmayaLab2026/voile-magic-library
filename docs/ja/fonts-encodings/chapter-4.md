# 第4章 · 正規化、双方向アルゴリズムと東アジア文字体系
### Chapter 4: Normalization, bidirectionality, and East Asian characters
**著者：ヤニス・ハラランブス 博士（Yannis Haralambous, Ph.D.）**  
*『フォントとエンコーディング』（Fonts & Encodings）原著 127–158 ページより*

*翻訳者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

---

Unicode 文字の基本定義、低層の符号化形式、および巨視的なプレーン構造を理解した上で、我々はテキスト組版における極めて難解な 3 つの計算論的挑戦に対峙しなければならない。すなわち、**文字シーケンスの等価正規化**、**多言語混植における双方向フローアルゴリズム**、そして**東アジア表意漢字および音節文字の複雑な幾何学的トポロジー**である。

これら 3 つの領域は、現代デジタルテキスト処理の中核を成している。正規化が存在しなければ、検索エンジンは不均一な膨大なテキスト群に確定的な索引を構築できず、双方向アルゴリズムがなければ、アラビア文字やヘブライ文字が同一段落内で西洋文字と調和して共存することは永遠に不可能であり、東アジア文字体系に対する深い数理的モデルがなければ、数万の漢字を抱える広大な情報世界は文字爆発の泥沼に沈むこととなる。

## 分解と正規化（Decompositions and Normalizations）

Unicode は過去のレガシー規格から多数の「事前合成済み文字」（Precomposed Characters、例えばアクセント付きラテン文字 ‘é’ や ‘ü’）を継承すると同時に、「基底文字 ＋ 結合変音記号」（Base Character + Combining Marks）による動的結合機構も提供している。

ここから深刻な数学的課題が生じる。人間の視覚と意味論において完全に同一である単一の文字単位に対して、コンピュータ内部では複数の全く異なるバイナリコードポイント列が存在し得るのである！例えば抑音符付き文字 ‘è’ は以下のように表現できる：
* 単一の合成済み文字：`U+00E8`（LATIN SMALL LETTER E WITH GRAVE）；
* 基底文字と結合記号の列：`U+0065`（LATIN SMALL LETTER E）+ `U+0300`（COMBINING GRAVE ACCENT）。

システムがこれらのシーケンスを一意に正規化しなければ、文字列比較、ハッシュ探索、およびデータベースの主キー照合は完全に破綻する。このため、Unicode 共同創始者マーク・デイビス（Mark Davis）とマルティン・デュルスト（Martin Dürst）は共同で **Unicode 標準附属書第 15 号（UAX #15: Unicode Normalization Forms）** を策定した。

### 結合文字と正準結合クラス（Combining Characters & Combining Classes）

基底文字に複数の異なる方向の変音記号が付随する場合（ベトナム語や古典ギリシャ語の多重アクセント文字など）、データストリーム内における記号の前後順序は任意であってはならない。

言語学およびタイポグラフィの知見によれば、変音記号は直交する方位クラスに分類できる。異なる方位（例えば一方が文字の下、もう一方が文字の上）にある場合、それらの適用順序は最終的な印刷形状に影響を与えないが、二つの記号が同一の物理方位にある場合（例えば文字の上に順に積み重なる場合）、下から上へのスタック順序は決定的な意味を持つ！

これを数学的に厳密に定式化するため、Unicode は各結合文字に $0 \sim 255$ の整数値属性——**正準結合クラス（Canonical Combining Class, ccc）**——を割り当てている：
* **Class 0（Spacing / Base Characters）**：すべての基底文字、不可視制御文字、通常のスペース；
* **Class 1（Overlay）**：文字の中央を貫く重ね打ち記号（取り消し線、スラッシュなど）；
* **Class 7（Nukta）**：インド系文字の子音下部に添えられる発音微調整点；
* **Class 8（Kana Voicing）**：日本語仮名の濁点（゛）および半濁点（゜）；
* **Class 9（Virama）**：インド系文字で固有母音を消去し結合文字を形成するハラント（Halant / Virama）；
* **Class 200–214（Fixed Position Marks）**：ヘブライ語聖書朗唱記号などの固定位置記号；
* **Class 216（Attached Below / ATBL）**：文字下部に密着する記号（ルーマニア語の下コンマなど）；
* **Class 218（Attached Below Right）**：文字右下部に密着する記号；
* **Class 220（Below / B）**：文字の直下に位置する変音符（下加点 `U+0323`、セディージャなど）；
* **Class 222（Below Right / BR）**：文字右下に位置する独立変音符；
* **Class 228（Above / A）**：文字の直上に位置する変音符（鋭音符、抑音符、マクロン `U+0304`、チルダなど）；
* **Class 230（Above Right / AR）**：文字右上に位置する変音符；
* **Class 232（Double Above / DA）**：隣接する 2 文字にまたがる二重変音記号；
* **Class 240（Iota Subscript）**：古代ギリシャ語特有の下付きイオタ（Iota Subscript）。

### 正準順序付けアルゴリズム（Canonical Ordering Algorithm）

結合クラスに基づき、Unicode は決定論的な**正準順序付けアルゴリズム（Canonical Ordering Algorithm）**を確立した：
1. 文字列を左から右へと走査する；
2. 基底文字（`ccc = 0`）の位置は完全に固定する；
3. 基底文字に後続する連続した結合文字シーケンスを、**正準結合クラス（ccc）の昇順にソートする**；
4. 二つの隣接する結合文字の `ccc` 値が完全に等しい場合は、元の相対的な前後順序を維持する（同一方向の積み重ね関係を保持するため）。

例えば、文字 ‘a’ に下加点（`U+0323`，`ccc = 220`）と上部マクロン（`U+0304`，`ccc = 228`）が付随する場合：
* シーケンス 1：`U+0061` + `U+0323`（下点 220）+ `U+0304`（長音 228）；
* シーケンス 2：`U+0061` + `U+0304`（長音 228）+ `U+0323`（下点 220）。  
$220 < 228$ であるため、アルゴリズムの適用により、シーケンス 2 は確定的にシーケンス 1 へと並べ替えられる！

### 正準分解と互換分解

Unicode は 2 つの異なるレベルの文字分解を定義している：
* **正準分解（Canonical Decomposition）**：  
  言語学および組版機能において**完全に等価であり、不可逆な情報損失が一切ない**文字ペアに対する分解。例えば ‘é’（`U+00E8`）を ‘e’（`U+0065`）+ 鋭音符（`U+0300`）へと分解する；
* **互換分解（Compatibility Decomposition）**：  
  組版スタイル、歴史的活字、または過去の工業標準において微細な視覚的差異を有するが、プレーンテキストの意味論において等価な文字に対する分解。例えば：
  * 日本の組版合字 ‘㎦’（`U+33A6`）を ‘k’ + ‘m’ + 上付き ‘3’（`U+00B3`）を経て ‘3’ へと分解；
  * ローマ数字 ‘Ⅳ’（`U+2163`）を ‘I’ + ‘V’ へと分解；
  * 欧文合字 ‘ﬁ’（`U+FB01`）を ‘f’ + ‘i’ へと分解；
  * 全角英字 ‘Ａ’（`U+FF21`）を通常のアスキー ‘A’ へと分解；
  * 丸囲み数字 ‘①’（`U+2460`）を数字 ‘1’ へと分解。

### 4 大正規化形式（The Four Normalization Forms）

| 正規化形式 | 英語名称 | 中核機構 | 典型的な適用領域 |
| :--- | :--- | :--- | :--- |
| **NFD** | Normalization Form D | 正準分解（Canonical Decomposition）＋ 結合クラス昇順ソート | 言語学的音声分析、変音符抽出、検索エンジン低層 |
| **NFC** | Normalization Form C | NFD 正準分解を実行後、文字を再び**正準合成（Canonical Composition）** | **W3C、HTML、XML および現代 Web の標準デフォルト** |
| **NFKD** | Normalization Form KD | 互換分解（Compatibility Decomposition）＋ 結合クラス昇順ソート | 意味論的テキスト抽出、あいまい検索、平文テキスト化 |
| **NFKC** | Normalization Form KC | NFKD 互換分解を実行後、正準合成を実行 | 全文検索エンジンの転置インデックス作成、識別子正規化 |

## 双方向組版アルゴリズム（The Bidirectional Algorithm / UAX #9）

西洋文字からなる単一方向の世界において、テキストの流れは常に左から右（LTR）である。しかし近東文明において、アラビア文字、ヘブライ文字、シリア文字、およびターナ文字はすべて右から左（RTL）へと書かれる。

現代の学術文献、条約文書、または Web ページにおいて、英語、ヘブライ語、アラビア語、および数式が混在するとき、計算機組版は極めて過酷な挑戦に直面する：
1. **段落の主方向とインラインの入れ子方向との衝突**；
2. **右から左へと流れるテキスト中に埋め込まれたアラビア数字は、左から右へと書かれる！**
3. **括弧、引用符、数学不等号はテキスト方向に応じて視覚的に物理的な幾何鏡像反転を行わねばならない！**
4. **複数行組版における改行（Line Breaking）位置の双方向境界の再構成！**

これが著名な **Unicode 双方向組版アルゴリズム（Unicode Bidirectional Algorithm、通称 Bidi アルゴリズム、UAX #9）** である。

### 段落組版のマクロフローとミクロ改行

著者は極めて示唆的な実験を提示している：英文（LTR）の中に右から左へと書かれたアラビア語の一節が埋め込まれていると仮定し、小文字の逆順綴りでその流れをシミュレートすると、以下のようになる：
> First second third fourth hthgie htneves htxis htfif  
> htneetriht htflewt htnevele htnet htnin fourteenth  
> fifteenth sixteenth seventeenth.

第 2 行の配置に注目されたい：これは右から左へと流れる段落であるため、第 1 行の右端で改行が発生した際、テキストは第 2 行の左端からではなく、**第 2 行の最右端から左に向かって書き続けられる**！そして埋め込み段落が終わると、英文（`fourteenth ...`）は再び左端から配置される。厳密な数学的アルゴリズムがなければ、改行座標の計算は視覚的な大混乱を引き起こす。

さらに数字の扱いは輪をかけて複雑である：アラビア語やヘブライ語において、**数字はいかなる場合も左から右へと書かれる**。例えば著者の誕生日は：
`Friday, February 16, 1962`
アラビア語において単語部分は右から左であるが、数字 `1962` と `16` は左から右へと維持される。すなわち、すべての数字列はミクロな左横書きの「孤島」として扱われるのである。

### 双方向文字型（Bidirectional Character Types）

Unicode は全 111 万コードポイントに対し、3 大分類 19 種の双方向型を厳密に割り当てている：

1. **強文字型（Strong Types）**：固有的かつ主導的な方向性を持つ：
   * **L（Left-to-Right）**：すべてのラテン文字、キリル文字、ギリシャ文字、東アジア漢字および仮名；
   * **R（Right-to-Left）**：ヘブライ文字および関連セム系文字；
   * **AL（Arabic Letter）**：アラビア文字および専用約物。
2. **弱文字型（Weak Types）**：文脈に依存して方向性が定まる：
   * **EN（European Number）**：欧文数字（`0`–`9`）；
   * **ES（European Number Separator）**：数字の符号（`+`、`-`）；
   * **ET（European Number Terminator）**：通貨記号およびパーセント（`$`、`%`、`€`）；
   * **AN（Arabic-Indic Number）**：アラビア・インド数字（`٠`–`٩`）；
   * **CS（Common Number Separator）**：数字区切り記号（コロン、カンマ、小数点など 11 文字）；
   * **NSM（Non-Spacing Mark）**：結合文字および異体字セレクタ；
   * **BN（Boundary Neutral）**：制御文字、言語タグなど。
3. **中立文字型（Neutral Types）**：固有の方向性を持たず、周囲の強文字に従う：
   * **B（Paragraph Separator）**：段落区切り（改行 `\r`, `\n`）；
   * **S（Segment Separator）**：タブ文字；
   * **WS（Whitespace）**：非ゼロ幅の通常スペース；
   * **ON（Other Neutral）**：汎用約物、数学記号、幾何図形など（3,007 文字）。
4. **明示的書式制御文字（Explicit Formatting Codes）**：  
   `LRE`、`RLE`、`LRO`、`RLO`、`PDF` の 5 大制御文字。

### 双方向アルゴリズムの 6 大解決ステップ（The Six Steps of UAX #9）

* **ステップ 1：段落基本レベル（Base Level）の決定**：最初の強文字が L なら $S_0 = 0$、R/AL なら $S_0 = 1$；
* **ステップ 2：明示的埋め込みレベルの解決**：方向スタック（最大 125 レベル）によるプッシュ／ポップ；
* **ステップ 3：弱文字型の解決（W1〜W7）**：NSM の継承、EN の AN 変換、AL の R 変換、数値区切り記号の吸収など；
* **ステップ 4：中立文字型の解決（N1〜N2）**：前後の強文字方向に基づく中立区間の決定；
* **ステップ 5：暗黙的レベルの解決（I1〜I2）**：確定した文字型に基づくレベルの微調整；
* **ステップ 6：行内並べ替えとミラー反転（L1〜L4）**：最高レベルから最低レベルへと**部分文字列を階層的に反転（Reverse）**させ、鏡像属性文字をグリフ反転する。

### 鏡像属性（Mirroring & BidiMirroring.txt）

左丸括弧 ‘(’ は西洋言語において「文の開始」を象徴するが、右から左へと流れる文書において「文の開始」は物理空間の右側にある！したがって、RTL テキストにおいて ‘(’ に出会った組版エンジンは、右に凸の弧を描くのではなく、動的に左に凸の ‘)’ へと反転しなければならない。

Unicode は標準化マッピングファイル `BidiMirroring.txt` において、**320 ペアの厳密な幾何鏡像文字**を規定している：括弧類（`()`、`[]`、`{}`、`〈〉`、`«»`）、数学関係演算子（`<` と `>`、`≤` と `≥`）、および幾何矢印（$\leftarrow$ と $\rightarrow$）。

## 東アジア書記体系（East Asian Scripts）

### 中日韓漢字表意文字（Ideographs of Chinese Origin / CJK）

漢字は古代中国の甲骨文・金文に発し、数千年の変遷を経て朝鮮半島、日本列島、ベトナムへと伝播し、「漢字文化圈」を形成した。

しかし漢字は数十のアルファベットからなる線形文字とは根本的に異なり、膨大な文字数、2 次元の正方形構造、および多音多義の表意文字体系である。『康熙字典』だけでも 47,035 文字を収録し、学術・古典整理における総数は 10 万字を優に超える！

Unicode は中日韓の専門家からなる**表意文字作業部会（Ideographic Rapporteur Group, IRG）**を設置し、計算機史上最大の**中日韓漢字統合（Han Unification）**を完遂した：
* 『康熙字典』の 214 部首およびストロークトポロジーに基づく統合規則の確立；
* 統合漢字データベース（Unihan Database）の構築による、北京語、広東語、唐代中古音、日本語の音読み・訓読み、韓国語音、ベトナム語音の完全な相互索引付け。

#### 漢字構造記述文字（Ideographic Description Characters, IDC）

未収録の稀少漢字（外字、Gaiji）を記述するため、Unicode は $0\text{x2FF0} \sim 0\text{x2FFB}$ に **12 個の表意文字記述文字（IDC）**を導入した。これらは前置記法（Prefix Notation）により漢字の 2 次元幾何組み立て構造を記述するオペレータである（例：⿰ 禾 口 $\to$ 和、⿴ 囗 大 $\to$ 因、⿺ 辶 巛 $\to$ 巡）。

### 文字記述言語（Character Description Language, CDL）

トム・ビショップ（Tom Bishop）とリチャード・クック（Richard Cook）によって開発された **CDL（Character Description Language）** は、XML 構文を用いて漢字の幾何学的骨格を精密に記述する：
1. **部品再利用（Component-based）**：既成の漢字や部首と相対座標による合成；
2. **純粋筆画組み立て（Stroke-based）**：筆画種別コードと制御点座標による直接描画。

CDL は漢字のあらゆる筆画を **30 種の基本ストロークコード**（横 `h`、提 `t`、豎 `s`、豎鉤 `sg`、撇 `p`、捺 `n`、横折 `hz`、横折鉤 `hzg` など）へと高度に抽象化している。

### 朝鮮語ハングル（Hangul）とアルファベット算術

東アジアのすべての書記体系の中で、朝鮮語の**ハングル（Hangul）**は人類の文字史上最も卓越した理性的設計と数理的純粋性を誇る。

1443 年、李氏朝鮮第 4 代国王**世宗大王（Sejong the Great）**は、集賢殿の学者たちとともに『訓民正音』（Hunminjeongeum）を創製した。17 の子音と 11 の母音からなるこの体系は、音声学と宇宙観の結晶である：
* **子音の生理的発声器官の幾何象形**：舌根が喉を塞ぐ形状（ㄱ）、舌先が上歯茎に触れる形状（ㄴ）、口の形状（ㅁ）、歯の形状（ㅅ）、喉の形状（ㅇ）。これに画を加えて激音・有気音（ㅋ, ㄷ, ㅌ, ㅂ, ㅍ）を表現する；
* **母音の天地人三元宇宙観**：天の丸（·）、平らな地（ㅡ）、直立する人（ㅣ）の組み合わせ（ㅗ, ㅜ, ㅏ, ㅓ）。

### 現代ハングル音節ブロックのデジタルアルゴリズム芸術

ハングルは音素文字（Jamo）でありながら、初声子音（Initial, $L$）、中声母音（Medial, $V$）、および終声子音（Final, $T$）を 1 つの正方形音節ブロックへと厳密に組み立てる：

$$S = L + V + T^*$$

初声 19 種、中声 21 種、終声 28 状態（無終声を含む）の組み合わせ総数は正確に：

$$N = 19 \times 21 \times 28 = 11{,}172$$

Unicode は BMP の $0\text{xAC00} \sim 0\text{xD7A3}$ にこの 11,172 個の合成済み音節ブロックを完全に配置した。いかなるハングル音節のコードポイントも、極めて優雅な一次代数方程式によって双方向計算が可能である：

$$\text{CodePoint} = \text{0xAC00} + (L_{\text{index}} \times 588) + (V_{\text{index}} \times 28) + T_{\text{index}}$$

（ここで $588 = 21 \times 28$）。例えば「한글」（Hangul）の「한」（$L=18, V=0, T=4$）は `U+D55C`、「글」（$L=0, V=18, T=8$）は `U+AE00` として瞬時に計算される。

---

文字の正準等価判定から、ユーラシア・アフリカ大陸を跨ぐ双方向の複雑な改行フロー、そして東アジア漢字の幾何骨格とハングルの代数的音節組立に至るまで、第 4 章は現代デジタルフォントの背後にあるスリリングなアルゴリズムの全景を提示した。

しかしながら、これらすべての高層テキスト規格は、最終的に OS 低層のグラフィックウィンドウおよび組版サーバへと受け渡され、実際にラスタライズ描画されなければならない。Unix / Linux の長きにわたる進化の歴史において、グラフィックシステムはどのようにフォントを発見・選択し、X Window のスクリーン上へとグリフを投射してきたのか？

これこそが、我々が**第 8 章：X Window システムにおけるフォント管理アーキテクチャ**において深く探索する UNIX エンジニアの世界である。
