# 第13章：ラスタライズ最適化とヒンティング技術（Hinting）

**ヤニス・ハラランブス（Yannis Haralambous, Ph.D.）著**  
*『Fonts & Encodings』第 505–548 頁より*

*訳者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

---

もしフォントだけの世界が存在するならば、その『創世記』にはきっと次のような言葉が刻まれていたに違いない——「**なんとなれば汝はピクセルなれば、ピクセルに帰るべきなり**」（*for pixels thou art, and unto pixels thou shalt return*）。

実のところ、私たちはしばしば忘れてしまいがちである。グリフのベジェ曲線輪郭を表現するあらゆる精緻な数学的構造の究極の目的とは、何よりもまずピクセルによって構成される画像を生成することにほかならない。もし私たちのディスプレイやプリンタが、最初からたった一つの固定されたフォントサイズ、たった一つの決まった解像度しか持たなかったならば、アウトラインフォントなどという技術はそもそも一切必要なかったはずである——純粋なビットマップ（Bitmaps）だけで、すべての要求を完璧に満たすことができたからだ。アウトラインが存在する唯一の理由、それはフォントが刻々と変化する物理的利用環境に柔軟に適応し、レンダリングの瞬間にその場で適切なビットマップを動的に生成できるようにするためである。

「ベジェ曲線輪郭（ベクトル）」の状態から「ビットマップ点陣」の状態へと移行するこの極めて重要かつ決定的な処理過程を、コンピュータグラフィックスでは**ラスタライズ**（Rasterization）と呼ぶ。画面上に最終的に結像するテキストの美しさと読みやすさは、すべてこのラスタライズアルゴリズムの成否にかかっている。

本章の真の価値を理解するためには、まずラスタライズがどのように行われるのかを冷静に見つめ直さなければならない。

幸いなことに、物理世界のピクセルは規則正しく等間隔に並んだ正方格子の形状をしている。それゆえ、私たちは幾何学的に完璧なグリフのアウトラインの背後に、微小な格子状のグリッドが敷き詰められている光景を思い描くことができる。このとき、ラスタライズの作業とは、**グリッド上の特定の正方形（ピクセル）を黒く塗りつぶし、アウトラインの形状を可能な限り忠実に近似すること**に帰着する。「いくつかの正方形を塗りつぶす」——理屈は極めて単純だが、問題は「一体どの正方形を塗りつぶすべきか？」という点にある。まさにここに、あらゆる技術的苦闘が潜んでいる。

最も素朴で機械的なアプローチを採るならば、「**ピクセルの幾何学的中心点がアウトラインの内部（または境界線上）にあるとき、そのピクセルを黒く塗りつぶす**」という規則が考えられる。しかし、この単純な「中心点包含判定法」は極めて脆く、不安定である。アウトラインの位置がほんのわずかにズレただけで、一連のピクセル列の中心が一斉に輪郭内に転がり込んで真っ黒になってしまったり、あるいは逆にすべて輪郭の外に放り出されて白く抜け落ちてしまったりする。

文字の高さがわずかに異なる5つの大文字「H」をこの中心点判定法で低解像度ラスタライズしてみると、戦慄すべき現象が露呈する。
最初の2つの「H」では、2本の縦ステムの太さが不揃いになり（一方が2ピクセル、他方が1ピクセル）、さらに中央の水平クロスバーに至っては、1ピクセルから2ピクセルへと膨張したかと思えば、続く文字では再び突如として1ピクセルへと縮小してしまう！

**結論は冷酷である。たとえ数学的にどれほど完璧なアウトラインを描き上げたとしても、劣悪なラスタライズはその努力のすべてを一瞬で水泡に帰せしめ、完全に予測不能な視覚的破滅をもたらす。** お粗末にレンダリングされたグリフが見逃されることを期待して手をこまねいているわけにはいかない。タイポグラフィの世界では、わずかでも不都合が生じれば読者の目は即座にそれを見抜く。何より、それは私たちが心血を注いだフォントに対する冒涜である。何時間もかけて完璧な輪郭を磨き上げた以上、劣悪なラスタライズを決して受け入れるわけにはいかない。私たちは行動を起こさなければならない——断固たる行動を！

デジタルフォントの三大主要潮流（METAFONT、PostScript Type 1、TrueType）は、この課題に対してそれぞれまったく異なる解決哲学を提示した：

* **METAFONT の哲学**：METAFONT においては、ラスタライズのプロセス——ひいてはグリフ生成のすべて——がプログラミングコードによって完全に直接制御される。その仕組みは極めて特異であり、**ビットマップはフォントが実際に利用される前に、METAFONT コンパイラによってオフラインで事前に生成される。** 特定のディスプレイやプリンタの物理的ハードウェア特性さえあらかじめ判明していれば、METAFONT はその機器に極限まで最適化されたビットマップフォントを完璧に焼き出すことができる。それゆえラスタライズ品質は完璧を極めるが、その代償として、フォントは特定の出力装置のハードウェア仕様に完全に縛り付けられることになる。METAFONT が開発された時代、この制約は何ら問題にならなかった。手元の端末やレーザープリンタ専用にフォントを焼き出せばよかったからである。  
  しかし、ワールドワイドウェブ（Web）の爆発的普及によって、この静的な調和は根底から覆された。現代の「電子文書」は、いかなるプラットフォームであっても即座に普遍的に閲覧・印刷可能でなければならず、特定のハードウェアに依存することは許されない。それゆえ、METAFONT は本質的に Web と相容れないものとなった。本書の付録 F において、METAFONT の内部アルゴリズムについて詳述する。
* **PostScript Type 1 / OpenType CFF の哲学**：PostScript フォントにおいては、ラスタライズの最適化は**ヒント**（**Hints**）を通じて行われる。Adobe の戦略は極めて巧妙であった。彼らはラスタライズエンジン内部の具体的なブラックボックスの挙動を仕様として厳密に開示することを頑なに拒み、フォント設計者に対しては、フォントの大まかな幾何学的特徴を「控えめに示唆する」程度の権限しか与えなかった。あとはレンダリングエンジン側がそれを良きに計らって解釈してくれることを祈るのみである。このアプローチはプログラマからは不満の嵐を巻き起こしたが、フォントデザイナーたちからは大いに歓迎された——なぜなら、ピクセル単位での最適化という過酷な責務からデザイナーを解放してくれたからである！ 設計者はブラックボックスであるエンジンにいくつかの幾何学的ヒントを放り込むだけでよい。表示が破綻したとき、Adobe は「デザイナーが適切なヒントを与えなかったせいだ」と言い、デザイナーは「Adobe のラスタライザが無能なせいだ」と互いに指を指し合うことになる。しかし、PostScript フォントは主として高精度の電算写植（イメージセッタ）で用いられていたため、この曖昧さは大した問題にはならなかった。数千 DPI の解像度において、1ピクセルの差など人間の肉眼で知覚することは不可能だからである。付録 C において、ヒントの完全な技術仕様を解説する。
* **TrueType の哲学**：TrueType フォントは、曖昧なブラックボックスを完全に排除し、アセンブリ言語に酷似した**命令セット**（**TrueType Instructions** / バイトコード）を採用して、離散ピクセルグリッドに対する輪郭制御のすべてを厳密に定義する道を選んだ。ここには一切の秘密のブラックボックスは存在せず、すべてが白日の下に晒されている。それゆえ、TrueType 命令は PostScript ヒントに比べて桁違いに複雑である。当然のことながら、TrueType 命令はフォントデザイナーたちから激しい拒絶に遭った——これらを操るためには並外れた学習コストと、芸術的感性とは対極にあるシステムプログラマとしての過酷な論理的思考が要求されるからである。Monotype のように専任のヒンティングエンジニアを抱える一部の大手ファウンダリを除けば、今日私たちが目にする大半の TrueType フォントの命令は、フォント制作ソフトウェアによって機械的に自動生成されたものに過ぎない。これは誠に惜しむべきことである。なぜなら、TrueType 仮想マシンが秘めている強大なポテンシャルの大半が、未開拓のまま眠っているからである。付録 E のすべてを、TrueType 命令の技術的解剖に捧げている。

技術的な仕様の細部は付録に譲るとして、本章では最も本質的な実践的問いに焦点を当てる：**「私たちは実際にどのようにヒントを配置し、どのようにフォントに命令を与えるのか？」** すなわち、業界標準の三大ツール——FontLab、FontForge、そしてマイクロソフトが無償配布している Visual TrueType（VTT）——を用いて、いかにしてこの最高峰の技術を操るかを解き明かしていく。

PostScript ヒントは大きく2つの階層に分類される：フォント全体に影響を与える**グローバルヒント**（Global Hints）と、単一のグリフ内部にのみ作用する**個別ヒント**（Individual Hints）である。

## 1. グローバルヒント（Global PostScript Hints）

グローバルヒントにおいて、極めて重要な2大要素が存在する：
1. **整列ゾーン**（**Alignment Zones**：主要な基準高さおよびそれに伴う錯視調整の突き出し量 Overshoot、付録 §C.3.4.1–C.3.4.3 参照）；
2. **標準ステム幅**（**Relevant Stroke Thicknesses**）。

図 13-2 は、典型的な整列ゾーンとステム幅の分布構造を示している。フォント制作における最初のステップは、フォント内のすべての基準高さとストローク幅の統計的棚卸しを行うことである。ラテン文字フォントであればこれらは古典的な規範に従うが、その他の文字体系では丹念な測定と共通パターンの抽出が必要となる。

::: tip 図 13-2：PostScript フォントにおける主要な整列ゾーンの概念図（Computer Modern Sans Serif の例）。(1)–(2) 大文字の基準高さと大文字「O」の上部オーバーシュート；(3)–(4) 小文字の基準高さと小文字「o」の上部オーバーシュート；(5)–(6) ベースラインと「o」の下部オーバーシュート；(7)–(8) ベースラインと「O」の下部オーバーシュート。主要ステム幅：V1 は大文字の縦ステムおよび垂直正接部の太さ；V2 は小文字の同等部；H1 は大文字の横ステム幅；H2 は大文字「E」「H」のクロスバーおよび「o」の水平部幅；H3 は「O」の水平部幅；H4 は「z」の上部ストローク幅
![図 13-2：PostScript フォントにおける主要な整列ゾーンの概念図](/images/fonts-encodings/fig13-2.png)
*図 13-2：PostScript フォントにおける主要な整列ゾーンの概念図（Computer Modern Sans Serif の例）。*
:::

整列ゾーンは数学的には数値のペア、すなわち「基準高さ」と「オーバーシュート量」によって定義される。これらは PostScript フォントのプライベート辞書内のパラメータ `BlueValues` に格納される。ベースラインより下方に位置するゾーン（小文字「p」のディセンダなど）については、専用のパラメータ `OtherBlues` に格納しなければならない。

これらに加えて、3つの補助パラメータが存在する：
* `BlueScale`：オーバーシュートを強制的に無効化する文字サイズの閾値を定義する。この閾値より小さいサイズでは、エンジンは波打ちを防ぐために円弧の突き出しを直線文字と同一のピクセル行へと平坦化する。
* `BlueShift`：オーバーシュートが有効となる最小ピクセル移動量を規定する。
* `BlueFuzz`：整列ゾーンの許容誤差範囲（デフォルトは 1 設計単位）を規定する。

また、ブール値パラメータ `ForceBold` は、極小サイズ描画時にフォントを「太め」にレンダリングするようエンジンに明示的に指示し、細体との識別性を死守する。

標準ステム幅は、最も代表的な水平ステム幅が `StdHW`、垂直ステム幅が `StdVW` に記録され、その他の補助的な幅は `StemSnapH` および `StemSnapV` の2つの配列に格納される（**各方向最大12個まで**）。

### FontLab におけるグローバルヒント管理

FontLab のフォント情報ウィンドウ（`File > Font Info`）において、データは3つのタブに分散配置されている（図 13-3）：
1. **Hinting: Alignment zones（図 13-3 [a]）**：`Primary zones`（`BlueValues` 用）と `Secondary zones`（`OtherBlues` 用）の2つのリストを含む。**Auto zones** ボタンを押すことで、FontLab が自動測定して入力してくれる。
2. **Hints: Standard stems（図 13-3 [b]）**：`V Stems` と `H Stems` にそれぞれのステム幅を入力する。**Auto stems** ボタンによる自動測定も可能。
3. **Additional hinting parameters（図 13-3 [c]）**：`BlueScale`、`BlueShift`、`BlueFuzz` などの数値を手動設定する。

### FontForge におけるグローバルヒント管理

FontForge におけるグローバルヒント管理は、`Element > Font Info > PS Private Dictionary` の単一パネルで行われる。値は角括弧 `[...]` で囲まれた空白区切りの PostScript 配列構文で入力する。

特筆すべきは、FontForge の **Hist**（ヒストグラム）ボタンである。これをクリックすると対話型の度数分布図が表示される。棒グラフのバーの上にマウスを乗せると、正確な座標値や、その太さを持つグリフの総数、該当グリフの一覧がツールチップとして表示される！
バーをクリックすればそれが主標準値（`StdVW` など）に設定され、Shift キーを押しながらクリックすれば補助リスト（`StemSnapV` など）に追加される。`Sum Around` スライダは離散的なノイズを平滑化し、クラスタの中心を浮き彫りにする。

## 2. 個別ヒント体系（Individual PostScript Hints）

個別ヒントは、各グリフの内部で定義される局所的な指示である。設計者はラスタライズエンジンに対して、どの水平・垂直ストロークが主要な骨格であるかを伝える。エンジンは指定された座標に存在するストロークを検出し、それらがピクセルグリッド上で完全に均一な太さになるように調整する。

しかし、Adobe のヒント定義方式には根本的な問題があった：**ヒントが輪郭の節点ではなく、グリフ全体を横断する「幾何学的ゾーン（帯）」として定義されたことである。** ステム同士が離れている大文字「H」のような文字では完璧に機能するが、大文字「B」のように上下のループが中央で重なり合う複雑な形状では、ヒント帯同士が必然的に衝突・重複してしまう！

この衝突を解決するため、Type 1 において Adobe は**ヒント置換**（**Hint Replacement** / **Hint Substitution**）という極めて複雑な機構を導入した。輪郭線を描画するパスの途中で、重複するヒントを動的に有効化・無効化する手法である（Type 2 / OpenType CFF では `hintmask` 命令として整理された）。

さらに困難なのは、文字内部の白い空間——**字谷**（**Counters**）の均一性である。小文字「m」では、3本の縦ステムが同じ太さになるだけでなく、その間に挟まれた2つの白い字谷もピクセル単位で完全に等幅でなければならない。
Adobe は当初、平行する3本のストローク間を均等配分する `hstem3` / `vstem3` 演算子を導入したが、漢字の「皿」「目」（4画）、「冒」（7画）、さらには42画に及ぶ極限の文字「癴」のような東アジア文字の前では無力であった。そこでは線が不揃いになること以上に、黒い線同士が癒着して字谷が完全に消失してしまうことが致命的だからである。これに対処するため、Adobe は「字谷制御（Counter Control）」機構を開発し、Type 2/CFF の `cntrmask` へと結実させた。

### FontLab における個別ヒント操作

FontLab で PostScript ヒントを表示するには、`Tools > Hints & Guides > Type 1 Hinting` を選択する（図 13-4）。ルーラー上から Mac の Command（Windows の Ctrl）キーを押しながらドラッグすることでヒント線を引き出し、Shift キーで幅を調整できる。

さらに FontLab は、ヒントをアウトラインの節点に直接結びつける**リンク**（**Links**）という概念を導入した。節点が移動すればリンクも追従するため、より安全に作業できる。

# TrueType 仮想マシンと命令型ヒンティング（TrueType Instructions）

PostScript のヒントがラスタライザに対する「助言」であるとすれば、TrueType の命令体系は冷徹な「絶対専制」である。TrueType 命令は単なるパラメータではなく、完全なチューリング完全性を備えた低級アセンブリ言語そのものである。

デザイナーが TrueType 命令を目にしたときの戦慄は、フロイトが人間の無意識を「**抑圧された欲望が暗闇の中で蠢く洞窟**」と呼んだ光景に酷似している：

```ttasm
MIRP[00100]
MIRP[10100]
MIRP[01110]
SRP1[ ]
SRP2[ ]
SLOOP[ ]
```

このようなコードが何百行も並ぶ光景は、技術嫌いでなくとも冷や汗を流すのに十分である。しかし、真の制御を手に入れるためには、この仮想マシンの基本原理を理解しなければならない。

## 1. グリッドフィッティング輪郭（Grid-Fitted Outline）の原理

TrueType 命令の動作原理は明快である：**文字のラスタライズを最適化するために、離散ピクセルグリッド上でベジェ曲線輪郭そのものの幾何形状を力ずくで変形させる！**

各表示サイズ（PPM）において、命令群によって歪められた輪郭を**グリッドフィッティング輪郭**（**Grid-fitted Outline**）と呼ぶ。この変形された輪郭自体は見た目に美しくある必要はない。なぜなら、人間の目に触れることは決してなく、単にピクセル中心包含判定の鋳型として機能するだけだからである。

TrueType の世界において、輪郭とは点の集合にほかならない：
1. **接触点（Touched Points）**：命令によってピクセルの境界や中心に直接整列させられた点。一度移動された点は「Touched」とマークされ、原則として再移動されない。
2. **CVT 距離点（Points at CVT Distance）**：すでに接触した基準点から、**制御値テーブル**（**Control Value Table, CVT**）に定義された規定の距離（ステム幅など）を保つように配置される点。1ピクセル未満への縮退を防ぐ「最小距離（Minimum Distance）」プロパティが保証される。
3. **非接触点（Untouched Points —— グリフの「プロレタリアート大众」）**：直接の指示を受けず、接触した親ノードの移動に受動的に従う点。**IUP**（Interpolate Untouched Points）命令による線形補間によって滑らかに追従し、曲線の優美な弧を維持する。

## 3. マイクロソフト Visual TrueType（VTT）の工業的実践

マイクロソフトが無償提供する **Visual TrueType**（**VTT**）は、高水準の宣言型言語（VTT Talk）を用い、ネイティブな TrueType バイトコードをリアルタイム生成する最高峰のツールである。

### CVT の意味論と継承構造

VTT は、CVT テーブルの最初の120個のエントリに対して極めて厳密な標準セマンティクスを付与している：
* **基準高さグループ（CVT 0–19, 図 13-8）**：エントリ $n$ が平坦な基準高さを保持し、$n+1$ が対応するオーバーシュートを保持する（大文字高 $2+3$、ベースライン $8+9$、x-高さ $4+5$ など）。
* **ステム・セリフ体系（CVT 68–119, 図 13-9）**：大文字（Uppercase）、小文字（Lowercase）、数字（Figure）、その他（Other）に分類され、ストローク属性（StraightStroke、RoundStroke、SerifHeight **SH**、SerifExtension **SW**、Distance）および色（Black、White、Grey）が定義される。
* **継承木（Inheritance）**：すべての親となるエントリ 65 から、水平の母 66 と垂直の母 67 が派生し、各大文字・小文字のストローク幅がこれらを継承する（例：`68: 200 = 66 @27` —— 27 pt 以下では親のピクセル数に完全に従い、それ以上のサイズで初めて独立したピクセル計算を行う）。

::: tip 図 13-10：マイクロソフト Visual TrueType（VTT）の単一文字ヒンティング作業画面
![図 13-10：マイクロソフト Visual TrueType（VTT）の単一文字ヒンティング作業画面](/images/fonts-encodings/fig13-10.png)
*図 13-10：マイクロソフト Visual TrueType（VTT）の単一文字ヒンティング作業画面。*
:::

### VTT 実践チュートリアル要約（Trebuchet フォント）：
1. **大文字「O」**：頂点 3 を CVT 3（大文字オーバーシュート）、底点 9 を CVT 9 にアンカー固定。外側から内側に向けて水平リンク（CVT 70）と垂直リンク（CVT 74）を張り、最小距離 1px を保証。
2. **大文字「H」**：上端を CVT 2、下端を CVT 8 にアンカー固定。縦ステムに CVT 68 のリンクを張り、クロスバーの垂直位置は点 0 と 6 の間で補間。視覚的心理に基づき、端数が出た場合にクロスバーが上方に持ち上がるよう下側の点 2 を補間基準とする。
3. **大文字「A」**：頂点 8 をピクセル中心にアンカーし、斜めストロークには **Stroke ツール**（CVT 77）を適用。クロスバーの水平を保つため、端点間に `YShift` を適用。

フォント出荷時には `Tools > Ship Font` を実行し、ソースコードが格納されたプライベートテーブル（`TSI0`〜`TSI3`）をストリップしてバイナリサイズを削減・保護する。

## 5. FreeType 仮想マシン、自動ヒンティング（Auto-hinter）とサブピクセル描画

現代のデジタルタイポグラフィ環境において、オープンソースの **FreeType** ライブラリ（David Turner、Robert Wilhelm、Werner Lemberg らが創設）は、Linux、Android、ChromeOS などのプラットフォームで文字描画の中核を担っています。

### 1. アップル特許紛争とオープンソースの克服

1990年代初頭、アップルは TrueType のヒンティング技術に関して広範な特許（Auto-flipping、投影ベクトルと自由ベクトル、CVT Cut-In 閾値制御）を取得しました。商用 Linux ディストリビューションに対する特許侵害訴訟のリスクを回避するため、FreeType は長年にわたりバイトコード仮想マシンの実装をデフォルトで無効化（`#define TT_CONFIG_OPTION_BYTECODE_INTERPRETER` をコメントアウト）せざるを得ませんでした。2010年頃、これら特許の保護期間（20年）が満了したことで、FreeType は完全なバイトコード解釈系を公式に標準有効化しました。

### 2. FreeType 自動ヒンティング（Auto-hinter）アルゴリズム

特許封鎖の時代に開発された FreeType Auto-hinter は、フォント内部の命令に依存せず、ベジェ曲線から直接グリフの骨格を解析する高度な数学的パイプラインです：
1. **セグメント解析（Segment Analysis）**：曲線の1次導関数（速度ベクトル）を計算し、水平・垂直に近い微小線段を検出：
$$\mathbf{B}'(t) = \big( x'(t), \, y'(t) \big)$$
2. **エッジ検出（Edge Detection）**：同方向の微小線段をクラスタリングし、仮想ステムエッジを合成；
3. **ステム結合（Stem Linking）**：対向する平行エッジを探索して主幹（ステム）を同定し、メモリ上で等価的な標準ステム幅（CVT）を動的に統計算出；
4. **グリッドスナップ（Grid Snapping）**：ベースライン、x-ハイト、キャップハイトのアライメント領域に吸着させ、内部空間のプロポーションを均等に保ちます。

### 3. サブピクセル描画（Subpixel Rendering / ClearType）の物理革命

カラー液晶ディスプレイ（LCD）の各ピクセルは、赤（R）・緑（G）・青（B）の3つの微細な物理サブピクセルで構成されています。
マイクロソフトの **ClearType** や FreeType の LCD フィルタリング技術は、RGB を一体として扱う従来の制限を破り、各サブピクセルを独立に輝度制御することで、**水平方向の実効解像度を3倍に向上（$3\times$ Horizontal Resolution）**させました。

色にじみ（カラーフリンジ）を防止するため、5タップ FIR ローパスフィルタ核が適用されます：

$$W = \left[ \frac{1}{16}, \, \frac{4}{16}, \, \frac{6}{16}, \, \frac{4}{16}, \, \frac{1}{16} \right]$$

これにより、96 DPI の通常液晶ディスプレイにおいても、印刷物のような滑らかで読みやすい文字描画が実現されました。

PostScript の宣言型ヒント、TrueType のチューリング完全な仮想マシン、VTT Talk 高級言語、そして FreeType の自動ヒンティングとサブピクセル描画技術は、粗い離散格子の上で文字の美と可読性を守るために築き上げられた工学的金字塔です。
