# 第5章 · Unicode の実践と応用
### Chapter 5: Using Unicode
**著者：ヤニス・ハラランブス 博士（Yannis Haralambous, Ph.D.）**  
*『フォントとエンコーディング』（Fonts & Encodings）原著第 159–188 頁より*  

*訳者：[Lycoris \<lycorismisaka@gmail.com\>](mailto:lycorismisaka@gmail.com)*

---

現代の計算機世界において、テキストが流通するあらゆる領域に Unicode の足跡が刻まれている。世に存在する Unicode 対応ソフトウェアを網羅的に列挙することは無益な作業であろう。むしろ一歩退き、デジタル通信全体を貫く壮大な**データ伝送チェーン**（Data Transmission Chain）を俯瞰することとしよう。

1. **著者によるデータ入力**：著者が入力媒体を通じて文字を打ち込む。
2. **ローカル処理と中継**：データは著者のコンピュータの CPU を経由し、ネットワークを通じて読者や対話相手の端末へと向かう。
3. **端末での描画と印刷**：受信側の計算機が情報を画面上にレンダリング表示するか、あるいは印刷機器を通じて紙の上にインクで印字し、受信者が滞りなくそれを読めるようにする。

このチェーン上の主要結節点を点検してみよう。
- 第一に**データ入力**（Data Entry）：我々はいかにしてネイティブな Unicode データを入力すべきか？ また、既存のデータが旧来のレガシーコードで記述されている場合、いかにしてそれを高精度に Unicode へ変換すべきか？
- 第二に、データがメモリ上に展開された後の**視覚的表示**（Display）：そのためには Unicode を十全にサポートするデジタルフォント（Fonts）が不可欠である（フォントに関する広大な探訪は、本書後半の全編――第 6 章から第 14 章、ならびに付録 A〜F において繰り広げられる）。
- 第三に、校正と組版を終えたテキストがネットワークを通過する段階：第 2 章で詳述した MIME プロトコルや、Unicode の各種伝送符号化形式（UTF-8、UTF-16 など）がこれを担う。このプロトコル階層においては、下位の HTTP や TCP/IP にとって、運ばれるデータが Unicode であるか旧式コードであるかはパケットの透過的伝送において本質的な差異を持たない。
- 最終的に、データが通信端末に到達する。受信側のオペレーティングシステムは、当該文字集合をカバーするフォントを装備していなければならない。その後、受信者が返信を執筆すれば、このデータチェーンは再び逆方向へと巡回を始める。

本章において我々は、Unicode テキストを取得するための**三大基本経路**（Three Ways to Obtain Text in Unicode）に焦点を当てる。
1. **対話的入力**：視覚的な文字一覧表や文字パレット（Palettes）を通じて手動で文字を選択する。
2. **仮想キーボード**：入力メソッドや仮想キーボードドライバ（Virtual Keyboards）をカスタマイズし、自然なタイピングを実現する。
3. **データ変換**：工業用水準のトランスコーディングパイプラインにより、既存のレガシー文字コード（Legacy Encodings）を一括して標準 Unicode へ変換する。

## 対話的入力（Interactive Entry）

日常の文章では滅多に出現しない稀少な古典籍文字、特殊な数学演算子、難解な記号について、ユーザーに十六進コードポイントの暗記を強いることは非現実的である。最も直観的で参入障壁の低い入力手段は、OS や専用ツールが提供する視覚的パネルによる対話的選択である。

### Mac OS X の文字パレット（Character Palette）

Apple の Mac OS X において、OS 標準で極めて洗練された**文字パレット**（Character Palette）が内蔵されている。このツールは国際化入力メニューに直接統合されており、任意のテキスト編集領域においていつでも呼び出すことができる。

このパレットは二つの表示ビューを備えている。
- **記号および言語分類ビュー**：矢印、数学記号、約物、日本語の仮名などの直観的なグループ分け。
- **Unicode コード表ビュー**：Unicode 標準に準拠した全ブロックの網羅的リスト。

文字を選択すると、右下に高解像度の拡大プレビューが表示されるのみならず、現在のシステムにインストールされているフォントの中で**当該文字を正常に描画できるすべてのフォントの一覧**が提示される。これにより、組版者はどのフォントが最も優れたデザイン品質を持つかを一目で比較・検討できる。

## 仮想キーボード（Virtual Keyboards）

対話型パレットは時折の特殊記号入力には便利であるが、ポリトニック・ギリシャ文字、サンスクリット、アラビア語などによる長大な専門論文を執筆する場合、一文字ずつのクリック入力は組版作業を破綻させてしまう。

物理キーボードの打鍵動作を動的に Unicode コードストリームへと変換する**仮想キーボードドライバ**（Virtual Keyboards）が必要不可欠となる所以である。

### デッドキー機構と複合キーシーケンス（Dead Keys & Composition）

タイプライターの時代、文字 ‘e’ の上にアキュートアクセントを付して ‘é’ を打つために、機械式タイプライターには特殊な「**デッドキー**」（Dead Key）が備えられていた。アクセントキーを押すと印字ヘッドがインクリボンを叩いてアクセント記号を印字するが、**紙送りプラテンは機械的にロックされ、横に進まない**。直後に通常の ‘e’ を打鍵すると、印字ヘッドはアクセント記号の直下に重なって ‘e’ を打ち込み、合成文字が完成する。

デジタル時代において、このデッドキーの概念はソフトウェアによって見事に継承・抽象化された。
- ユーザーが所定のデッドキーを押下した際、画面上には直ちに文字は出力されない（カーソルはその場で待機する）。
- キーボードドライバの内部状態が遷移し、待機モードに入る。
- ユーザーが次のキー（例えば字母 ‘a’）を打鍵した瞬間、ドライバは状態遷移テーブルを参照し、両者を合成した事前合成文字 ‘á’（`U+00E1`）をアプリケーションへと発行する。

## レガシー文字コード変換工学（Data Conversion）

Unicode 普及以前に蓄積された数億件におよぶ旧来の文書資産（ISO 8859 シリーズ、Windows コードページ、Mac コードページ、中国 GB2312/GBK、日本 Shift_JIS、EUC-KR など）を、正確無比に Unicode へマイグレーションすることは、あらゆる情報システムが直面する必須課題である。

### マッピングテーブルの原理と変換アルゴリズム

トランスコーディングの神髄は**テーブルルックアップ写像**（Table Lookup）である。8 ビットコードと Unicode コードポイントの間に単純な数理公式は存在しないため、変換ライブラリはメモリ内に双方向マッピングテーブルを常駐させる。

典型的な変換処理では、三種類の境界リスクに対処せねばならない。
1. **未定義コードポイント（Undefined Code Points）**：元規格において未定義の不正バイトが出現した場合。
2. **マルチバイト途絶（Incomplete Multi-byte Sequences）**：ネットワークやバッファ境界でマルチバイト文字が中途で切断された場合。
3. **不可逆目標写像（Unmappable Characters）**：Unicode から容量 256 文字の旧コードページへ逆変換する際、文字が収容不能な場合。

これに対し、工業的エンジンは柔軟な**フォールバック戦略**を提供する。
- **厳格停止（Strict Abort）**：即座に例外を発行し、データの汚染を遮断する。
- **置換文字（Replacement Character）**：変換不能文字を ‘?’ や Unicode 置換文字 ‘’（`U+FFFD`）に置き換える。
- **実体参照化（Numeric Character References）**：XML/HTML 文脈において `&#x20AC;` のような十六進実体参照へと退避する。

### 業界標準：POSIX iconv ツールチェーン

システム水準のコード変換において最も堅固な標準が、POSIX 準拠の **`iconv`** ユーティリティおよび C 言語ランタイムライブラリである。

コマンドラインでの典型的な操作：
```bash
# 西欧 ISO-8859-1 ファイルを標準 UTF-8 へ変換
iconv -f ISO-8859-1 -t UTF-8 input.txt -o output.txt

# 簡体字中国語 GBK データを UTF-8 へ変換し、稀少文字エラーを自動スキップ
iconv -f GBK -t UTF-8//IGNORE legacy_chinese.txt > utf8_chinese.txt
```

C/C++ プログラムでは、3 つの標準 API によって制御される。
- `iconv_open()`：変換記述子（Conversion Descriptor）の割り当て。
- `iconv()`：高性能ポインタ走査とマルチバイト変換の実行。
- `iconv_close()`：リソースの解放。

### 現代のスクリプト言語における文字コード生態系

現代の高水準言語において、文字コード変換は言語基盤そのものに組み込まれている。

- **Perl の `Encode` モジュール**：  
  Perl 5.8 以降、言語ネイティブで抽象 Unicode 文字列モデルが確立された。標準モジュール `Encode` により、デコード（バイト列から抽象文字列への復元）とエンコード（抽象文字列から特定バイト列への直列化）が極めて平易に記述できる。
  ```perl
  use Encode qw(decode encode);
  my $characters = decode("Shift_JIS", $legacy_japanese_bytes);
  my $utf8_bytes  = encode("UTF-8", $characters);
  ```
- **Python の Unicode データモデル**：  
  Python 3 において、言語は不変のテキスト文字列（`str`、内部的に Unicode コードポイントで保持）と生バイナリバイト列（`bytes`）を峻別した。両者の暗黙の混同をコンパイラレベルで根絶したことにより、ソフトウェア業界を長年苦しめてきた文字化けの亡霊は決定的に払拭されたのである。
